Even after an iteration limit is reached, the approximation obtained so far may be useful.
However, invalid input or numerical breakdown requires investigating the cause before using a value.
SciOxide expresses these distinctions through errors, termination reasons, and partial-result diagnostics.

## `Err` and unsuccessful `Ok` values

The `Ok` variant of `Result<T, SciOxideError>` indicates that a result could be returned.
That alone does not mean a tolerance was achieved.
For iterative APIs, also inspect the termination reason in the result or report.

For `Err`, investigate the cause; for `Ok`, check the success conditions and partial result.


### What `Err(SciOxideError)` represents

`Err` represents invalid input, out-of-domain evaluations, non-finite values, numerical breakdown, and similar failures.
It also includes insufficient resources and failures of external providers, so the cause is not necessarily mathematical.
Check each API's contract for the treatment of output when some progress preceded the failure.

### What an unsuccessful `Ok(Result)` represents

Iterative solvers returning partial results record limit exhaustion or stagnation as the termination reason and include approximations and diagnostics in `Ok`.
Users examine residuals, feasibility, and work counts to decide whether to use the value or change the conditions and retry.
Termination types and accessor methods differ by field.
[Reading results](../../getting-started/reading-results/) collects representative examples.

`Admission::require` is a boundary that returns `ConvergenceFailure` when a count limit prevents execution.
It does not itself check convergence.
Whether a partial result can be returned or an error is produced depends on the called API's contract.

## Structured categories of `SciOxideError`

`SciOxideError` is an opaque struct, not an enum whose variants can be matched directly.
`kind()` returns one of the 20 `SciOxideErrorKind` kinds, and `view()` returns a `SciOxideErrorView` containing reasons and diagnostics.
Errors describe the failure through a category, argument or quantity identifier (`Argument` / `Quantity`), and details.
They retain no caller operation identifier, and such an identifier is not passed to checked arithmetic or `Admission::require()`.
Representative categories follow.

| Category | Example |
|---|---|
| `InvalidInput` | Reversed interval endpoints |
| `DimensionMismatch` | Incompatible matrix and vector shapes |
| `DomainError` | Cholesky factorization of a matrix that is not positive definite |
| `NonFinite` | NaN or infinity from inputs, callbacks, or arithmetic |
| `Singular` | A factorization pivot meets the singularity criterion |
| `ConvergenceFailure` | Non-convergence or count-limited refusal to execute at a boundary that does not return partial results |
| `NumericalInstability` | Numerical breakdown, such as violation of an iteration invariant |

A non-positive-definite input to Cholesky factorization produces `DomainReason::OutsideDomain`; reasons for numerical breakdown include `NumericalIssue::Breakdown`.
Some APIs instead report these as unsuccessful termination reasons.
Use the API's result type and category information rather than parsing error strings.
[Error categories and detailed views](../../scioxide-core/algorithms/errors-and-diagnostic-views/) explains the detailed views and reason enums for all 20 categories, with examples of reading the failure locations for dimensions and differentiation.

## Evaluating candidates and accepting states

Exposing candidates directly during iteration would leak intermediate states from failed trials.
Separate candidate evaluation from committing an accepted state, treating the process as a transaction.


A committed accepted state becomes the starting point for the next trial.
Do not treat rejected candidates as accepted states.
This mechanism does not roll back external side effects caused by user callbacks.

### Six transaction phases

1. **Preflight validation**: Check shapes, identifiers, resources, and other requirements before invoking user callbacks or changing visible state.
2. **Candidate generation**: Construct the next candidate from the current accepted state.
3. **Evaluation observation**: Evaluate functions or operators and count actual evaluations.
   Count retry evaluations as well, and distinguish cache lookups from evaluations.
4. **Acceptance decision**: Assess the candidate using residuals, error estimates, constraints, and other conditions.
5. **Commit**: Update the accepted numerical state and its diagnostics.
6. **Rollback**: Discard rejected candidates and preserve the last accepted state.

`SolveState` holds a solve identifier, an epoch distinguishing executions, counts, and metadata for accepted states.
It does not hold the solution vector itself.
The API's result or workspace owns the numerical state.
See the [index of solve identities and states](oxref:core-api-solve-state) for the related types.

## Recording attempts and recovering progress: `AttemptRecord` and `PartialFailure`

`AttemptRecord<P>` records a single call or resume attempt.
`kind()` distinguishes a new call from a resume, and `outcome()` distinguishes preflight rejection, failure, stopping, and success.
`counts()` returns work counts, and `progress()` returns a reference to saved progress.

`PartialFailure<P>` carries the primary error together with any progress that could be obtained.
`with_progress(error, capture)` attempts to capture progress and retains the primary error even if capture fails.
Inspect it through `error()` and `progress()`, or use `into_parts()` to separate the error and optional progress.

## Reliability categories for partial results (`PartialResultTrust`)

Reliability categories indicate which checks a state has passed.
The category alone does not determine suitability for a particular use.

| Category | Supported claim |
|---|---|
| `DiagnosticOnly` | A finite diagnostic state; no claim about feasibility or residual targets |
| `Admissible` | Satisfies the algorithm's acceptance and feasibility rules |
| `ResidualChecked` | An independently checked residual satisfies the configured threshold |
| `CertificateVerified` | Supported by an independently verified certificate |

For example, a small residual alone cannot guarantee forward accuracy in an ill-conditioned problem.
The scope of a `CertificateVerified` claim also depends on the contents of the verified certificate.

## Two paths at a count limit: unsuccessful Ok and boundary Err (interactive experiment)

The following cell is a small implementation example that uses the iteration limit in `SolveContext` to compute $x\leftarrow\cos x$.
Its inputs are an iteration limit, a dimensionless initial value, and a residual threshold.
It evaluates the candidate point's residual separately before accepting the state.
For the same stopping event, compare including a partial result in `Ok` with treating count-limited refusal to execute as an error through `Admission::require`.
The table shows the residual at the returned point and the forward error against the known fixed point $0.7390851332151607$.

```rust
//| id: concept-budget-exhaustion-paths
//| title: "Two paths at a count limit when finding the Dottie number (unsuccessful Ok and boundary Err)"
//| run: reactive
//| crates: [scioxide-core]
//| inputs:
//|   iteration_budget: {"type":"range","label":"Iteration limit [iterations]","description":"The maximum number of iterations allocated to the solve.","min":1,"max":40,"step":1,"value":10}
//|   initial_guess: {"type":"range","label":"Initial value x₀ [-]","description":"The starting point of the iteration.","min":0.0,"max":2.0,"step":0.1,"value":0.2}
//|   tolerance_exponent: {"type":"range","label":"Required residual exponent p (10ᵖ)","description":"The convergence threshold.","min":-14,"max":-2,"step":1,"value":-8}
use scioxide_core::{
    Admission, Budget, BudgetKind, ExecutionContext, PartialResultTrust, ProblemToken,
    RealScalar, ResidualTolerance, SolveBudgets, SolveIdentity, SolveState, algorithm_id,
};

let limit = Budget::try_from(iteration_budget as usize).map_err(|e| e.to_string())?;
let threshold = 10.0_f64.powf(tolerance_exponent);
let tolerance = ResidualTolerance::new(threshold, 0.0).map_err(|e| e.to_string())?;
let mut budgets = SolveBudgets::unbounded().with_limit(BudgetKind::Iteration, limit);
let mut state = SolveState::new();
let identity = SolveIdentity::new(
    ProblemToken::new(1),
    algorithm_id!("dottie", "picard", 1),
    0,
    0,
);
let mut context = state
    .begin_solve(ExecutionContext::sequential(), identity, &mut budgets)
    .map_err(|e| e.to_string())?;
let mut x = initial_guess;
let mut residual = (RealScalar::cos(x) - x).abs();
let mut success = tolerance
    .is_satisfied(residual, x.abs())
    .map_err(|e| e.to_string())?;
let mut final_admission = Admission::Granted(());
while !success {
    let admission = context.record_iteration().map_err(|e| e.to_string())?;
    if !admission.is_granted() {
        final_admission = admission;
        break;
    }
    let candidate = RealScalar::cos(x);
    residual = (RealScalar::cos(candidate) - candidate).abs();
    success = tolerance
        .is_satisfied(residual, candidate.abs())
        .map_err(|e| e.to_string())?;
    let trust = if success {
        PartialResultTrust::ResidualChecked
    } else {
        PartialResultTrust::DiagnosticOnly
    };
    context.commit_accepted(trust).map_err(|e| e.to_string())?;
    x = candidate;
}
let trust = if success {
    PartialResultTrust::ResidualChecked
} else {
    PartialResultTrust::DiagnosticOnly
};
let iterations = context.counts().own().iterations();
// Handle the same stopping event at a boundary that returns a partial result and one that turns count-limited refusal to execute into an error.
let partial: Result<_, scioxide_core::SciOxideError> = Ok((x, residual, trust));
let strict = final_admission.require();
let (point, checked_residual, checked_trust) = partial.map_err(|e| e.to_string())?;
let termination = if success {
    "Residual tolerance achieved"
} else {
    "Iteration limit"
};
emit_table_with_columns!(
    serde_json::json!([
    {"key":"0","label":"Termination reason","type":"string","nullText":"Undefined"},
    {"key":"1","label":"Iterations","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"2","label":"Returned point x","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"3","label":"Residual","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"4","label":"Threshold","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"5","label":"Forward error","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"6","label":"Reliability category","type":"string","nullText":"Undefined"}
    ]),
    vec![(
        termination,
        iterations,
        point,
        checked_residual,
        threshold,
        (point - 0.7390851332151607_f64).abs(),
        format!("{checked_trust:?}")
    )]
);
match strict {
    Ok(()) => emit_text!("The strict boundary also returns Ok: the residual tolerance was achieved."),
    Err(error) => {
        emit_text!("The strict boundary returns Err. The caller decides whether to use the partial result in the table above.");
        emit_table_with_columns!(
            serde_json::json!([
            {"key":"0","label":"Error category","type":"string","nullText":"Undefined"},
            {"key":"1","label":"Details","type":"string","nullText":"Undefined"}
            ]),
            vec![(format!("{:?}", error.kind()), format!("{:?}", error.view()))]
        );
    }
}
let outcome = if success {
    Outcome::satisfied("The residual condition was satisfied")
} else {
    Outcome::partial("Stopped at the iteration limit")
};
emit_outcome!(
    outcome
        .status(termination)
        .diagnostic("Residual", checked_residual, None)
        .diagnostic("Iteration count", iterations as f64, None)
);
```

A small limit leaves a nonconverged state, while a sufficient limit allows the residual condition to be met.
This example has no independent feasibility check, so nonconverged states are `DiagnosticOnly`.
The recorded work is the iteration count; this example does not implement function evaluation accounting.

## Summary and next steps

Check whether a result is `Ok` separately from whether the requested accuracy was achieved.
Decide how to use partial results by inspecting termination reasons and reliability categories.
Checking who owns the accepted state also clarifies what can be carried over to a retry.
