In numerical computing, the value type determines available operations and precision.
SciOxide represents the capabilities of real, complex, and other types through traits, and specifies the operations an algorithm requires as type bounds.
This page covers the contracts to check when choosing a type and the effects of rounding error on results.

## The hierarchy of scalar bounds and algebraic assumptions

The following four bounds are representative.
Similar names do not imply the same required capabilities.

| Trait | Main capabilities | Types that can implement it |
|---|---|---|
| `AlgebraicScalar` | Addition, subtraction, multiplication, division, zero, and one | External types can also implement it |
| `NumericScalar` | The above, plus conjugation, absolute values, real components, and other operations | `f32`, `f64`, and the corresponding `Complex` types |
| `RealScalar` | The above, plus partial ordering, elementary functions, floating-point classification, and other operations | `f32`, `f64` |
| `AffineValue` | Access to real components and shape representation | External vector types and others can also implement it |

`RealScalar` requires `NumericScalar`, and `NumericScalar` requires `AlgebraicScalar`.
`AffineValue` represents values with components, separately from this inheritance hierarchy.


`NumericScalar` and `RealScalar` are sealed traits that cannot be implemented externally.
This restriction keeps floating-point classification and type conversion semantics consistent among supported types; it does not provide a mechanism for users to change the rounding mode.
In generic code, the compiler generates processing for concrete types according to these bounds.

Because floating-point numbers include NaN, ordinary comparisons use `PartialOrd`.
Methods requiring `RealScalar` target real numbers; check each API's bounds to determine whether complex numbers are supported.
Providing basic arithmetic operations alone does not mean that the field axioms hold without rounding.

## Choosing between single precision (`f32`) and double precision (`f64`)

If the required precision is not yet known, first establish a reference result with `f64`.
When choosing `f32`, check both the reduction in memory use and whether the required accuracy can be maintained.

| Property | `f32` | `f64` |
|---|---|---|
| Effective bits | 24 | 53 |
| Approximate significant decimal digits | About 7 | About 16 |
| Unit roundoff $u$ | $2^{-24}$ | $2^{-53}$ |
| Size per element | 4 bytes | 8 bytes |

There is no uniform upper limit on acceptable condition numbers determined by the type alone.
Account for required digits, input errors, operation counts, and algorithmic stability.
Assuming independent rounding errors accumulate to approximately $\sqrt{N}u$, a rough model of the remaining digits is

$$
d \approx -\log_{10}(\kappa\sqrt{N}u)
$$

This is not a guaranteed error bound.

The following cell computes the sum of $a_k=1+A\sin(k\alpha)$ ($\alpha=1.618033988749895$).
The inputs are the dimensionless amplitude $A$ and term count $N$; the condition number is computed from the generated sequence as $\kappa=\sum|a_k|/|\sum a_k|$.
Using the rounded value after exact accumulation in `checked_sum` as the reference, compare sequential addition in `f32` and `f64`.
The error for `f32` also includes rounding when converting the inputs.

```rust
//| id: concept-scalar-digit-budget
//| title: "Varying amplitude and term count to compare predicted and observed remaining digits in f32 and f64"
//| run: reactive
//| crates: [scioxide-core]
//| inputs:
//|   condition_exponent: {"type":"range","label":"Input amplitude exponent p (A=10ᵖ)","description":"Vary the amplitude and compute the condition number of summation for the generated sequence.","min":0,"max":10,"step":1,"value":3}
//|   operation_exponent: {"type":"range","label":"Operation count exponent q (N=10ᑫ)","description":"The number of terms N in naive summation.","min":1,"max":5,"step":0.5,"value":3.5}
use scioxide_core::{RealScalar, checked_sum};

// Use the same f64 inputs as the reference. The f32 computation also includes rounding during type conversion.
fn measure(n: usize, amplitude: f64) -> Result<(f64, f64, f64, f64), String> {
    let terms: Vec<f64> = (1..=n)
        .map(|k| 1.0 + amplitude * RealScalar::sin(k as f64 * 1.618033988749895))
        .collect();
    let exact = checked_sum(&terms).map_err(|e| e.to_string())?;
    let absolute: Vec<f64> = terms.iter().map(|v| v.abs()).collect();
    let magnitude = checked_sum(&absolute).map_err(|e| e.to_string())?;
    let sum64 = terms.iter().fold(0.0_f64, |s, &v| s + v);
    let sum32 = terms.iter().fold(0.0_f32, |s, &v| s + v as f32);
    Ok((
        magnitude / exact.abs(),
        exact,
        (sum32 as f64 - exact).abs() / exact.abs(),
        (sum64 - exact).abs() / exact.abs(),
    ))
}
let amplitude = 10.0_f64.powf(condition_exponent);
let n = 10.0_f64.powf(operation_exponent).round() as usize;
let (condition, exact, error32, error64) = measure(n, amplitude)?;

    {"key":"1","label":"Input amplitude A","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"2","label":"Summation condition number κ","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"3","label":"Rounded value after exact accumulation","type":"number","format":{"significantDigits":6},"nullText":"Undefined"}
    ]),
    vec![(n, amplitude, condition, exact)]
);
let u = [f32::EPSILON as f64 / 2.0, f64::EPSILON / 2.0];
let digits = |e: f64| if e == 0.0 { None } else { Some(-e.log10()) };
emit_table_with_columns!(
    serde_json::json!([
    {"key":"0","label":"Type","type":"string","nullText":"Undefined"},
    {"key":"1","label":"Measured relative error","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"2","label":"Measured digits","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"3","label":"Model digits","type":"number","format":{"significantDigits":6},"nullText":"Undefined"}
    ]),
    vec![
        (
            "f32",
            error32,
            digits(error32),
            digits(condition * (n as f64).sqrt() * u[0])
        ),
        (
            "f64",
            error64,
            digits(error64),
            digits(condition * (n as f64).sqrt() * u[1])
        ),
    ]
);

let mut measured = [Vec::new(), Vec::new()];
let mut model = [Vec::new(), Vec::new()];
let mut exact_matches = [0_usize; 2];
for i in 0..=12 {
    let count = 10.0_f64.powf(1.0 + i as f64 / 3.0).round() as usize;
    let (kappa, _, e32, e64) = measure(count, amplitude)?;
    for (j, error) in [e32, e64].into_iter().enumerate() {
        if error == 0.0 {
            exact_matches[j] += 1;
        } else {
            measured[j].push([count as f64, -error.log10()]);
        }
        model[j].push([
            count as f64,
            -(kappa * (count as f64).sqrt() * u[j]).log10(),
        ]);
    }
}
// Use the same color for the measurements and model of a type, and draw the model dashed. Keep the vertical axis linear because it shows digit counts.
let (c32, c64) = ("#d97706", "#2563eb");
let series = vec![
    serde_json::json!({"name":"f32 measured", "points":measured[0], "style": {"color": c32}}),
    serde_json::json!({"name":"f32 model", "points":model[0], "style": {"color": c32, "lineType": "dashed"}}),
    serde_json::json!({"name":"f64 measured", "points":measured[1], "style": {"color": c64}}),
    serde_json::json!({"name":"f64 model", "points":model[1], "style": {"color": c64, "lineType": "dashed"}}),
];
emit_line_chart!(
    &series,
    options = &serde_json::json!({"xLabel": "Term count N [-]", "yLabel": "−log₁₀(relative error) [digits]", "xType": "log"})
);
emit_table_with_columns!(
    serde_json::json!([
    {"key":"0","label":"Type","type":"string","nullText":"Undefined"},
    {"key":"1","label":"Points matching the reference among the 13 sampled points","type":"number","format":{"significantDigits":6},"nullText":"Undefined"}

    vec![("f32", exact_matches[0]), ("f64", exact_matches[1])]

```

The chart uses term count on a logarithmic horizontal axis and digits derived from relative error on the vertical axis; each dashed line is the model for the type with the same color.
At points matching the reference value, the logarithm cannot be taken, so the digit count is undefined; exclude these points from the chart and report their count in a separate table.
Negative digit counts indicate relative error greater than 1.
Even at the same amplitude, changing the term count changes the degree of cancellation.
The purpose of this experiment is to interpret this behavior, including differences between model and measurements.

## Problem traits and solution methods

Problem traits describe what to compute, while solvers determine how to solve it.
For example, solving the same right-hand side function with different ODE methods compares methods without changing the model.

| Field | Problem trait | Provided operation |
|---|---|---|
| Linear algebra | `LinearOperator` | Compute $y=Ax$ without an explicit matrix |
| Quadrature | `Fn(S) -> Result<V, SciOxideError>`, `Fn(&[S]) -> Result<V, SciOxideError>` | Evaluate the integrand |
| Optimization | `ObjectiveFunction` | Evaluate the objective and, when supported, its derivatives |
| Root finding | `ScalarFunction`, `ResidualOperator` | Evaluate function values and, when supported, derivatives |
| ODEs | `OdeSystem` | Evaluate the right-hand side and, when supported, the Jacobian |

The method for obtaining derivatives depends on each solver's contract.
A path using `DerivativeStrategy` tries the specified candidates in order, advancing to the next candidate only on `Ok(None)`.
Errors are returned to the caller.
This does not mean that every solver automatically switches to automatic differentiation.
See [Richardson extrapolation and Ridders' method](../../scioxide-differentiate/algorithms/richardson-and-ridders/) for details.

## Summary and further reading

When choosing a type, consider required arithmetic capabilities and precision separately.
The condition number is not a property of the type; it depends on the relationship between the inputs and the quantity being computed.
After comparing measured errors with a reference, choose the scale of the stopping criterion in [Tolerances and residuals](../tolerances-and-residuals/).
The [foundation crate's API guide](../../scioxide-core/api/) gives the detailed contracts of each trait.
