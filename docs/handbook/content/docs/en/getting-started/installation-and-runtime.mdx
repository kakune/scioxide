SciOxide is a numerical computing library for Rust consisting of 19 crates.
Add the crates that provide the capabilities you need as dependencies.

This section explains the Cargo settings for adding SciOxide to your own Rust project, the MSRV (Minimum Supported Rust Version), support for `no_std` environments, the Nix development environment, and the execution model of this book's interactive cells.

---

## Adding Cargo dependencies

The workspace version of the source used on this page is 0.1.0.
Specify the version matching the [0.1.0 API reference](https://docs.rs/scioxide-core/0.1.0/scioxide_core/) in Cargo.toml.

```toml
[dependencies]
# Shared foundations (scalar types, tolerances, and range-safe arithmetic)
scioxide-core = "=0.1.0"

# Add crates as needed
scioxide-linalg = "=0.1.0"        # Dense matrices, matrix factorizations, and Krylov methods
scioxide-rootfind = "=0.1.0"      # Root finding for nonlinear equations
scioxide-ode = "=0.1.0"           # Ordinary differential equation solvers
```

### Edition and MSRV

- **Rust edition**: Rust 2024
- **MSRV (Minimum Supported Rust Version)**: `1.93.0`

SciOxide uses recent features of stable Rust and requires a compiler at or above the MSRV.

### Dependency policy

SciOxide's published library crates (`crates/scioxide-*`) **include no third-party crates among their normal published dependencies or build dependencies**.
Normal dependencies remain within the SciOxide crates.
Check the APIs and supported execution environments of the version you use when installing it.

### Switching between `std` and `no_std` + `alloc`

All SciOxide crates enable the `std` feature by default.
For embedded systems or bare-metal environments without an OS, set `default-features = false` and provide a heap allocator to use a `no_std` + `alloc` environment.
There is no need to specify a Cargo feature named `alloc`.

```toml
[dependencies]
scioxide-core = { version = "=0.1.0", default-features = false }
scioxide-linalg = { version = "=0.1.0", default-features = false }
```

When the `std` feature is disabled throughout the dependency graph, OS-dependent capabilities such as OS thread parallelism (`ThreadExecutor`) and the standard clock (`StdClock`) are disabled, and the deterministic sequential executor (`SequentialExecutor`) is used.

## Setting up the development environment (Nix)

Using Nix at the root of the SciOxide repository opens a development environment with a pinned toolchain.
Downloading the required packages takes time on the first run.

```bash
# Run in the SciOxide source directory
nix develop
```

This development shell contains the following tools.
- Rust 1.95.0, matching the MSRV (including `rustfmt`, `clippy`, `rust-analyzer`, and the `wasm32-unknown-unknown`, i686, and AArch64 targets)
- Node.js 24

Use `nix develop .#handbook` to run the handbook locally.
This shell also uses Rust 1.95.0 and provides the Wasm target, Node.js 24, pnpm, and Binaryen for optimizing Wasm.

## Wasm execution model and restrictions of handbook cells

The interactive code cells embedded in this book are compiled by the Oxiquill engine to the `wasm32-unknown-unknown` target and run in the browser's Wasm runtime.
This execution environment has the following characteristics and restrictions, which differ from those of native execution.

1. **Single-threaded sequential execution**: The browser environment creates no threads.
   Parallel policies (`ExecutionPolicy::Parallel`) and parallel dispatch through `ThreadExecutor` are unavailable; all execution is sequential.
2. **Time and time limits**: `StdClock` and execution deadlines `Deadline::after` that depend on `std::time::Instant` cannot be used in Wasm.
3. **Pointer width (usize)**: In a Wasm32 environment, `usize` is 32 bits wide (a maximum of approximately $4.29 \times 10^9$).
   Integer combinatorial functions returning `usize` (such as `checked_factorial` and `checked_binomial` in `scioxide-core`) therefore report overflow at lower thresholds than in a native 64-bit environment (whose maximum is $1.84 \times 10^{19}$).
   For example, $13! \approx 6.22 \times 10^9 > 2^{32}$ cannot be represented in 32 bits.
4. **Restrictions on validated computation**: Verified enclosure computations in `scioxide-validated` round endpoints outward using error-free transformations, so they do not modify floating-point control registers.
   Instead, they require round-to-nearest, ties-to-even, gradual underflow (no flush-to-zero), and masked floating-point exceptions, and read the control registers before each operation and after callbacks to check these conditions.
   Only x86 (SSE2), x86_64, and AArch64 are supported; in Wasm, `kind()` returns an error of kind `InvalidInput` (`InvalidInputReason::UnsupportedConfiguration`).
   The browser therefore displays the proof portion as "not executed."
   Any accompanying reference computation also carries no proof.

## Trying interactive cells locally

To run and modify the code examples in this book on your own machine, write them as ordinary Rust applications.

### 1. Creating a project and adding dependencies

```bash
cargo new scioxide-sandbox --bin
cd scioxide-sandbox
cargo add scioxide-core --path ../scioxide/crates/scioxide-core
cargo add scioxide-linalg --path ../scioxide/crates/scioxide-linalg
```

### 2. Transferring the code

The following cell displays the solution and backward error in a table.
Check that both the browser result and your local result are close to $x=(2,3)$.
To read the backward error diagnostics, solve with `solve_with_options` using the factors constructed by `LuDecomposition::factor(&matrix)`.
When trying this locally, place the code inside `fn main() -> Result<(), String> { ...; Ok(()) }`.
`emit_*` is an output macro for the handbook; replace it with `println!` or a similar mechanism in an ordinary Rust project.

```rust
//| id: installation-linear-system
//| title: "A linear system example that can also be reproduced locally"
//| run: button
//| crates: [scioxide-linalg]
use scioxide_linalg::{
    DirectSolveOptions, Estimation, LuDecomposition, Matrix, RankPolicy, Vector,
};

let matrix = Matrix::from_vec(2, 2, vec![3.0_f64, 1.0, 1.0, 2.0]).map_err(|e| e.to_string())?;
let rhs = Vector::from_vec(vec![9.0_f64, 8.0]);
let lu = LuDecomposition::factor(&matrix).map_err(|e| e.to_string())?;
// Backward error diagnostics are not computed by default; request them explicitly through solve_with_options.
let options = DirectSolveOptions::new(RankPolicy::Exact).with_residual(Estimation::Estimate);
let result = lu
    .solve_with_options(&rhs, &options)
    .map_err(|e| e.to_string())?;
let solution = result.solution().ok_or("The solution was not accepted")?;
let residual = result.report().residual().ok_or("The requested residual diagnostics are absent")?;
emit_table_with_columns!(
    serde_json::json!([
    {"key":"0","label":"x₁","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"1","label":"x₂","type":"number","format":{"significantDigits":6},"nullText":"Undefined"},
    {"key":"2","label":"Backward error with respect to the original matrix [-]","type":"number","format":{"significantDigits":6},"nullText":"Undefined"}
    ]),
    vec![(
        solution.as_slice()[0],
        solution.as_slice()[1],
        residual.scaled_norm()
    )],
    metadata = serde_json::json!({"id":"solution"})
);
emit_outcome!(
    Outcome::satisfied("The direct solution was accepted")
        .status(format!("{:?}", result.report().termination()))
);
```

```bash
cargo run
```
