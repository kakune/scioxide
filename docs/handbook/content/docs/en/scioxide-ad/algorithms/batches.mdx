Many computations evaluate the same expression repeatedly from shared parameters $\theta$ and per-item values to obtain a sum or mean and its gradient, including Monte Carlo expectations, mean per-sample losses, and sums of partially separable functions.
`BatchPlan` packs many independent items into lanes (one SIMD element) in groups of `W`, chooses a numeric type according to whether gradients are requested, and returns bitwise identical results regardless of worker count.
This page covers writing evaluation functions and data, blocks and summation order, mode selection, standard errors, directional derivatives, and workspace.

## Derivatives of sums and means

For items $i = 0, \dots, n - 1$, evaluate $y_i = f(\theta, a_i, d_i)$ from shared parameters $\theta$, active inputs $a_i$ (per-item values to differentiate), and passive data $d_i$ (values not differentiated), and compute the sum $F = \sum_i y_i$ or mean $\bar F = F/n$.
Differentiation is linear, so

$$
\nabla_\theta F = \sum_{i} \nabla_\theta f(\theta, a_i, d_i), \qquad
\nabla_{a_i} F = \nabla_{a_i} f(\theta, a_i, d_i)
$$

and the parameter gradient is the sum of per-item gradients, while input gradients are independent for each item.

Suppose there is an intermediate quantity $q$ depending only on parameters, as in $f(\theta, a, d) = h(q(\theta), a, d)$.
The chain rule gives $\nabla_\theta F = J_q(\theta)^\top \sum_i \bigl(\partial h / \partial q\bigr)^{\!\top}$, so evaluate $q(\theta)$ once, stop per-item reverse sweeps at $q$ and accumulate adjoints, then perform just one final reverse sweep from $q$ to $\theta$.

If $d_i$ are independent samples of a random variable $Z$, $\bar F$ is a Monte Carlo estimator of the expectation $\mathbb{E}[f(\theta, Z)]$, with standard error $s/\sqrt{n}$ using the sample standard deviation $s$.
$\nabla_\theta \bar F$ is the mean of pathwise derivatives and is an unbiased estimator of $\nabla_\theta \mathbb{E}[f]$ when differentiation and expectation can be interchanged.
A sufficient condition for interchange is that $f$ is almost surely differentiable in $\theta$ and Lipschitz continuous with an integrable Lipschitz constant.
Functions such as $\max(S - K, 0)$ whose kinks occur only on a probability-zero set satisfy this condition.
For discontinuous functions such as $\mathbf{1}\{S > K\}$, the pathwise derivative is zero almost everywhere and cannot estimate the derivative of the expectation.

## `BatchFunction` and `BatchData`

`BatchFunction<S>` is a trait for writing the evaluation function once for numeric types `R: Real<S>`; it requires `Sync` because workers share it.

- `type Shared<R: Real<S>>` is the type of the item-independent intermediate quantity $q(\theta)$.
- `prepare(parameters)` constructs `Shared<R>` from parameters and is called once per block (defined below).
- `item(shared, inputs, data)` is called once per group (`W` items), evaluating one item per lane.
  `inputs` contains active inputs of type `R`; `data` contains passive data of type `R::Base` (`Lanes<S, W>`).
  Bring data into arithmetic with `R::passive(d)`.

Both methods are generic over numeric types, so the same implementation supports value evaluation (`Lanes`), forward mode (`MultiDual<Lanes, N>`), reverse mode (`Var<Lanes>`), and directional derivatives (`Dual<Lanes>`).
In unit tests, `prepare` and `item` can be called directly with `f64`.
Returning an error stops batch evaluation.
`item` operates on types with lanes, so write value-dependent branches with `select` rather than `if` ([Branches, masks, and table lookup](../control-flow/)).

`BatchData<S>` provides per-item values (active inputs, directions, and passive data) and also requires `Sync`.
Each item has `width` values; `fill(first, width, column, lanes)` writes value `column` of items `first..first + lanes.len()` into `lanes`.
Batch evaluation calls it once per value per group, with `column < width` and at most `W` lanes.
Providers whose same-valued columns for consecutive items are adjacent (overlapping windows of one array or arrays per value) can copy without rearrangement.

Slices `[S]`, `Vec<S>`, and arrays `[S; N]` implement `BatchData` as row-major tables (items × `width`); value `column` of item `i` is element `i·width + column`.
`column ≥ width` returns `OutOfBounds` (quantity `batch_columns`); insufficient rows return `OutOfBounds` (quantity `batch_rows`).
When there are no active inputs or data, pass the zero-element array `&[]`.
`BatchDataFn::new(|first, width, column, lanes| …)` wraps a closure with the same arguments as `fill` as a provider, without performing checks or allocations itself.
Providers able to generate values from item and column indices, such as random values, can be passed this way without constructing tables ([One-shot means and function providers](#one-shot-means-and-function-providers)).

## `BatchPlan` and blocks

`BatchPlan::<W>::new(items, parameters, inputs, data, reduction, options)` constructs a plan with `items` items, `parameters` shared parameters, and `inputs` active inputs and `data` passive values per item.
`W` (default 8) is the number of items packed into one `Lanes`.
`W = 0` returns `InvalidInput` (argument `lanes`, `OutOfRange`); `BatchReduction::Mean` with `items = 0` returns `InvalidInput` (argument `items`, `Empty`).

`BatchReduction` has two forms: `Sum` (default, giving $+0$ for no items) and `Mean`.

Items are partitioned into consecutive blocks, and blocks into groups of `W` items.
Block size `block()` is the value from `BatchOptions::with_block` (default 256) rounded up to a multiple of `W`; the block count is `blocks()` $= \lceil n / \text{block} \rceil$.
Missing lanes in the last group repeat the final item and are excluded from all outputs.
Reverse mode seeds missing lanes with zero.

Each block sums item values in item order; for `Mean` it also computes the mean and sum of squared deviations.
The calling thread combines block results by block index with pairwise summation (adding neighboring blocks, then adding pairs of those results).
The summation tree depends only on the block count, not on how blocks are assigned to workers, so estimates, gradients, and errors have the same bits regardless of execution policy or worker count.
Means and sums of squared deviations are combined with the formulas of Chan, Golub, and LeVeque.

Let block size be $b$ and block count $B$.
Summing in item order within a block adds at most $b - 1$ roundings, and pairwise block summation adds $\lceil \log_2 B \rceil$ levels; error bounds for sequential and pairwise summation (Higham, §4.2) therefore bound the summation rounding error by

$$
\Bigl| \widehat{F} - F \Bigr| \le \gamma_k \sum_i |y_i|, \qquad k = b + \lceil \log_2 B \rceil, \qquad \gamma_k = \frac{k\varepsilon}{1 - k\varepsilon}
$$

where $\varepsilon$ is unit roundoff ([Floating-point numbers and conditioning](../../../concepts/floating-point-and-conditioning/)).
$k$ is one greater than the number of rounding levels $b - 1 + \lceil \log_2 B \rceil$, so even including rounding from division by $n$ in `Mean`, the mean's error is at most $\gamma_k \sum_i |y_i| / n$.
Forward-mode gradients sum per-item tangents in the same order and have a bound of the same form.
Reverse-mode gradients accumulate group adjoints per lane before reversing the shared part, then sum over lanes, so summation order differs from forward mode.
Per-item values and derivatives themselves have the accuracy of the numeric type.

## Value, forward, and reverse modes

Batch evaluation chooses a numeric type according to whether gradients are requested and the number $m$ of active values (parameters plus inputs).
Conditions are checked from the top row of the table downward.

| Condition | Item numeric type | `BatchMode` |
|---|---|---|
| No gradient requested, or $m = 0$ | `Lanes<S, W>` | `Value` |
| `KinkPolicy::Error`, `DerivativeMode::Reverse`, or `Auto` with $m > 4$ | `Var<Lanes<S, W>>` | `Reverse` |
| Either `Auto` or `DerivativeMode::Forward`, with $m \le 4$ | `MultiDual<Lanes<S, W>, m>` | `Forward { tangents: m }` |

`DerivativeMode::Forward` with $m > 4$ returns `InvalidInput` (argument `options.derivative_mode`, `UnsupportedConfiguration`).
However, `KinkPolicy::Error` selects reverse mode first, avoiding this error.
Forward mode attaches $m$ tangents to every value and updates them all at each operation, so per-item cost grows with $m$, but no tape is used.
Reverse-mode cost is a constant multiple of value evaluation independent of $m$, with tape recording and sweeps added.

Reverse mode uses one tape per worker.
For each block it records parameters and `prepare` once and remembers the recording length.
For each group it records `item`, reverses to the remembered position to read input adjoints, and rewinds the tape to that position.
Finally, it reverses the shared part with accumulated adjoints from all groups once and sums parameter gradients over lanes.
Tape length need only cover the shared part and one group.

In every mode wrappers take their values from primal values, so the estimate `value()` is bitwise identical across value, forward, and reverse modes.
Gradient summation order differs by mode, giving agreement within rounding.
In reverse mode, `BatchEstimate::kinks()` returns the count of operations whose active arguments hit kinks, counting once per item lane (once per block for `prepare`).
Forward mode uses only the kink convention (midpoint) and does not count occurrences.

`KinkPolicy::Error` forces reverse mode.
The evaluating plan applies its kink policy and byte limit to worker tapes.
Thus under `KinkPolicy::Error`, active arguments hitting kinks cause `evaluate_into` and `hvp_into` to return `DomainError`.
`jvp_into` evaluates with dual numbers, uses no tape, and counts no kinks, so this policy has no effect.

Under `NonFinitePolicy::Error`, parameters and directions are checked before evaluation and active inputs when loaded; nonfinite values return `NonFinite` (`Input`).
Passive data are not checked.
Estimates, per-item values, gradients, and requested input gradients are checked before writing; nonfinite values return `NonFinite` (`Output`).
The default `Propagate` writes computed values directly ([Kinks and nonfinite-value policies](../nonsmooth-and-nonfinite-policies/)).

## Outputs and estimates

`evaluate_into(function, parameters, inputs, data, outputs, workspace, context)` writes outputs requested through `BatchOutputs` and returns a `BatchEstimate`.
Only whether gradients are requested determines whether automatic differentiation is used.

- `with_values(values)` writes per-item $y_i$ (length `items`).
  The aggregation scale ($1/n$ for the mean) is not applied.
- `with_parameter_gradient(gradient)` writes the gradient of the reduced value with respect to parameters (length `parameters`).
- `with_parameter_gradient_error(error)` writes standard errors of gradient components using block batch means (below).
- `with_input_gradient(gradient)` writes per-item input gradients (row-major `items × inputs`) without applying the aggregation scale.

Inconsistent output lengths return `DimensionMismatch`.
Outputs are accumulated in workspace and written only after every block succeeds, so errors leave all outputs unchanged.
Function and data-provider errors are returned unchanged; cancellation of `context` returns `ExecutionStopped`.
A workspace size or number of active values (parameters plus inputs) not fitting in `usize` returns `SizeOverflow`; failure to grow workspace returns `AllocationFailure`.

`BatchEstimate` contains the following values.

- `value()` is the sum or mean.
- `standard_error()` is the mean's standard error $s/\sqrt{n}$ ($s^2 = \sum_i (y_i - \bar y)^2/(n - 1)$) for `Mean` with at least two items, and `None` otherwise.
- `derivative()` is the reduced directional derivative from `jvp_into` and is `None` for `evaluate_into`.
- `items()` and `blocks()` are item and block counts; `mode()` is the mode used (`BatchMode`).
- `kinks()` is the reverse-mode kink count, or `None` for value and forward modes.

Per-item parameter gradients are not stored, so gradient standard errors are estimated from block means (batch means).
Let block $j$ have $n_j$ items and mean gradient $\bar g_j$, with overall mean $\bar g$; the standard error of the mean gradient is

$$
\mathrm{SE}(\bar g) = \sqrt{\frac{\sum_j n_j (\bar g_j - \bar g)^2}{(B - 1)\,n}}
$$

and is multiplied by $n$ for `Sum`.
This assumes block means are approximately independent and identically distributed; the estimator itself varies with $B - 1$ degrees of freedom, so few blocks give a rough standard-error estimate.
Fewer than two blocks returns `InvalidInput` (argument `outputs.parameter_gradient_error`, `OutOfRange`).

The next two cells evaluate the expectation of the terminal value of geometric Brownian motion at maturity $T$,

$$
S_T = S_0 \exp\Bigl( \bigl(r - \tfrac{1}{2}\sigma^2\bigr) T + \sigma \sqrt{T}\, Z \Bigr), \qquad Z \sim N(0, 1)
$$

using standard normal samples $z_i$ in batch evaluation.
Parameters are $\theta = (S_0, \sigma, r)$ ($S_0$ [JPY], $\sigma$ [1/√year], $r$ [1/year]), with $T = 1$ year.
`prepare` constructs drift $(r - \sigma^2/2)T$ and diffusion $\sigma\sqrt{T}$; `item` returns $S_0 \exp(\text{drift} + \text{diffusion} \cdot z_i)$.
The closed form is $\mathbb{E}[S_T] = S_0 e^{rT}$, with $\partial/\partial S_0 = e^{rT}$, $\partial/\partial \sigma = 0$, and $\partial/\partial r = T S_0 e^{rT}$.
Samples are generated from a seed with `Normal` and `Xoshiro256StarStar` from scioxide-random ([scioxide-random chapter](../../../scioxide-random/)).

```rust
//| id: ad-batch-forward-model
//| kind: definitions
//| title: "Geometric Brownian terminal values and standard normal samples"
//| crates: [scioxide-ad, scioxide-core, scioxide-random]
use scioxide_ad::{BatchFunction, Real};
use scioxide_core::SciOxideError;
use scioxide_random::{Distribution, Normal, SeedableRng, Xoshiro256StarStar};

/// Terminal value S_T at maturity T [year]. Parameters: [S₀, σ, r]; data: standard normal z.
pub(crate) struct Terminal {
    pub(crate) maturity: f64,
}

/// Path-independent quantities: S₀, drift (r − σ²/2)T, and diffusion σ√T.
pub(crate) struct Market<R> {
    spot: R,
    drift: R,
    diffusion: R,
}

impl BatchFunction for Terminal {
    type Shared<R: Real> = Market<R>;
    fn prepare<R: Real>(&self, p: &[R]) -> Result<Market<R>, SciOxideError> {
        let (spot, sigma, rate) = (p[0], p[1], p[2]);
        Ok(Market {
            spot,
            drift: (rate - sigma * sigma * 0.5) * self.maturity,
            diffusion: sigma * Real::sqrt(self.maturity),
        })
    }
    fn item<R: Real>(&self, m: &Market<R>, _: &[R], z: &[R::Base]) -> Result<R, SciOxideError> {
        Ok(m.spot * (m.drift + m.diffusion * R::passive(z[0])).exp())
    }
}

/// Generate n standard normal samples from seed.
pub(crate) fn normals(n: usize, seed: u64) -> Result<Vec<f64>, SciOxideError> {
    let law = Normal::new(0.0, 1.0)?;
    let mut rng = Xoshiro256StarStar::from_seed(seed);
    law.sample_n(&mut rng, n)
}
```

At the defaults $n = 4096$ and $\sigma = 0.2$ with seed 42, all three modes give the bitwise identical estimate $102.95621368850519$ JPY.
With three active values, `Auto` selects forward mode (three tangents); specifying `Reverse` selects reverse mode.
Forward and reverse gradients differ in the last digit and agree within rounding due to different summation orders.
The reverse-mode kink count is zero; this model uses no functions with kinks.

The estimate's standard error is 0.327 JPY, matching $s/\sqrt{n}$ computed with `f64`.
The difference from the closed form $S_0 e^{rT} = 103.045$ JPY is $-0.27$ standard errors; differences for the three gradients also lie between $-0.34$ and $-0.28$ standard errors.
The closed form for $\partial/\partial \sigma$ is zero; the estimate $-0.35$ lies within its standard error of 1.25.
The pathwise derivative $S_T(-\sigma T + \sqrt{T} z)$ has large variance despite its zero mean, so estimating zero requires many paths.
$\partial/\partial S_0 = \bar S / S_0$ and $\partial/\partial r = T \bar S$ are proportional to the estimate for every sample, so differences from their closed forms share the sign of the estimate's difference.
The magnitudes of their standardized differences differ from the estimate's because its standard error uses per-item values, whereas gradient standard errors use batch means of 16 blocks.

With seed 7, standardized differences are $+1.6$ and $+1.5$; shifts of one or two standard errors with the seed are natural sampling-error magnitudes.
At $\sigma = 1$ and $n = 16384$, heavier tails raise the estimate's standard error to 1.03 JPY, three times that at $\sigma = 0.2$ despite quadrupling paths.

## One-shot means and function providers

`batch_mean(function, parameters, data, items)` treats rows of the row-major table `data` (`items` rows × `data.len() / items` columns) as passive data and returns the mean $\bar F$; `batch_mean_and_grad` returns a pair of $\bar F$ and its parameter gradient (a scioxide-linalg `Vector`).
Internally this evaluates `BatchPlan::<8>` with `BatchOptions::new()`, no active inputs, `BatchReduction::Mean`, and one worker; estimates and gradients have the same bits as `evaluate_into` in this configuration.
Every call allocates one workspace (and a tape and gradient if gradients are requested).
`items = 0` returns `InvalidInput` (argument `items`, `Empty`); `data.len()` not divisible by `items` returns `DimensionMismatch`.
Use `BatchPlan` for sums, per-item inputs or values, gradient standard errors, or different lane or worker counts.

## Directional derivatives and Hessian–vector products

`jvp_into(function, parameters, inputs, data, parameter_direction, input_direction, derivatives, workspace, context)` computes the directional derivative with respect to $\varepsilon$ at $(\theta + \varepsilon u, a_i + \varepsilon w_i)$ using `Dual<Lanes<S, W>>`.
$u$ is the parameter direction and $w_i$ the per-item input direction, passed with a provider of the same type as the inputs.
It writes per-item directional derivatives to `derivatives` (length `items`, without the aggregation scale) and returns the reduced directional derivative in `BatchEstimate::derivative()`.
The mode is `Forward { tangents: 1 }`.

`hvp_into(function, parameters, inputs, data, parameter_direction, input_direction, parameter_product, input_product, workspace, context)` writes derivatives with respect to $\varepsilon$ in the same direction of the reduced value's parameter gradient and the per-item input gradients.
`parameter_product` (length `parameters`) is the derivative of the reduced value's parameter gradient, the parameter part of the reduced value's Hessian–vector product.
`input_product` (`items × inputs`) contains derivatives of per-item input gradients without the aggregation scale, as with `with_input_gradient`.
For mean reduction, dividing `input_product` by $n$ gives the input part of the reduced value's Hessian–vector product.
Under conditions where `evaluate_into` selects forward mode, each value is represented by `Dual<MultiDual<Lanes<S, W>, N>>` ($N = m$), using forward-over-forward.
The inner `MultiDual` value and $N$ tangents hold the value and derivatives in unit directions of active values (gradient components), as in `evaluate_into`.
The derivative component of the outer `Dual` is also a `MultiDual`: its value holds the directional derivative in direction $(u, w)$, and its $N$ tangents hold derivatives of gradient components with respect to $\varepsilon$ (Hessian–vector product components).
`BatchMode::Forward { tangents }` counts these two sets of tangents and returns $2N$ (8 for four active values).
Otherwise items are evaluated with `Var<Dual<Lanes<S, W>>>` (forward-over-reverse), and the mode is `Reverse`.

Both return `DimensionMismatch` for slices of inconsistent lengths; other errors match `evaluate_into`.

## Workspace and parallel execution

`workspace_requirements(workers)` returns the storage needed by `workers` workers as `BatchRequirements`.
It comprises per-worker lane storage, per-block results, and per-item accumulated values; read `workers()`, `blocks()`, `items()`, and the byte count `bytes::<S>()` per scalar type (excluding tape contents).
Worker counts must be from 1 to 64; other values return `InvalidInput` (argument `workers`, `OutOfRange`).
`workspace::<S>(workers)` returns a `BatchWorkspace` allocated to the requirements, or `AllocationFailure` on allocation failure.

`try_reserve(requirements)` on `BatchWorkspace` grows storage; `check(requirements)` returns whether retained storage suffices as a `Capacity`.
`evaluate_into` grows it automatically if insufficient.
Requirements exclude tapes.
A worker holds two tapes, one for gradients and one for Hessian–vector products; each grows on first use within the evaluating plan's `BatchOptions::with_byte_limit` limit.
Growth exceeding the limit gives `ResourceLimit` ([Tape lifecycle and reuse](../tape-lifecycle/)).
The limit applies only to growth during that plan's evaluation; a tape grown under a larger limit retains its storage.
In sequential execution, evaluation with workspace warmed by the same plan performs no allocations.

`BatchOptions` has the following settings; `BatchOptions::new()` returns defaults.

| Method | Default | Meaning |
|---|---|---|
| `with_execution_policy` | `ExecutionPolicy::Sequential` | Policy for assigning blocks to workers |
| `with_block` | 256 | Items per block (rounded up to a multiple of `W`) |
| `with_derivative_mode` | `DerivativeMode::Auto` | Gradient mode |
| `with_non_finite_policy` | `NonFinitePolicy::Propagate` | Nonfinite-value policy |
| `with_kink_policy` | `KinkPolicy::Midpoint` | Kink policy (`Error` selects reverse mode and returns `DomainError` at kinks) |
| `with_byte_limit` | None | Bytes each worker's individual tapes can preallocate |

Parallel execution assigns consecutive block ranges to workers according to the execution policy and workers of `ExecutionContext`.
Each worker uses its own lane storage and tape and places block results in workspace.
The calling thread combines them using the pairwise summation above, giving bitwise identical results to sequential execution.
`context.check()` is called before execution, once per block, and before output writing; output is therefore not written even for zero-item evaluations or a stop requested during the last block.
Browser cells cannot use threads in Wasm, so the following cells demonstrate only sequential execution.

The next two cells use the same terminal-value model to examine block size and directional derivatives.

## Summary

For sums or means of many independent items, write `BatchFunction` once generically over numeric types and evaluate with `BatchPlan`; value, forward, or reverse mode is selected according to gradient requests, and estimates have the same bits in every mode.
The default is forward mode for at most four active values and reverse mode for more; reverse mode records and sweeps the parameter-only `prepare` part just once per block.
Results follow pairwise summation by block index, preserving bits when worker count changes; summation rounding error is at most $\gamma_{b + \lceil \log_2 B \rceil} \sum_i |y_i|$.
When comparing Monte Carlo estimates with closed forms or other estimates, use `standard_error()` and batch means `with_parameter_gradient_error` with sufficiently many blocks, interpreting differences in standard-error units.
Directional derivatives and Hessian–vector products use `jvp_into` and `hvp_into` with the same plan and workspace.
If only a table's mean and gradient are needed in the default configuration, `batch_mean_and_grad` returns identical bits in one call; values generated on demand without a table can be provided with `BatchDataFn`.
