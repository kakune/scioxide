This page summarizes the shared premises of `scioxide-ad`'s algorithm pages.
These cover representing computations as statement sequences, notation, the sweeps and memory needed for each derivative quantity, and contracts shared by all number types.
Finally, it lists the questions answered by each page.

## Computational graphs and statement sequences

Functions differentiated with `scioxide-ad` are ordinary Rust code written for `R: Real` ([Number types, lanes and generic code](number-types-and-lanes/)).
Running the code at a chosen evaluation point produces a fixed sequence of operations such as arithmetic and elementary functions.
Let the inputs be $v_1 = x_1, \dots, v_n = x_n$ and construct subsequent values as follows:

$$
v_i = \varphi_i\bigl(v_j\bigr)_{j \in P(i)}, \qquad P(i) \subset \{1, \dots, i - 1\}, \qquad i = n + 1, \dots, N
$$


$\varphi_i$ is one operation, $P(i)$ is the set of its argument indices, and the output is a tuple of values $\mathbf{y} = F(\mathbf{x})$ selected from this sequence.
Each value is defined exactly once from earlier values, so the dependencies form a directed acyclic graph (computational graph).
This sequence is called a Wengert list; an individual operation recorded on a tape is called a statement.

Automatic differentiation computes the following local partial derivatives at the evaluation point and composes them using the chain rule:

$$
c_{ij} = \frac{\partial \varphi_i}{\partial v_j}, \qquad j \in P(i)
$$


Forward mode uses the input tangent vector $\dot{\mathbf{x}}$ as a seed and computes $\dot v_i = \sum_{j \in P(i)} c_{ij}\,\dot v_j$ in sequence order.
Reverse mode uses the output cotangent vector $\bar{\mathbf{y}}$ as a seed and accumulates $\bar v_j = \sum_{i : j \in P(i)} \bar v_i\,c_{ij}$ in reverse sequence order.
$\bar v_j$ is called the adjoint of $v_j$.
A traversal of the sequence is called a sweep.

For example, the list and local partial derivatives for $f(x_1, x_2) = x_1 x_2 + \sin x_1$ are as follows.

| $i$ | Statement | Local partial derivatives |
|---|---|---|
| 1 | $v_1 = x_1$ | None |
| 2 | $v_2 = x_2$ | None |
| 3 | $v_3 = v_1 v_2$ | $c_{31} = v_2$, $c_{32} = v_1$ |
| 4 | $v_4 = \sin v_1$ | $c_{41} = \cos v_1$ |
| 5 | $v_5 = v_3 + v_4$ | $c_{53} = c_{54} = 1$ |

With the seed $\dot{\mathbf{x}} = (1, 0)$, forward mode obtains $\dot v_3 = v_2$, $\dot v_4 = \cos v_1$ and $\dot v_5 = v_2 + \cos v_1 = \partial f / \partial x_1$ in one sweep.
$\partial f / \partial x_2$ requires another sweep with the seed $(0, 1)$.
Traversing backward from $\bar v_5 = 1$ in reverse mode gives $\bar v_3 = \bar v_4 = 1$, $\bar v_2 = \bar v_3 v_1 = x_1$ and $\bar v_1 = \bar v_3 v_2 + \bar v_4 \cos v_1 = x_2 + \cos x_1$, obtaining both gradient components in one sweep.

Forward-mode number types (`Dual`, `MultiDual`, `Jet`) carry tangent components while executing the sequence and do not record it.
Reverse mode's `Var` records operations with input-dependent (active) arguments as tape statements and traverses them backward after evaluation.
Some operations, such as adding a constant or `floor`, record no statement even with active arguments.
`dot` (and each component of `gemv_into` and `gemm_into`) is recorded as one statement without expansion into scalar products and sums; `solve_into`, `checkpointed_loop` and `Var::external` are recorded as single call statements.
`cholesky_into` and `qr_into` record factorization algorithms as scalar-operation statements.
See [Reverse mode and tapes](reverse-mode-and-replay/) for recording rules.

## Notation

Chapter notation follows [Numerical notation and terminology](../../reference/).

| Symbol | Meaning | Corresponding API |
|---|---|---|
| $n$, $m$ | Number of input scalars and output scalars | `Linearization::inputs`, `outputs` |
| $\mathbf{x} \in \mathbb{R}^n$, $\mathbf{y} = F(\mathbf{x}) \in \mathbb{R}^m$ | Evaluation point and output primal values | Argument `point`, `Linearization::values` |
| $v_i$, $\varphi_i$, $P(i)$ | The $i$th value, its operation and the set of argument indices | Tape statements |
| $c_{ij}$ | Local partial derivative $\partial\varphi_i / \partial v_j$ | Each operation's rule |
| $\dot v$, $\dot{\mathbf{x}}$ | Tangent component and input tangent vector (seed) | `Dual::derivative`, `MultiDual::gradient` |
| $\bar v$, $\bar{\mathbf{y}}$ | Adjoint and output cotangent vector (seed) | Argument of `Linearization::vjp_into` |
| $\mathbf{J} \in \mathbb{R}^{m \times n}$ | Jacobian $J_{ij} = \partial F_i / \partial x_j$. Rows are outputs, columns are inputs | `jacobian`, `Linearization::jacobian_into` |
| $\mathbf{J}\dot{\mathbf{x}}$, $\mathbf{J}^\mathsf{T}\bar{\mathbf{y}}$ | Jacobian-vector product (JVP), vector-Jacobian product (VJP) | `jvp`, `vjp` |
| $\nabla f$, $\mathbf{H}$ | Gradient and Hessian of a scalar function | `grad`, `hessian` |
| $\mathbf{H}\mathbf{v}$ | Hessian-vector product (HVP) | `hvp`, `Tape::hvp_into` |
| $c_k = \dfrac{1}{k!}\dfrac{d^k}{dt^k} f(\mathbf{x} + t\mathbf{d})\Big\vert_{t=0}$ | Normalized Taylor coefficient | `Jet::coefficients`, `jet` |
| $\varepsilon$ | Dual-number infinitesimal ($\varepsilon^2 = 0$) | `Dual` |
| $N$ | Number of `MultiDual` directions or `Jet` coefficients | `MultiDual<V, N>`, `Jet<V, N>` |
| $W$ | Lane width (number of independent values in one value) | `Lanes<S, W>`, `BatchPlan<W>` |
| $\chi$ | Number of colors in a sparse-matrix coloring | `ColoringSchedule` |
| $C_F$ | Operation count for one evaluation of $F$ | None |
| $\varepsilon_{\mathrm{mach}}$, ulp | Machine epsilon ($2^{-52}$ for `f64`, $2^{-23}$ for `f32`), unit in the last place | `RealScalar::EPSILON` |

The symbol $\varepsilon$ denotes the dual-number infinitesimal; machine epsilon uses a subscript, as in $\varepsilon_{\mathrm{mach}}$ or $\varepsilon_{32}$ (the `f32` value).

## Computational cost model

Computational cost is counted as a multiple of the operation count $C_F$ for one function evaluation and as a number of sweeps.
Both a forward sweep (JVP) and a recording plus reverse sweep (VJP or a scalar-function gradient) cost a small constant multiple of $C_F$, with a constant independent of $n$ and $m$ (Griewank and Walther's complexity model; [Bibliography](../../reference/bibliography/)).
This is why reverse mode is used for gradients of scalar functions with many inputs.
A forward-mode gradient requires one sweep per input direction, $n$ sweeps in total.

The two modes have different memory requirements.
Forward-mode values retain no recording and store only the primal value and tangent components ($N$ with `MultiDual`) per value.
A reverse-mode tape stores `u64` words describing statements (one word for unary and binary statements), an array of partial derivatives and an adjoint per word, so memory grows in proportion to recording length.
See [Loops and checkpointing](checkpointing/) for reducing memory in long loops.

Sweep counts for each required quantity are as follows.

| Required quantity | Main API | Sweep count |
|---|---|---|
| JVP $\mathbf{J}\dot{\mathbf{x}}$ | `Dual`, `jvp`, `Linearization::jvp_into` | 1 forward sweep |
| JVP in $N$ directions, gradient with $N$ inputs | `MultiDual<V, N>` | 1 forward sweep (derivative work is about $N$ times larger) |
| VJP $\mathbf{J}^\mathsf{T}\bar{\mathbf{y}}$, gradient $\nabla f$ | `vjp`, `grad`, `Tape::gradient_into`, `Linearization::vjp_into` | 1 recording and 1 reverse sweep |
| Dense Jacobian $\mathbf{J}$ | `jacobian`, `Linearization::jacobian_into` | 1 recording and $n$ forward or $m$ reverse sweeps (`JacobianMode::Auto` selects reverse when $m < n$) |
| Sparse Jacobian | `Linearization::sparse_jacobian_into` | 1 recording and 1 forward sweep per color ($\chi$ sweeps) |
| HVP $\mathbf{H}\mathbf{v}$ | `hvp`, `Tape::hvp_into` | 1 dual-number recording and 1 reverse sweep (a small constant factor of a gradient) |
| Dense Hessian $\mathbf{H}$ | `hessian` | Recording and reverse sweep per direction ($n$ times) |
| Sparse Hessian | `Tape::sparse_hessian_into` | Recording and reverse sweep per color ($\chi$ times) |
| Taylor coefficients $c_0, \dots, c_{N-1}$ | `Jet`, `jet` | 1 forward sweep ($O(N^2)$ per nonlinear operation) |

The table counts recordings and sweeps.
A transform with insufficient tape capacity executes the function once more to count statements, so function execution counts may exceed recording counts.
For one-shot calls creating a new tape each time, `grad`, `value_and_grad`, `vjp`, `jacobian` and `hvp` execute the function twice, `hessian` executes it $n + 1$ times, and `Tape::sparse_hessian_into` on a new tape executes it $\chi + 1$ times ([Tape lifecycle and reuse](tape-lifecycle/)).

Hessian-vector products use forward-over-reverse differentiation, recording dual numbers `Dual<f64>` on a tape.
Record with inputs $\mathbf{x} + \mathbf{v}\,\varepsilon$ and perform a reverse sweep: the adjoints' value components contain the gradient and their tangent components contain $\mathbf{H}\mathbf{v}$.

### Computational costs arising from the design

The constants in this model depend on the implementation and execution environment.
The following computational costs arise from `scioxide-ad`'s design.

- SIMD instructions used by `Lanes` depend on the build's target features selected at compile time.
  On x86-64, AVX2 requires `-C target-cpu=x86-64-v3` (or `native`); default SSE2 builds are about 1.2–1.7 times slower for code dominated by lane operations.
- Recording large elementwise computations on a scalar tape costs tens of nanoseconds per element.
  Evaluate such computations in batches with `Lanes` or differentiate them in forward mode.
- A Hessian rerecords the function per direction (per color for a sparse Hessian).
- Every number type evaluates with ordinary IEEE arithmetic without range adjustment (scaling); outside the accuracy envelope, intermediate values may overflow or underflow even where a range-aware formula would avoid overflow.

## Contracts shared by all pages

The following contracts apply to all number types and transforms.
Each page assumes these contracts and describes only the rules specific to its subject.

- Values follow IEEE 754 and operation order is fixed.
  Number-type operations do not check arguments or return errors, and propagate NaN and infinity unchanged.
  Failures are returned through `Result` at tape and batch-transform boundaries, in structured operations, in a few methods checking argument lengths or indices, and in `try_map_scalar`, which returns rule errors.
- Values do not depend on the differentiation method.
  Wrapper types compute value components using arithmetic of the next inner type (`Primal`), so function values from `Dual`, `MultiDual` and `Var` agree bit for bit with evaluation of the same function using the inner type (`f64` for `Dual<f64>`).
  `Lanes` results are independent of lane width; only the eight lane kernels (`exp`, `exp_m1`, `ln`, `ln_1p`, `sin`, `cos`, `tanh`, `powf`) and operations using them may differ from scalar results in the last few digits.
- `Dual`, `MultiDual` and `Var` evaluate each function's partial derivatives with `Primal` arithmetic and compose them using the chain rule.
  Nested types differentiate the evaluated expression again.
  Functions switching formulas according to argument range (`atan`, `tanh`, `asinh`, `acosh`, `hypot`, `atan2`) compute both expressions and choose with `select` based on comparisons of base values.
- All updates in tape reverse and forward sweeps use `azmul` (a product returning $+0$ when a factor is exactly 0).
  `Dual` and `MultiDual` use `azmul` for partial derivatives except `×`, scalar multiplication and division, `fract`, and smooth-function families such as `exp`, `sin`, `cos` and `tanh`; `Jet` uses IEEE products throughout.
  Chain-rule sums of products and Taylor-coefficient recurrences perform multiplication and addition separately without replacing them with fused multiply-add (FMA).
  Only the scalar derivative kernels for `sinc` and `sincpi` explicitly use fused multiply-add to compute rounding residuals; these operations return the same values with or without hardware FMA, so results do not depend on FMA availability.
  See [Forward mode and dual numbers](forward-mode/) for the choices and examples where results differ as a consequence.
- Every number type uses the midpoint of the one-sided derivatives at kinks.
  A tape counts active arguments reaching kinks; under `KinkPolicy::Error`, it turns them into `DomainError` at the transform boundary.
  Nonfinite values propagate within number types according to IEEE; `NonFinitePolicy` determines their treatment at transform boundaries ([Handling kinks and nonfinite values](nonsmooth-and-nonfinite-policies/)).
- When a transform fails, the caller's outputs remain unchanged.
  With insufficient tape capacity, a transform grows the tape and executes the function again; the function can run up to twice per transform and must be deterministic.
  Transforms on a tape that has previously recorded the same function do not allocate, except for structured operations requiring workspace and `Var::external` with passive inputs ([Tape lifecycle and reuse](tape-lifecycle/)).

### Accuracy guarantees

The following accuracy is verified by tests.
Each contract concerns a local quantity for one operation or Taylor coefficients; it does not promise correctly rounded derivatives of a composed function as a whole.

- Values preserve scioxide-core elementary-function accuracy.
  Lane kernels stay within 4 ulp of exact values; other lane operations agree bit for bit with scalar functions.
- Unary first partial derivatives are within 64 ulp of high-precision references (4 ulp for `log10` and `tanh` near formula switches or subnormal results; 1 ulp for `log2`, `log10` and `exp2`, which only multiply by constants); first and second derivatives of stable transforms are within 64 ulp.
- Binary first partial derivatives are within 64 ulp, and nested second partial derivatives are within 256 ulp.
  This contract applies at points where arguments, values and partial derivatives are all either 0 or have magnitudes in $[\sqrt{\texttt{MIN\_POSITIVE}}, \sqrt{\texttt{MAX}}]$.
- Through order 8, the absolute error of Taylor coefficient $c_k$ at points subject to the same restrictions is at most $64\,\varepsilon_{\mathrm{mach}}(k + 1)\,g$ plus the smallest positive subnormal number.
  $g$ is the sum of absolute values of all terms in the exact composition.

See [Floating-point arithmetic and conditioning](../../concepts/floating-point-and-conditioning/) for general discussion of rounding, condition numbers and types of accuracy guarantees.

## Summary

Functions evaluate as statement sequences; forward mode propagates tangent vectors in sequence order, while reverse mode propagates adjoints in reverse order.
JVPs and gradients or VJPs each require one sweep costing a small constant multiple of function evaluation; a dense Jacobian requires $n$ forward or $m$ reverse sweeps, and a Hessian requires recording and a reverse sweep per direction.
Choose forward mode for few inputs and reverse mode for scalar-function gradients with many inputs, accounting for reverse-mode memory growing in proportion to statement count.
Values agree bit for bit with evaluation in the inner type regardless of differentiation method; accuracy guarantees are in ulp for local partial derivatives, so estimate composed derivative error from propagation of primal-value rounding.
