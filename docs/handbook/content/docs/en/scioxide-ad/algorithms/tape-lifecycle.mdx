`Tape` is caller-owned recording storage holding one recording at a time.
When differentiating the same function at many points, reusing one tape lets subsequent transforms avoid allocation and execute the function only once.
This page explains tape settings, insufficient-capacity procedures, checking requirements and preallocating, transform reports, error classification and failed outputs, and thread and borrowing rules.
[Reverse mode and tapes](../reverse-mode-and-replay/) covered statement-recording rules and reverse sweeps.
See [Workspaces and reproducibility](../../../concepts/workspaces-and-reproducibility/) for the general procedure for checking and growing workspace capacity.

## Tape settings

`TapeOptions` determines tape-transform behavior and is fixed on the tape with `Tape::new(options)`.
`Tape::default()` is equivalent to `Tape::new(TapeOptions::new())` and creates a tape with the defaults below.
`TapeOptions::new()` and `TapeOptions::default()` return these defaults; change them individually with `with_*` methods.

| Setting | Default | Setter | Determines |
|---|---|---|---|
| Nonfinite policy | `NonFinitePolicy::Propagate` | `with_non_finite_policy` | Whether to propagate nonfinite points and results or reject them with `NonFinite` |
| Kink policy | `KinkPolicy::Midpoint` | `with_kink_policy` | Whether to use the midpoint of one-sided derivatives or return `DomainError` at kinks |
| Jacobian direction | `JacobianMode::Auto` | `with_jacobian_mode` | Sweep direction for `jacobian_into` |
| Byte limit | `None` (unlimited) | `with_byte_limit` | Limit on retained tape bytes `reserved_bytes()` |

`with_byte_limit` takes `Option<usize>`; `None` removes the limit.
Getters with the same names (`non_finite_policy()`, `kink_policy()`, `jacobian_mode()`, `byte_limit()`) return the values; `Tape::options()` returns tape settings.
Tape settings cannot change after creation; create another tape for different settings.
[Handling kinks and nonfinite values](../nonsmooth-and-nonfinite-policies/) covers the policies' mathematical meaning; [Reverse mode and tapes](../reverse-mode-and-replay/) covers Jacobian direction.

## Insufficient capacity and second recordings

A tape stores words, partial-derivative arrays, per-word adjoints, call tables and workspace, and variable storage as ordinary vectors.
Recording writes into existing capacity and does not grow tape storage during the recording.
Statements exceeding capacity are not saved, but word and partial-derivative counts continue.
Before recording, a transform grows input/output variable storage to the input count plus the previous recording's output count (1 for the first recording).
When a recording exceeds capacity, the transform follows these steps.

1. Execute the function once, counting required words, partial derivatives, calls and workspace.
2. Check that the bytes retained after growing each storage area to the counted size fit the byte limit and the word count fits its limit; grow each area to exactly that size.
3. Execute the function again, recording into the expanded storage.

Thus, a function executes up to twice per transform; `TapeReport::recorded_twice` indicates whether it recorded twice.
A new tape without preallocation has no capacity, so its first transform always records twice.
One-shot `grad`, `value_and_grad`, `vjp`, `jacobian` and `hvp` create new tapes on every call, executing the function twice each time; `hessian` records each direction on the same tape and executes $n + 1$ times for $n$ inputs.
The second execution is assumed to record the same statements as the first, so the function must be deterministic.
If the second execution still exceeds expanded capacity, the transform returns `InvalidInput` (argument `function`, reason `Inconsistent`).
If the function returns `Err` during the first execution that exceeds capacity, the error propagates unchanged without executing the function again.
A smaller second recording is not detected; do not pass functions whose recordings depend on changing state such as execution counts, time or a random sequence advancing on each call.

Tapes do not shrink.
Each storage area grows to exactly the maximum size required by prior recordings, and smaller recordings fit without changes.
Consequently, a tape grown several times for different recording sizes retains the same byte count as a new tape recording only the largest of those recordings (verified in the next cell).
Transforms on a tape that has recorded the same function do not allocate.
Exceptions are structured operations allocating workspace (`solve_into`, `cholesky_into`, `qr_into`, `least_squares_into`, `implicit_solution_into`, `checkpointed_loop`), `Var::external` allocating evaluation workspace (on the first recording for differentiated inputs, on every call for passive inputs), and `Linearization::jacobian_into` allocating one matrix of workspace on its first call.

Tape size has two limits.
The `with_byte_limit` limit applies to retained bytes returned by `reserved_bytes()`.
Whenever a tape grows storage (recording storage, variable storage, second-derivative seeds or intermediate `jacobian_into` results), it compares the resulting byte count to the limit; exceeding it returns `ResourceLimit` for quantity `tape_bytes` without growing.
A tape denied growth retains its previous storage, so `reserved_bytes()` after the transform does not exceed the limit.
The exception is when a function pushes more outputs into the output vector than the tape preallocated, causing the vector to grow itself.
Even without a byte limit, word count is limited to $2^{28} = 268{,}435{,}456$ words; exceeding this returns `ResourceLimit` for quantity `tape_words`.
Byte-count overflow in `usize` returns `SizeOverflow`; allocation failure while growing storage returns `AllocationFailure`.
In every case the tape remains valid and usable for the next transform.

## Checking requirements and preallocating

`Tape::requirements()` returns requirements `TapeRequirements` of the last completed recording.
Requirements consist of six counts, readable through accessors with the same names.

| Accessor | Counted quantity |
|---|---|
| `words()` | Words, including constant and input words |
| `partials()` | Partial derivatives stored with value type `V` |
| `scalars()` | Constant partial derivatives stored with scalar `S` |
| `calls()` | Call-table entries |
| `scratch()` | Call-workspace values: the largest input-plus-output count among `Var::external`, `solve_into` and `checkpointed_loop` calls. The tape retains an additional twice this storage for sweeps |
| `variables()` | Variables: the input count plus output count |

`TapeRequirements::new(words, partials, scalars, calls, scratch, variables)` constructs requirements from these six counts.
`Tape::try_reserve(&requirements)` grows each tape storage area to exactly the size satisfying the requirements.
It returns `ResourceLimit` if the resulting byte count exceeds the byte limit or word count exceeds $2^{28}$, and `AllocationFailure` on allocation failure; the tape remains usable after failure.
`Tape::check(&requirements)` does not allocate; it returns `Capacity::Sufficient` if retained capacity suffices and `Capacity::NeedsGrowth` if growth is required.
After a completed recording, `check(&tape.requirements())` returns `Sufficient`.
`check` also returns `ResourceLimit` if growing to the requirements would exceed the byte limit.
`Tape::reserved_bytes()` returns the tape's current retained byte count.

Copy requirements from a tape after recording, or derive them by counting the recording rules.
Growing the tape with `try_reserve` before an allocation-free loop makes the function execute once starting with the first transform.
Requirements include call workspace `scratch()`; even for functions containing `Var::external` or `solve_into`, another tape preallocated from the recorded tape's `requirements()` executes the function once from its first transform.

The cells on this page differentiate the same extended Rosenbrock function as [Reverse mode and tapes](../reverse-mode-and-replay/) using a tape:

$$
f(\mathbf{x}) = \sum_{i=1}^{n-1} \Bigl[100\,(x_{i+1} - x_i^2)^2 + (1 - x_i)^2\Bigr]
$$


The next block's `rosenbrock` writes this $f$ for `R: Real` and is shared by three cells.

```rust
//| id: ad-tape-rosenbrock-model
//| kind: definitions
//| title: "Extended Rosenbrock function"
//| crates: [scioxide-ad]
use scioxide_ad::Real;

/// Extended Rosenbrock function f(x) = Σᵢ [100 (xᵢ₊₁ − xᵢ²)² + (1 − xᵢ)²].
pub(crate) fn rosenbrock<R: Real>(x: &[R]) -> R {
    x.windows(2)
        .map(|w| {
            let a = w[1] - w[0] * w[0];
            let b = -w[0] + 1.0;
            a * a * 100.0 + b * b
        })
        .sum()
}
```

With the default $n = 16$, `check` before the first call returns `NeedsGrowth`; the transform executes the function twice and `recorded_twice()` becomes `true`.
On calls 2–4, `check` returns `Sufficient`, the function executes once, and word count and retained bytes remain at 136 and 3,764 B.
The fifth call's 32-dimensional point requires 280 words, so the tape records twice again and grows to 7,668 B.
Returning to 16 dimensions on the sixth call returns the word count to 136, but retained bytes stay at 7,668 B; the tape does not shrink.
The other tape preallocated with predicted requirements executes the function once from the first transform and retains 3,764 B, matching the first call on the first tape.
In the second table, the six counts in `requirements()` match predictions from the recording rules.

The fifth call's 7,668 B matches the new tape recording only the same 32-dimensional point (last row).
Each growth sets each storage area to exactly the larger of its prior capacity and the counted recording size, leaving no extra storage after regrowth.
Recording the extended Rosenbrock function on the same tape while increasing dimension one at a time from 2 to 16 grows the tape and executes the function twice each time; final retained bytes are 3,764 B, matching a new 16-dimensional tape.
One tape can be reused even when each recording grows, but each increase causes allocation and a second function execution.
To avoid this, call `try_reserve` beforehand with the largest recording's requirements.
A tape preallocated for 16 dimensions never grows during recordings from 2 through 16 dimensions, remaining at 3,764 B.

At $n = 2$, the recording has one term and 10 words; the fifth call has 28 words.
At $n = 100$, the recording has 892 words and the fifth call has 1,792 words; at both dimensions, function execution counts and `check` results follow the default sequence.
Retained bytes depend on `usize` width and `Var` size; the figures above are for Wasm.
On 64-bit native platforms, the default figures are 4,036 B and 8,196 B.

## Transform reports

`Tape::report()` returns the last transform's report `TapeReport`.

- `words()` is the last recording's word count, indicating memory use and the cost of one sweep.
- `reserved_bytes()` is the byte count retained when the transform finished recording.
- `kinks()` counts active arguments at kinks in the last recording, once per operation and lane ([Handling kinks and nonfinite values](../nonsmooth-and-nonfinite-policies/)).
- `recorded_twice()` reports whether the function recorded twice to grow the tape.

If `recorded_twice()` becomes true on a reused tape, that point's recording exceeded capacity and the tape allocated.
Functions whose branches or iteration counts vary by point also have point-dependent recording sizes.
To avoid allocation inside a loop, call `try_reserve` beforehand with the largest recording's requirements.

## Failure classification and outputs

Recordings with `gradient_into` and `linearize` return the following errors.
[Reverse mode and tapes](../reverse-mode-and-replay/) lists errors returned by `Linearization` products.

| Classification `kind()` | Condition | Details available through `view()` |
|---|---|---|
| `DimensionMismatch` | `gradient` length differs from `point` | Expected and actual lengths |
| Function error | Function returned `Err` | Unchanged from the function |
| `NonFinite` | Under `NonFinitePolicy::Error`, a nonfinite point (before recording), or a nonfinite value or derivative (before writing) | Source `Input` or `Output` |
| `DomainError` | Under `KinkPolicy::Error`, an active argument is at a kink | Argument `point`, reason `Undefined` |
| `InvalidInput` | Second execution exceeds expanded capacity, or an operation mixes values from two recordings | Argument `function`, reason `Inconsistent` |
| `ResourceLimit` | Resulting retained bytes exceed the byte limit, or word count exceeds $2^{28}$ | Quantity `tape_bytes` or `tape_words`, requirement (resulting retained bytes or words), limit |
| `SizeOverflow`, `AllocationFailure` | Byte-count overflow or inability to grow storage | Quantity |
| `ExecutionStopped` | Context stopped by cancellation or deadline | Stop reason |

Code mixing values from two recordings normally fails to compile because of `Var`'s lifetime bound.
Transforms also check this at runtime: the mixed operation returns an undifferentiated NaN value and the transform fails with `InvalidInput`.

Failed transforms leave outputs such as `gradient` unchanged.
The tape remains usable after failure, and the next transform records normally.
Transforms (such as `gradient_into` and `linearize`) check stop requests once at the API boundary; reverse and tangent sweeps check with `context.check()` before and after each sweep and every 1,024 traversed words (including argument words in multi-argument and call statements; [Reverse mode and tapes](../reverse-mode-and-replay/)).
A transform stopped at the API boundary does not execute the function.
`Linearization` products (`vjp_into`, `jvp_into`, `jacobian_into`, `sparse_jacobian_into`) also check at the API boundary and before each sweep; even products with fewer than 1,024 words and `jacobian_into` repeating sweeps per row or column observe stop requests before the next sweep.
See [Error classification and detail views](../../../scioxide-core/algorithms/errors-and-diagnostic-views/) for general guidance on reading `kind()` and `view()`.

The next block's `describe` turns a transform or product result into a table row (situation, `kind()`, argument or quantity, reason or source, required amount, limit, retained bytes after the transform, gradient output).
The gradient output is filled with 7 before the transform; if all entries remain 7 afterward, it is labeled “Unchanged”.
Reasons and sources are shown by the variant names returned by `view()`.

```rust
//| id: ad-tape-error-row
//| kind: definitions
//| title: "Turn transform results into table rows"
//| crates: [scioxide-core]
use scioxide_core::{
    DomainReason, ExecutionStopReason, SciOxideError, SciOxideErrorKind, SciOxideErrorView,
    InvalidInputReason, NonFiniteOrigin,
};

/// (Situation, kind(), argument or quantity, reason or source, required [B], limit [B], retained [B], gradient output).
pub(crate) type Row = (
    &'static str,
    &'static str,
    Option<&'static str>,
    Option<&'static str>,
    Option<usize>,
    Option<usize>,
    Option<usize>,
    &'static str,
);

/// Turn a transform or product result into one row. Fill gradient with 7 before the transform.
/// held is the retained tape byte count after the transform, or None when not shown.
pub(crate) fn describe<T>(
    situation: &'static str,
    result: Result<T, SciOxideError>,
    gradient: &[f64],
    held: Option<usize>,
) -> Row {
    let output = if gradient.iter().all(|&g| g == 7.0) {
        "Unchanged"
    } else {
        "Written"
    };
    let Err(error) = result else {
        return (situation, "Ok", None, None, None, None, held, output);
    };
    let kind = match error.kind() {
        SciOxideErrorKind::ResourceLimit => "ResourceLimit",
        SciOxideErrorKind::NonFinite => "NonFinite",
        SciOxideErrorKind::DomainError => "DomainError",
        SciOxideErrorKind::InvalidInput => "InvalidInput",
        SciOxideErrorKind::ExecutionStopped => "ExecutionStopped",
        _ => "Other",
    };
    let (name, reason, required, limit) = match error.view() {
        SciOxideErrorView::ResourceLimit {
            resource,
            required,
            limit,
        } => (Some(resource.as_str()), None, Some(required), Some(limit)),
        SciOxideErrorView::NonFinite { origin, .. } => {
            let origin = match origin {
                NonFiniteOrigin::Input => "Input",
                NonFiniteOrigin::Output => "Output",
                _ => "Other",
            };
            (None, Some(origin), None, None)
        }
        SciOxideErrorView::DomainError {
            argument, reason, ..
        } => {
            let reason = match reason {
                DomainReason::Undefined => "Undefined",
                _ => "Other",
            };
            (Some(argument.as_str()), Some(reason), None, None)
        }
        SciOxideErrorView::InvalidInput {
            argument, reason, ..
        } => {
            let reason = match reason {
                InvalidInputReason::Inconsistent => "Inconsistent",
                _ => "Other",
            };
            (Some(argument.as_str()), Some(reason), None, None)
        }
        SciOxideErrorView::ExecutionStopped { reason } => {
            let reason = match reason {
                ExecutionStopReason::Cancelled => "Cancelled",
                _ => "Other",
            };
            (None, Some(reason), None, None)
        }
        _ => (None, None, None, None),
    };
    (situation, kind, name, reason, required, limit, held, output)
}
```

This is exactly the byte count retained by a successfully recorded tape (the retained amount in the $L = 4{,}096$ B row).
Before recording, the transform grows variable storage to 17 entries for 16 inputs and one output (748 B in Wasm); growth to the size counted during the first recording is then rejected.
Rejected growth leaves storage unchanged, so the tape retains 748 B (1,020 B natively) and the gradient remains 7.
The NaN point is rejected before recording with `NonFinite` and source `Input`.
At $x = 0$, $\sqrt{x}$ has finite value 0 but derivative $+\infty$, so it is rejected before writing with `NonFinite` and source `Output`.
Evaluating $|x|$ at $x = 0$ gives `DomainError` with argument `point` and reason `Undefined`.
At $L = 4{,}096$ B, requirements fit the limit; the first row also writes the gradient and the tape retains 3,764 B.
$L = 3{,}712$ B is only 52 B below 3,764 B, but growth for recording is still rejected.
The limit is compared with the exact retained byte count after growth, so this recording succeeds when $L \ge 3{,}764$ B ($L \ge 4{,}036$ B natively).
At $L = 0$ B, growth of variable storage before recording is rejected; required bytes are 748 B (1,020 B natively) and retained bytes are 0.
To choose a limit, record the same function at the largest point on an unlimited tape and use its `reserved_bytes()` as a guide.

## Threads and borrowing

`Tape` implements `Send` and `Sync` and can move to another thread.
Transforms take `&mut self`, so only one thread can use a tape at a time.
For parallel differentiation, give each thread its own tape and call `try_reserve` with identical requirements if needed.
`Var` is neither `Send` nor `Sync`; the recorded function executes on the thread calling the transform.
The recorder is constructed on the transform's stack; there is no thread-local or global state outside the tape.

The `Linearization<'a, V>` returned by `linearize` mutably borrows the tape.
While a linearization lives, no other transform can use that tape; release it (leave its scope) before recording another function.
Products of one linearization (`vjp_into`, `jvp_into`, `jacobian_into`) also take `&mut self` and use the same recording sequentially.
For parallel gradients of sums or means of many independent items, `BatchPlan` from [Batch evaluation of many items](../batches/) is preferable to splitting tapes manually.

## Summary

`Tape` fixes policies, Jacobian direction and byte limit with `TapeOptions`; settings remain fixed after creation (the byte limit bounds retained bytes `reserved_bytes()`).
Insufficient-capacity recordings are counted, the tape grows and the function runs again; write deterministic functions and expect two executions in a new tape's first transform.
Reuse tapes for differentiation at many points; before allocation-free regions or loops with growing recordings, call `try_reserve` with the largest recording's requirements (from `requirements()` or recording rules).
If `TapeReport::recorded_twice()` becomes true inside a loop, the recording grew and allocation occurred.
Failed transforms leave outputs unchanged and the tape usable; inspect the cause with `kind()` and `view()`, then retry on the same tape.
Give each thread its own tape and finish using `Linearization` before recording the next function.
