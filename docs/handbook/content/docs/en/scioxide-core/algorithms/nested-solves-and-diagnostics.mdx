Iterative methods often call other iterative methods internally.
The caller wants inner function evaluations to consume outer limits without mixing inner and outer iteration counts.
`scioxide-core` starts inner solves as children through `SolveScope`, records shared-resource consumption in all outer solves, and keeps work counts separated by level.
This page covers child construction and accounting rules, `_scoped` contracts, allocation of shared limits to parallel children, and diagnostics when inner limits stop a solve.
It assumes solve state `SolveState`, context `SolveContext`, and epochs from [Solve identity and epochs](oxref:core-solve-identity), and limits `Budget` and `SolveBudgets`, local versus shared limits, and admission operations from [Local and shared solve limits](oxref:core-local-and-shared-budgets).

## Nested solves and accounting

Composite algorithms run child solves inside parent solves, as when Newton's method for nonlinear equations invokes an iterative linear solver at every iteration.
`SolveScope` specifies where a solve starts.
`SolveScope::from(execution)` (from `ExecutionContext`) starts a root solve without a parent, while `SolveScope::from(&mut context)` (from `&mut SolveContext`) starts a child solve.
`scope.run(&mut child_state, identity, allowance, |child| { ... })` starts a new epoch in `child_state` and records work under these rules.

- The child's epoch, accepted state, and local limits (`allowance`) belong to its `SolveState`; they do not advance the parent's accepted state.
- A child inherits the parent's execution context, using the same executor, cancellation, and deadline.
  [Cancellation checks](oxref:core-cancellation-checks) explains adding a deadline only to a child.
- When a child performs a shared-limit operation, its count is also added to every outer solve.
  Before recording, the whole outer chain checks limits and count representability; if any level rejects, no level's recorded counts change.
  Evaluations whose callbacks return errors also count toward outer evaluation totals.
- The parent's `counts()` returns `SolveCounts`, retaining its own work `own()` and descendant work `nested()` without overlap.
  Both are `EvaluationCounts`, containing counts for iterations, proposals, acceptances, rejections, cache lookups, and evaluations by role.
  Child counts, including unshared categories such as iterations and acceptances, are added to `nested()` in every outer solve.
  `total()?` adds both sets of counts with overflow checks.

Inner computations too small to warrant child solves can be counted directly on the `nested()` side through `record_nested_iterations(amount)` and `record_nested_providers(role, amount)`.
Their evaluations still consume shared limits, while their iterations do not count as the solve's own iterations.

### Contracts of `_scoped` functions

Across SciOxide crates, functions ending in `_scoped` take the caller's scope or context as their final argument and execute within it.
For example, scioxide-rootfind's `find_bracket_scoped` takes `impl Into<SolveScope<'_, '_>>` as its final argument, accepting either `ExecutionContext` or `&mut SolveContext`.

- With `&mut SolveContext`, the function runs as a child of the caller's solve.
  It checks the caller's cancellation and deadline, and shared categories such as evaluations also add to the caller's counts.
- With `ExecutionContext`, the function runs as a root solve using that context's executor, cancellation, and deadline.
- The unsuffixed form performs the same computation independently.
  `find_bracket` passes `ExecutionContext::sequential_native()` to `find_bracket_scoped`, so it has neither cancellation nor deadline and contributes nothing to the caller's accounting.

When calling a SciOxide solver from your own iterative method, pass your `&mut SolveContext` to the `_scoped` form.
The unsuffixed form omits inner evaluations from your accounting and does not propagate cancellation inward.

The following cell defines `inner_scoped` as an inner solve in this form, attempting the specified number of iterations and one function evaluation.
It creates a parent with an iteration limit of 1 and an input evaluation limit (1–3), then calls `inner_scoped` once as a child and once as a root solve.
After the child call, the parent itself attempts one iteration and one function evaluation.
The first table shows attempted and admitted operations, the second evaluation limit reports, and the third counts and accounting integrity for the three `SolveState` values ([accounting integrity](#accounting-integrity)).
Check that child iterations do not enter the parent's own iterations, child evaluations consume the parent's evaluation allowance, and a root call leaves parent records unchanged.

### Allocating limits to parallel children

A `SolveScope::run` child mutably borrows its parent for accounting, so only one can run at a time.
In `backend::with_partitioned_solves`, which runs children in parallel per executor partition, children cannot borrow the parent; shared remaining allowances are therefore distributed before execution.
For each shared category, let $R$ be the smallest remaining allowance among the parent and outer solves, and $c$ the child count.
Child index $i$ ($0 \le i < c$) receives the limit

$$
R_i = \lfloor R / c \rfloor + [\, i < R \bmod c \,], \qquad \sum_{i=0}^{c-1} R_i = R
$$

so the first $R \bmod c$ children receive one extra unit each.
Square brackets denote 1 when their enclosed condition holds and 0 otherwise.
If `allowance` has a smaller resource limit than $R_i$, the smaller value limits the child.
A resource unlimited in every outer solve, including the parent, is not divided; the `allowance` limit applies unchanged.
Remaining representable counts in `usize` are distributed by the same formula.
Unused allowances are not transferred to siblings, so each child's limit is independent of execution order or speed.
When all children finish, their records, including those ending in errors, merge into the parent in index order.
Preparation and merging take time proportional to the child count.

### Accounting integrity

`SolveCounts::integrity()` indicates through `AccountingIntegrity` whether records cover all work in the epoch.
Normally this is `Exact`; if a parallel child's record cannot merge, its parent and all outer solves become `Invalid`.
Other children that merge successfully still contribute records; the error reports the smallest index among failed children.
In a `Invalid` epoch, `total()`, checkpoint construction, and further resource admission produce `AccountingInvariant` errors, remaining so until a new epoch starts.
`own()` and `nested()` remain readable for diagnostics but cannot represent total work.

## Nested limits and diagnostics

Configuration uses positive integers `Budget`, while reporting uses `BudgetLimit`, which can also represent zero.
`BudgetLimit::Finite(n)` is a finite limit; when distributing parallel allowances with $R < c$, it becomes zero for children indexed at least $R$.
`BudgetLimit::Unbounded` indicates that no limit is configured.
`BudgetReport::remaining()` returns `None` for `Unbounded`, and `exhausted()` is true only when a finite limit has been reached.

A child context's `budget_report(kind)` reports its own limit and consumption.
For shared resources, `effective_budget_report(kind)` reports the limit with the least remaining allowance among itself and outer solves (the nearest on a tie); for local resources it reports its own limit.
Use the latter method to read how many evaluations the child can still perform.
The `BudgetReport` returned on rejection reports the rejecting limit: if an outer solve rejects a child evaluation, it shows that outer solve's consumption and limit.

If an inner limit stops a solve and prevents the outer solve from continuing, the outer solve returns a `ConvergenceFailure` error containing diagnostics from each level.
`ConvergenceDiagnostics` contains the algorithm, counts, limiting resource report, residual, and last accepted state.
`with_nested(algorithm, inner)` adds inner diagnostics and their descendants as a flat sequence ordered from outer to inner.
Readers obtain reason `ConvergenceReason` and `ConvergenceDiagnosticsView` from the `SciOxideErrorView::ConvergenceFailure` of `error.view()`, then read `NestedLevel` from outer to inner through `nested_levels()`.
Each `NestedLevel` contains algorithm `algorithm()`, counts `counts()`, limiting resource report `budget()`, residual `residual()`, and last accepted state `partial_result()`, allowing a single loop to inspect all levels even with deep nesting.

The following cell considers an inner solve that cannot return partial results.
It attempts three units, each containing one iteration and one function evaluation, converting rejection to an error through `.require()?`.
Inputs are the inner iteration limit (1–4, local to the inner solve) and a shared evaluation limit configured in the parent (1–4).
On receiving an inner error, the outer solve returns `ConvergenceFailure` (reason `NestedSolver`) containing its own counts and the inner diagnostics.
The table shows each level's algorithm, counts, and limiting resource report read from the error's `view()`.
Check that the limiting category and consumption match the values determined by the input limits.
If the inner solve completes three units, no table is emitted; only the outcome is shown.

use scioxide_core::{
    AlgorithmId, Budget, BudgetKind, BudgetLimit, BudgetReport, ConvergenceDiagnostics,
    ConvergenceReason, EvaluationRole, ExecutionContext, SciOxideError, SciOxideErrorView,
    ProblemToken, SolveBudgets, SolveContext, SolveCounts, SolveIdentity, SolveScope,
    SolveState, algorithm_id,
};

const OUTER: AlgorithmId = algorithm_id!("handbook", "outer", 1);
const INNER: AlgorithmId = algorithm_id!("handbook", "inner", 1);
/// Number of units performed by the inner solve (one iteration and one evaluation each).
const UNITS: usize = 3;

/// The inner solve returns no partial results, so require() converts rejection to ConvergenceFailure.
fn inner(child: &mut SolveContext<'_, '_>) -> Result<(), SciOxideError> {
    for _ in 0..UNITS {
        child.record_iteration()?.require()?;
        child
            .invoke_provider(EvaluationRole::Function, || Ok(()))?
            .require()?;
    }
    Ok(())
}

/// The outer solve counts one iteration, calls the inner solve, and attaches each level's diagnostics to the inner ConvergenceFailure.
fn outer(
    parent: &mut SolveContext<'_, '_>,
    child_state: &mut SolveState,
    inner_limit: Budget,
) -> Result<(), SciOxideError> {
    parent.record_iteration()?.require()?;
    let identity = SolveIdentity::new(ProblemToken::new(1), INNER, 0, 0);
    let allowance = SolveBudgets::unbounded().with_limit(BudgetKind::Iteration, inner_limit);
    let result = SolveScope::from(&mut *parent).run(child_state, identity, allowance, inner);
    let Err(error) = result else {
        return Ok(());
    };
    let stopped_by = match error.view() {
        SciOxideErrorView::ConvergenceFailure { diagnostics, .. } => diagnostics.budget(),
        // Propagate errors other than convergence failures unchanged.
        _ => return Err(error),
    };
    // Inner level: counts from the inner SolveState and the resource limit report that stopped it.
    let mut nested = ConvergenceDiagnostics::new().with_counts(child_state.counts());
    if let Some(report) = stopped_by {
        nested = nested.with_budget(report);
    }
    let diagnostics = ConvergenceDiagnostics::new()
        .with_algorithm(OUTER)
        .with_counts(parent.counts())
        .with_nested(INNER, nested);
    Err(SciOxideError::convergence_failure(
        ConvergenceReason::NestedSolver,
        diagnostics,
        "inner solve did not converge",
    ))
}

            reason,

            ..

            };
        let mut rows = vec![row(
            0,
            diagnostics.algorithm(),

            diagnostics.budget(),

            diagnostics
                .nested_levels()
                .enumerate()
                .map(|(index, nested)| {
                    row(
                        index + 1,

                        nested.counts(),
                        nested.budget(),

                }),

            { "key": "0", "label": "Level (0 is outer)", "type": "integer" },
            { "key": "1", "label": "Algorithm algorithm()", "nullText": "None" },
            { "key": "2", "label": "Iterations own [count]", "type": "integer" },
            { "key": "3", "label": "Function evaluations own [count]", "type": "integer" },
            { "key": "4", "label": "Limiting resource kind budget().kind()", "nullText": "None" },
            { "key": "5", "label": "Consumption [count]", "type": "integer", "nullText": "None" },
            { "key": "6", "label": "Limit [count]", "type": "integer", "nullText": "None" }
        ]);

            columns,
            rows,
            metadata = serde_json::json!({ "id": "levels", "title": "Error diagnostic levels" })
        );
        Outcome::failed("An inner limit stopped the solve; the outer solve cannot return a result")

## Summary

Use `SolveScope::from(&mut context)` to start another solve inside your method; when calling a SciOxide solver, pass your `&mut SolveContext` to its `_scoped` form.
Inner evaluations then count toward your solve and outer solves, while inner iterations are limited only by the inner `allowance`.
Read the parent's `counts()` with `own()` and `nested()` separately to determine work at each level.
Read remaining child evaluations through `effective_budget_report` and inspect the `BudgetReport` returned on rejection to identify which level's limit stopped execution.
When returning nested failures, attach inner diagnostics with `with_nested`; recipients read levels from outer to inner through `nested_levels()`.
Do not use records with `integrity()` equal to `Invalid` as total work; start a new epoch.
