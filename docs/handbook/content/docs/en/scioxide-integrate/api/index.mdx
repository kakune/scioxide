`scioxide-integrate` provides one-dimensional fixed and adaptive rules and variable transformations, weighted and oscillatory integrals, sampled-data integration, infinite series summation, multidimensional deterministic quadrature, Monte Carlo methods, and integral parameter sensitivities for `f32` and `f64`.
Integrands may return real, complex, or vector values.
This guide maps tasks to API items and groups all 133 public items into tables by purpose.
This page lists 10 result types and settings shared by all methods; child pages group the 123 method-specific items.
Item-name links point to the version 0.1.0 API reference on docs.rs.

## APIs by task

When only values with default settings are needed, begin with the one-shot functions `scioxide_integrate::integrate`, `integrate_piecewise`, `integrate_fourier`, `integrate_unbounded`, `integrate_box`, `integrate_iterated`, `integrate_monte_carlo`, `trapezoid`, `simpson`, `cumulative_trapezoid`, and `sum_series`.
Task mappings and default methods are summarized in [One-shot functions and configured plans](oxref:integrate-choosing-one-shot).
The following table lists types and functions for choosing methods and settings explicitly.

## Type relationships

One-shot functions create default plans and workspace on each call, execute sequentially, and return answers only on success.
`integrate`, `integrate_piecewise`, `integrate_fourier`, `integrate_unbounded`, `integrate_box`, and `integrate_iterated` return `Integral`, pairing a value with an error estimate.
`integrate_monte_carlo` returns `MonteCarloStatistics`, and `sum_series` returns `SeriesResult`; `trapezoid` and `simpson` return only a value, and `cumulative_trapezoid` only a `Vec` of values.

Plans such as `AdaptiveIntegrator` and `CubaturePlan` are reusable immutable values that validate and retain nodes, geometry, tolerance, limits, and execution policy once at construction.
Pass integrands by value as closures implementing `Fn(S) -> Result<V, SciOxideError>` (one-dimensional) or `Fn(&[S]) -> Result<V, SciOxideError>` (multidimensional).
Pass `&f` to reuse the same closure in successive calls (closure references implement the same trait).
The integrand precedes other arguments such as endpoints or domains.
Value type `V` implements scioxide-core's `AffineValue` (real types, `Complex<S>`, `Vec<V>`, or `[V; N]`); every real component uses the same nodes and weights.
The owned-result API `integrate` and one-shot functions return only `Copy` values (real, complex, and fixed-size arrays), so pass a `Vec` or slice `[V]` output to `integrate_into` for vectors whose length is determined at runtime.
Complex values count as two components, real and imaginary.

Workspace is memory owned by the caller.
Requirements returned by a plan's `workspace_requirements(..)` (`IntegrationRequirements` for many plans) record the real component count and, for multidimensional plans, dimension; `workspace(..)` creates matching workspace.
`integrate_into(f, .., &mut out, &mut workspace, scope)` borrows output and workspace, computes, and returns a report.
For `scope`, pass an execution context such as `ExecutionContext::sequential()` or a solve scope with limits.
The owned-result API `integrate` creates workspace on each call, executes sequentially, and returns `(value, report)`.
The Monte Carlo integrator `MonteCarloIntegrator` retains statistics in workspace and has no owned-result API; series use `sum` and sensitivities use separate `jvp_into` and `vjp_into` APIs.

The `FixedRule` trait represents fixed rules and is implemented by `GaussianRulePlan`, `GaussKronrod`, `ClenshawCurtis`, and `NewtonCotes`.
Rules implementing this trait can also be used as one-dimensional rules in `ProductRule`.
Methods using adaptive bisection accept tolerance and limits through `SubdivisionOptions`; `Romberg` and `DoubleExponentialIntegrator`, which halve the step, use `LevelOptions`.
Options for weighted quadrature, Fourier tails, oscillatory integration, iterated integration, and sensitivities wrap `SubdivisionOptions` and add method-specific values.

## Minimal runnable example

The following cell prepares a two-point Gauss–Legendre plan once and reuses one workspace to compute $\int_{-1}^1 x^2\,dx = 2/3$ and $\int_{-1}^1 x^4\,dx = 2/5$ with `integrate_into`.
The two-point Gauss rule integrates polynomials through degree 3 exactly, so $x^2$ should agree up to rounding, while $x^4$ returns $2/9$ with discrepancy $8/45 \approx 0.178$.
The table shows values, differences from analytic results, evaluation counts, reported error estimates, and termination reasons.
Fixed rules have no error estimate, so that column shows no estimate.

```rust
//| id: integrate-api-gaussian-moment
//| ref: integrate-api-gaussian-moment
//| title: "Degree of exactness and workspace reuse for a two-point Gauss–Legendre rule"
//| run: reactive
//| crates: [scioxide-core, scioxide-integrate]
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"summary","path":"/rows/0/2","range":{"min":0,"max":1e-15}}
//|       - {"artifact":"summary","path":"/rows/1/2","approx":{"value":0.17777777777777778,"rtol":1e-12}}
//|       - {"artifact":"summary","path":"/rows/1/3","equals":2}
//|       - {"artifact":"summary","path":"/rows/1/4","equals":null}
//|       - {"path":"/outputs/1/state","equals":"satisfied"}
use scioxide_core::{ExecutionContext, Interval};
use scioxide_integrate::{FixedRule, GaussianRulePlan};

// 1. Prepare a two-point Gauss–Legendre plan once.
let plan = GaussianRulePlan::gauss_legendre(2).map_err(|e| e.to_string())?;

// 2. Create workspace for one real component once and reuse it for two integrands.
let mut workspace = plan.workspace(1).map_err(|e| e.to_string())?;
let interval = Interval::new(-1.0, 1.0).map_err(|e| e.to_string())?;
let integrands: [(&str, fn(f64) -> f64, f64); 2] = [
    ("x²", |x| x * x, 2.0 / 3.0),
    ("x⁴", |x| x * x * x * x, 2.0 / 5.0),
];
let mut rows = Vec::new();
let mut evaluations = 0;
for (name, f, exact) in integrands {
    // 3. Integrate with output, workspace, and execution context, then read the report.
    let mut value = 0.0_f64;
    let report = plan
        .integrate_into(
            |x: f64| Ok(f(x)),
            interval,
            &mut value,
            &mut workspace,
            ExecutionContext::sequential(),
        )
        .map_err(|e| e.to_string())?;
    evaluations += report.evaluations();
    rows.push((
        name,
        value,
        (value - exact).abs(),
        report.evaluations(),
        report.error_estimate(),
        report.termination().to_string(),
    ));
}
let termination = rows.last().map(|row| row.5.clone()).unwrap_or_default();

let sig15 = serde_json::json!({ "significantDigits": 15 });
let sci3 = serde_json::json!({ "notation": "scientific", "significantDigits": 3 });
let columns = serde_json::json!([
    { "key": "0", "label": "Integrand" },
    { "key": "1", "label": "Integral [-]", "type": "number", "format": sig15 },
    { "key": "2", "label": "Difference from analytic result [-]", "type": "number", "format": sci3 },
    { "key": "3", "label": "Evaluations [-]", "type": "integer" },
    { "key": "4", "label": "Error estimate [-]", "type": "number", "format": sci3, "nullText": "Not estimated" },
    { "key": "5", "label": "Termination reason" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "summary" })
);

// Applying a fixed rule ends with FixedRuleCompleted and makes no accuracy claim.
emit_outcome!(
    Outcome::satisfied("Applied a fixed rule twice")
        .explanation("Success means only that the rule was applied as configured. Assess accuracy from differences against analytic results.")
        .status(termination)
        .diagnostic("Evaluations", evaluations as f64, None)
);
```

For $x^2$, the difference is within rounding error; for $x^4$, it is $8/45$.
Both calls use 2 evaluations, terminate with `FixedRuleCompleted`, and have error estimate `None`.
Success only means the rule was applied as configured; the large error for $x^4$ does not appear in the report.
Assess accuracy by comparing different point counts or using a rule with error estimation, as in [Embedded pairs and global adaptive quadrature](../algorithms/adaptive-quadrature/).
The second call reuses the first call's workspace without new allocation.

## Interpreting results, errors, and termination

The `Integral` returned by one-shot functions contains only value `value()` and error estimate `error_estimate()`.
The error estimate equals the report's `error_estimate()`.
If the report has no estimate, it is zero when domain measure is zero and the scalar's largest finite value for other successful outcomes.
One-shot functions turn unsuccessful termination into errors and do not return estimates stopped by limits.
Error classification matches the right column below, even when stopping after a full-domain estimate is available.

The owned-result API `integrate` returns `(value, IntegrationReport)`; `integrate_into` writes the value to output and returns `IntegrationReport`.
The report's `termination()` is the sole termination reason; `is_success()` equals `termination().is_success()`.
`evaluations()` counts integrand evaluations (including inner evaluations in iterated integration); `subdivisions()` counts bisections.

An `Ok` result always has an estimate covering the full domain.
If evaluation limits, cancellation, or a deadline stop computation after a full-domain estimate is available, that estimate is returned with an unsuccessful termination reason such as `BudgetLimit`, `RefinementLimit`, or `Stagnation`.
Stopping before a full-domain estimate is available returns an error instead of a value and leaves output unchanged.
The classifications are as follows, read through `e.kind()`.

| Stop reason | Error without a full-domain estimate |
|---|---|
| Evaluation, iteration, or other limits (`BudgetLimit`) | `ConvergenceFailure` (`EvaluationLimit`, `IterationLimit`, `ResourceLimit`) |
| Level or term limit (`RefinementLimit`) | `ConvergenceFailure` (`TruncationLimit`) |
| Estimate stagnation (`Stagnation`) | `ConvergenceFailure` (`Stagnation`) |
| Extrapolation indicates divergence (`ProbablyDivergent`) | `ConvergenceFailure` (`Divergence`) |
| No representable evaluation point for the next subdivision (`GeometryFailure`) | `NumericalInstability` (`Breakdown`) |
| Cancellation or deadline (`ExecutionStopped`) | `ExecutionStopped` |

Input errors are returned before evaluation.
Out-of-range options or breakpoints, or requirements for another plan kind, give `InvalidInput`; NaN or infinite endpoints or arguments give `NonFinite` (input origin); mismatched output, vector tolerance, or workspace component counts give `DimensionMismatch`.
An integrand returning NaN or infinity gives `NonFinite` (callback origin); errors returned by the integrand propagate unchanged.
Insufficient workspace gives `DimensionMismatch` or `InvalidInput` depending on the plan, as specified in each plan's table.

`IntegrationTermination::is_success()` is true for `FixedRuleCompleted`, `ToleranceReached`, `HeuristicToleranceReached`, `SampleBudgetCompleted`, and `DegenerateDomain`.
Success means a method finished as configured; it does not bound the true error.
`HeuristicToleranceReached` is the successful termination reason when double-exponential transforms, Fourier tails, `CubaturePlan` in two or more dimensions, or sparse grids converge.
Series `SeriesTermination::is_success()` follows the same principle and is true for `BoundedTailReached`, `ExactEmpty`, and `HeuristicToleranceReached`.
For Levin u and Wynn ε, `HeuristicToleranceReached` stops on agreement of successive accelerated values; it neither proves convergence nor bounds the infinite tail.
The sensitivity `SensitivityReport` has no `is_success()`, so use `report.termination().is_success()`; VEGAS and MISER `TrainingReport::is_success()` is true when training completes.

Read deterministic error estimates from the `IntegrationErrorComponents` returned by `error_components()`.
They separate discretization, roundoff, inner integration, moments, extrapolation, and tail components; unestimated components are `None` and need not be zero.
The total `error_estimate()` (`total()`) is

$$
E = \max(\text{discretization},\ \text{roundoff}) + \text{inner} + \text{moments} + \text{extrapolation} + \text{tail}
$$

and becomes `None` if discretization is unestimated, tail diagnostics exist without a tail magnitude, or the sum overflows.
Every component is an estimate, not an upper bound.
Estimates for Gauss–Kronrod, Simpson, Romberg, and double-exponential transforms include the sample-derived roundoff floor $50\varepsilon\sum_i\lvert w_i f(x_i)\rvert$; sparse-grid surplus estimates have no separate roundoff floor.
Components inferred from observed decay have `ErrorReliability::Heuristic`.
For complex or vector values, reported components are maxima over real components; read per-component breakdowns from workspace `component_errors()`.
Monte Carlo reports have no error estimate; standard errors and confidence intervals are statistical uncertainty returned by workspace `statistics()`.

## Workspace reuse and allocation

Workspace corresponds to one real component count and, for multidimensional plans, one dimension.
`check(&requirements)` returns sufficiency as `Capacity`; differing component counts or dimensions, or insufficient memory, give `Capacity::NeedsGrowth`.
`try_reserve(&requirements)` retains the larger of current and requested capacity, allowing one workspace to serve multiple plans of the same kind.
Requirements for another plan kind give `InvalidInput`, and allocation failure leaves workspace unchanged.
`last_attempt()` returns the most recent call's record (result classification, evaluation count, and report), including failed calls.
`component_errors()` contains per-component error estimates from the most recent call; it is `None` before any call, after an error, or after a call without estimates, such as a zero-width interval.

`integrate_into` with sufficiently sized workspace allocates no memory.
Sampled-data plans use workspace created by their own `workspace`, `cumulative_workspace`, `axis_workspace`, and `cumulative_axis_workspace` and return neither reports nor error estimates.
Series, sensitivities, VEGAS, and MISER use dedicated requirements and report types, listed in child-page tables.
Workspace types and the quantities determining size are listed in [Plans, workspace, and execution contexts](oxref:integrate-plans-and-workspaces).
