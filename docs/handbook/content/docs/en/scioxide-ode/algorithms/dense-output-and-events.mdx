In adaptive methods, local error control changes step size $h_n = t_{n+1} - t_n$ from step to step.
Applications, however, need values at equally spaced times (samples for plots or FFTs) or event times such as ground impact, valve opening, or reaching a critical temperature.

Shortening steps to observation times integrates more finely than error control requires, increasing right-hand-side evaluations.
The crate `scioxide-ode` provides continuous extensions (dense output), representing accepted steps with polynomials, and event detection searching for event-function zeros on those polynomials.
This page covers continuous-extension construction and method-specific orders, output policies and sinks, and event detection, localization, and missed events.
[Solving procedure and contracts](../solve-lifecycle-and-contracts/) explains accepted steps versus attempts and the states and outputs retained after failure.

## Continuous extensions

Represent position within an accepted step $[t_n, t_{n+1}]$ (width $h$) by $\theta = (t - t_n)/h \in [0, 1]$.

### Constructing continuous extensions

A Runge–Kutta continuous extension weights the step's computed slopes $k_1, \dots, k_{s^*}$ (including stages evaluated solely for dense output) by polynomials in $\theta$:

$$
\tilde{y}(t_n + \theta h) = y_n + h \sum_{i=1}^{s^*} b_i(\theta)\, k_i
$$


Weights satisfy $b_i(0) = 0$ ($\tilde{y}(t_n) = y_n$ at the start) and $b_i(1) = b_i$ ($\tilde{y}(t_{n+1}) = y_{n+1}$ at the end).
The continuous-extension order is $p^*$ when interior-value error is $O(h^{p^*+1})$ given an exact step start.

A simple extension without stage slopes is cubic Hermite interpolation from endpoint values and slopes,

$$
\tilde{y}(t_n + \theta h) = (1-\theta)\, y_n + \theta\, y_{n+1} + \theta(\theta - 1)\Bigl[(1 - 2\theta)(y_{n+1} - y_n) + (\theta - 1)\, h f_n + \theta\, h f_{n+1}\Bigr]
$$


with $f_n = f(t_n, y_n)$ and $f_{n+1} = f(t_{n+1}, y_{n+1})$, giving extension order 3.

### Continuous-extension orders by method

| Method | Advancing solution order | Continuous extension | Order $p^*$ | Additional right-hand-side evaluations |
|---|---|---|---|---|
| `DormandPrince5` | 5 | Shampine's fourth-degree polynomial | 4 | None |
| `DormandPrince853` | 8 | Seventh-degree polynomial with three added stages | 7 | Three for steps whose dense output is read |
| `Rkf45`, `Verner65` | 5, 6 | Cubic Hermite interpolation | 3 | Endpoint $f_{n+1}$ (reused as the next first stage) |
| `RadauIia` | 5 | Collocation polynomial (cubic) | 3 | None |
| `RosenbrockW` | 2 or 3 | Cubic Hermite interpolation | 3 | Endpoint $f_{n+1}$ (reused as the derivative at the next step start) |
| `AdamsBashforth`, `AdamsMoulton`, `Bdf` | 1〜5 | History interpolation polynomial | Current order | None |
| `AutoStiff`, `AdamsBdf` | Active method | That of the active method | That of the active method | That of the active method |
| Fixed-step Runge–Kutta, `StormerVerlet`, and `Rattle` | — | None | — | — |

The method `DormandPrince853` evaluates three extra stages only when scheduled output, events, or delay-equation history reads that step's dense output.
The dense output of `Rkf45` and `Verner65` has lower order than the primary solution.
Methods without continuous extensions support neither events nor scheduled output.
Supplying them with events or `OdeOutputSchedule::Times` returns `InvalidInput` (`UnsupportedConfiguration`).
Tabulated orders describe interior-value errors from an exact step start; they do not bound accumulated trajectory error.
Dense-output error combines global error at the step start and continuous-extension error.

// Advance one step of size h and return the dense-output error at θh (endpoint-only output if θ is None) and
// the right-hand-side evaluation count.
fn one_step<M: OdeMethod<f64> + Clone, Sys: OdeSystem<f64>>(
    method: &M,
    system: &Sys,
    h: f64,
    theta: Option<f64>,
) -> Result<(f64, usize), String> {
    let tolerance = ErrorTolerance::scalar(1.0, 1.0, NormSelection::RootMeanSquare)
        .map_err(|e| e.to_string())?;
    let schedule = match theta {
        Some(theta) => OdeOutputSchedule::times(vec![theta * h]),
        None => OdeOutputSchedule::FinalOnly,
    };
    let options = OdeOptions::new()
        .with_error_tolerance(tolerance)
        .with_initial_step(h)
        .with_output_schedule(schedule);
    let problem = OdeProblem::new(system, h);
    let mut workspace = method
        .workspace(&problem, &options)
        .map_err(|e| e.to_string())?;
    let mut state = OdeState::new(0.0, Vector::from_vec(vec![1.0, 0.0]));
    // Record the difference from exact solution (cos t, −sin t) in the sink closure (f64 standard functions).
    let mut error = 0.0;
    let mut sink = |t: f64, y: &[f64]| -> Result<(), SciOxideError> {
        error = (y[0] - t.cos()).abs().max((y[1] + t.sin()).abs());
        Ok(())
    };
    let report = method
        .advance(
            &problem,
            &options,
            &mut state,
            &mut sink,
            &mut workspace,
            ExecutionContext::sequential(),
        )
        .map_err(|e| e.to_string())?;
    if report.accepted_steps() != 1 || report.rejected_steps() != 0 {
        return Err("The step was not accepted in one attempt".to_string());
    }
    Ok((
        error,
        report.counts().provider(EvaluationRole::RightHandSide),
    ))
}

The methods `DormandPrince5` and `RadauIia` need no extra evaluations for dense output.

## Output policies and sinks

Select states sent to the sink through `OdeOutputSchedule` supplied to `OdeOptions::with_output_schedule`.

| `OdeOutputSchedule` | States emitted |
|---|---|
| `FinalOnly` (default) | Only the last accepted state |
| `AcceptedSteps` | Initial state and endpoints of every accepted step |
| `Times { times, initial, final_state }` | Dense output at each time in `times`; also initial and final states if `initial` and `final_state` are true |

The constructor `OdeOutputSchedule::times(times)` creates `Times` excluding initial and final states.
The times `times` must be finite, within the integration interval, and monotone in its direction (duplicates are allowed and emitted unchanged).
The option `Times` requires a method with a continuous extension.
Requested times do not affect step size, so finer output does not change error-controlled steps.

A sink implements `OdeOutputSink` and is supplied as `&mut` to the `sink` argument of `advance`.
The method `emit(time, state)` receives states, `emit_requested(index, time, state)` receives states with requested-time position `index`, and `event(event)` receives events.
By default, `emit_requested` calls `emit`, and `event` discards events.
Three standard sinks are available.

- `()` discards all output.
  For only the terminal state, reading `state` of `advance` suffices.
- A `FnMut(S, &[T]) -> Result<(), SciOxideError>` closure receives states (discarding events).
- `OdeTrajectory` stores all states and events in memory.
  Read through `times()`, `states()`, and `events()`, or extract through `into_parts()`.

Sinks receive a step's output when it is accepted.
Within one step, states arrive first, followed by events in integration order (event-number order for equal times).
Emitted output is not retracted if a later step fails.
Sink errors stop integration and propagate unchanged from `advance`.
With sufficient workspace and nonallocating systems and sinks, `advance` does not allocate during integration.
The sink `OdeTrajectory` allocates for each state and event; to avoid allocation, use a closure writing preallocated arrays or a custom sink.

## Event detection

### Event functions and directions

An event is a zero of a state-dependent scalar event function $g(t, y(t))$.
An event function implements `EventFunction`: `eval` returns $g(t, y)$, `direction` gives the sign-change direction to count (`EventDirection`), and `is_terminal` indicates whether to stop integration.
The constructor `EventFn::new(closure)` builds an event function without total derivatives from closure `Fn(S, &[T]) -> Result<S, SciOxideError>`; `with_direction` and `with_terminal` change direction and terminal behavior (default: both directions, nonterminal).
Supply the event-function array to the problem through `OdeProblem::with_events`.

| `EventDirection` | Changes counted |
|---|---|
| `Rising` | Negative to nonnegative |
| `Falling` | Positive to nonpositive |
| `Either` | Both |

Direction is measured from step start to end, following integration order even backward in time.
An exactly zero sample does not initiate a sign change; the next nonzero sample establishes the sign for subsequent detection.
Initial-time zeros are therefore not events, and restarting at an event time does not count the same event again.

Detected events are supplied to sink `event` as `OdeEvent`.
The value `OdeEvent` holds event-function number `index()`, time `time()`, dense-output state `state()` at that time, occurrence kind `occurrence()` (`EventOccurrence::Rising`, `Falling`, `Tangency`), terminal flag `is_terminal()`, and localization evidence `evidence()`.
The value `state()` borrows integrator memory; retain it after the call by copying through `EventInfo::from_event` (`OdeTrajectory` does this to store `EventInfo`).
The evidence `EventEvidence` is `SampledZero` for an exactly zero sample, `Crossing { bracket, residual }` for a contracted sign-changing bracket, or `Contact { bracket, residual }` for a stationary point considered a contact; `bracket` is the final interval, and `residual` is $|g|$ at that time.
Evidence describes only root finding, not ODE solution accuracy.

A terminal event stops integration at its time, sets state to the corresponding dense output, and returns `OdeTermination::TerminalEvent` and `terminal_event()` (event number) in the report.
With multiple events in one step, emit them through the first terminal event in integration order.
Also emit events simultaneous with it within time tolerance, ordering that group by event number.

### Detection procedure

After each accepted step, check each event as follows.

1. Evaluate $g$ at the step endpoint and compare with the starting value.
   Under `EventSearchPolicy::Endpoints`, without a sign change matching the direction, proceed without reading that step's dense output.
2. Under `Subdivide(n)` and `DerivativeAssisted(n)`, divide the step into $n$ equal intervals, evaluate $g$ from dense output at each point, and check sign changes per subinterval.
3. For a sign-changing subinterval, contract it with TOMS 748 on dense output $\tilde{y}(t)$ and record event time and state.
4. Under `DerivativeAssisted(n)`, also evaluate total derivative $dg/dt$ at each point, locating stationary points in its sign-changing subintervals with the same root finder.
   If $g$ at a stationary point differs in sign from both endpoints, contract each side as two crossings between same-sign endpoints.
   If the sign does not change and $|g|$ is at most the contact tolerance, record a contact (`EventOccurrence::Tangency`, `EventEvidence::Contact`).
   Record contacts only for events with direction `EventDirection::Either`.

Every policy examines finitely many samples, so none can establish that no zeros between samples were missed.

### Root finding on a continuous extension

If $g(t_a)\, g(t_b) < 0$ (or one endpoint is zero) in a step subinterval $[t_a, t_b]$, continuity of $g$ ensures a zero inside.
The integrator `scioxide-ode` finds zeros of the function on the continuous extension,

$$
\psi(t) = g\bigl(t,\, \tilde{y}(t)\bigr)
$$

using Alefeld–Potra–Shi enclosure (Algorithm 748, TOMS 748).
TOMS 748 contracts intervals with inverse cubic interpolation (quadratic Newton interpolation and secant when unavailable) and double-length secant steps; cycles without sufficient contraction use bisection, always maintaining a sign-changing bracket ([Bracketed root-finding methods](../../../scioxide-rootfind/algorithms/bracketing-methods/)).
For smooth $\psi$ it converges with fewer evaluations than bisection, often reducing interval width substantially per iteration.
This evaluates only the polynomial and event function, without reintegrating the differential equation.

Contraction continues until width is within `OdeEventOptions` time tolerance (`localization()`), $\psi$ is exactly zero, or no representable floating-point number remains inside.
Default absolute and relative time tolerances are both $4\varepsilon$ (width at most $4\varepsilon + 4\varepsilon \max(|t_a|, |t_b|)$), with at most 64 iterations per event.
Here $\varepsilon$ is the time type's machine epsilon.
This is independent of integration and contact tolerances and is configurable through `OdeEventOptions::with_localization(tolerance, max_iterations)`.
If the iteration limit is reached before interval tolerance is met, integration stops with a `ConvergenceFailure` error.
Event-time accuracy cannot exceed continuous-extension accuracy, so its error is determined by the larger of the remaining localization width and dense-output error at that time.
Localization evaluations of $g$ also count as event-function evaluations (`EvaluationRole::Event`); report `event_search().evaluations()` counts event-function and total-derivative evaluations across both search and localization.

### Search policies and missed zeros

The default endpoint-only `EventSearchPolicy::Endpoints` misses groups of zeros giving an even number of crossings within one step and contacts where the trajectory touches the event surface and returns ($g(t^*) = 0$, $dg/dt(t^*) = 0$).
The policy `Subdivide(n)` also checks signs at points dividing each step into $n$ equal intervals; `DerivativeAssisted(n)` additionally uses the total derivative

$$
\frac{dg}{dt} = \frac{\partial g}{\partial t} + \nabla_y g \cdot \tilde{y}'(t)
$$

to bracket stationary points from its sign changes and search for double crossings between same-sign endpoints or contacts.
Supply total derivatives through `EventFunction::total_derivative(t, y, slope)`; `slope` receives the continuous extension's time derivative $\tilde{y}'(t)$ without reevaluating the right-hand side.
Selecting `DerivativeAssisted` requires every event function to return `true` from `has_total_derivative()`; otherwise it gives `InvalidInput`.
Since `EventFn` has no total derivative, use a direct implementation of `EventFunction` for `DerivativeAssisted`.
The `EventSearchEvidence` returned by report `event_search()` records the policy used (`policy()`) and evaluation count (`evaluations()`).

The following cell solves $y' = 1$, $y(0) = 0$, with time itself as state and constant step $h$, counting zeros of event function $g = \sin(\omega y + 0.3)$ under three policies.

    ));
    // Step endpoints are identical under every policy.
    nodes = path.times().to_vec();
}

### Detecting sign-preserving contacts

When a trajectory touches the event surface and returns, for example $g(t, y) = (y - a)^2$ is always nonnegative and no samples change sign.
The policy `EventSearchPolicy::DerivativeAssisted` brackets stationary points from sign changes in total derivative $dg/dt = 2(y - a)\, y'$, recording a contact if $|g|$ there is within contact tolerance.
Contact tolerance is supplied through `OdeEventOptions::with_contact_tolerance(tolerance, scale)`, with contact condition $|g| \le \mathrm{atol} + \mathrm{rtol} \cdot \mathrm{scale}$ (defaults $\mathrm{atol} = \mathrm{rtol} = \sqrt{\varepsilon}$, $\mathrm{scale} = 1$).
A contact is estimated with finite tolerance, rather than proof that the trajectory touched the surface.

The following cell solves $y' = 1$, $y(0) = 0$ over $[0, 1]$ in one step and searches for contact time $a$ with `Endpoints` and `DerivativeAssisted(1)`.
The contact tolerance is $|g| \le 10^{-12}$.
The input is contact time $a$; the table shows the difference between detected time and analytical time $a$.

```rust
//| id: ode-derivative-assisted-contact
//| ref: ode-derivative-assisted-contact
//| title: "Find sign-preserving contacts using total derivatives"
//| run: reactive
//| crates: [scioxide-core, scioxide-linalg, scioxide-ode]
//| inputs:
//|   contact_time: {"type":"range","label":"Contact time a [-]","description":"Time when g = (y − a)² touches zero.","min":0.31,"max":0.71,"step":0.1,"value":0.41}
//| cases:
//|   - {"id":"late-contact","label":"a = 0.71","description":"Varying the contact location keeps the time difference of the order of time tolerance.","inputs":{"contact_time":0.71}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"contact","path":"/rows/0/1","equals":0}
//|       - {"artifact":"contact","path":"/rows/1/1","equals":1}
//|       - {"artifact":"contact","path":"/rows/1/3","equals":"Contact"}
//|       - {"artifact":"contact","path":"/rows/1/5","range":{"max":1e-15}}
//|   - case: late-contact
//|     expect:
//|       - {"artifact":"contact","path":"/rows/1/5","range":{"max":1e-15}}
use scioxide_core::{Budget, SciOxideError, ResidualTolerance};
use scioxide_linalg::Vector;
use scioxide_ode::{
    DormandPrince5, EventDirection, EventEvidence, EventFunction, EventSearchPolicy,
    OdeEventOptions, OdeFn, OdeMethod, OdeOptions, OdeProblem, OdeState, OdeTrajectory,
};

// Contact event g = (y − a)² (always nonnegative) and its total derivative 2(y − a) y'.
struct Contact(f64);
impl EventFunction<f64> for Contact {
    fn eval(&self, _: f64, y: &[f64]) -> Result<f64, SciOxideError> {
        Ok((y[0] - self.0).powi(2))
    }
    fn has_total_derivative(&self) -> bool {
        true
    }
    fn total_derivative(&self, _: f64, y: &[f64], slope: &[f64]) -> Result<f64, SciOxideError> {
        Ok(2.0 * (y[0] - self.0) * slope[0])
    }
    fn direction(&self) -> EventDirection {
        EventDirection::Either
    }
    fn is_terminal(&self) -> bool {
        false
    }
}

let sci2 = serde_json::json!({ "notation": "scientific", "significantDigits": 2 });
let digits15 = serde_json::json!({ "significantDigits": 15 });
// Since y' = 1 and y(0) = 0, y = t.
let clock = OdeFn::new(1, |_: f64, _: &[f64], out: &mut [f64]| {
    out[0] = 1.0;
    Ok(())
})
.map_err(|e| e.to_string())?;
let event = Contact(contact_time);
let events: &[&dyn EventFunction<f64>] = &[&event];
let problem = OdeProblem::new(&clock, 1.0).with_events(events);
// Tolerance for |g| to count as contact is 1e-12 (reference scale 1).
let contact = ResidualTolerance::new(1e-12, 0.0).map_err(|e| e.to_string())?;
let policies = [
    ("Endpoints", EventSearchPolicy::Endpoints),
    (
        "DerivativeAssisted(1)",
        EventSearchPolicy::DerivativeAssisted(Budget::ONE),
    ),
];
let method = DormandPrince5::new();
let mut rows = Vec::new();
for (name, policy) in policies {
    let search = OdeEventOptions::new()
        .with_search(policy)
        .with_contact_tolerance(contact, 1.0);
    let options = OdeOptions::new()
        .with_initial_step(1.0)
        .with_event_options(search);
    let mut path = OdeTrajectory::new();
    let mut workspace = method
        .workspace(&problem, &options)
        .map_err(|e| e.to_string())?;
    let mut state = OdeState::new(0.0, Vector::from_vec(vec![0.0]));
    let report = method
        .advance(
            &problem,
            &options,
            &mut state,
            &mut path,
            &mut workspace,
            scioxide_core::ExecutionContext::sequential(),
        )
        .map_err(|e| e.to_string())?;
    if !report.is_success() {
        return Err(format!("Integration terminated early: {:?}", report.termination()));
    }
    let first = path.events().first();
    let (kind, residual) = match first.map(|event| event.evidence()) {
        Some(EventEvidence::Contact { residual, .. }) => ("Contact", Some(residual)),
        Some(EventEvidence::Crossing { residual, .. }) => ("Crossing", Some(residual)),
        Some(EventEvidence::SampledZero) => ("SampledZero", Some(0.0)),
        None => ("Not detected", None),
    };
    let time = first.map(|event| event.time());
    // Independent check: difference from analytical contact time a.
    let error = time.map(|t| (t - contact_time).abs());
    let evaluations = report
        .event_search()
        .ok_or("No search record")?
        .evaluations();
    rows.push((
        name,
        path.events().len(),
        time,
        kind,
        residual,
        error,
        evaluations,
    ));
}
let columns = serde_json::json!([
    { "key": "0", "label": "Search policy" },
    { "key": "1", "label": "Events [count]", "type": "integer" },
    { "key": "2", "label": "Time [-]", "type": "number", "format": digits15, "nullText": "—" },
    { "key": "3", "label": "Evidence" },
    { "key": "4", "label": "|g| [-]", "type": "number", "format": sci2, "nullText": "—" },
    { "key": "5", "label": "|t − a| [-]", "type": "number", "format": sci2, "nullText": "—" },
    { "key": "6", "label": "Event-function evaluations [count]", "type": "integer" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "contact" })
);
```

At the default $a = 0.41$, `Endpoints` finds no events.
Both endpoint $g$ values are positive; only two evaluations occur, one at the end and one initially.
The policy `DerivativeAssisted(1)` records the contact as `Contact`; its time differs from $a$ by $5.6 \times 10^{-17}$, with $|g|$ equal to $3.1 \times 10^{-33}$ and 11 combined event-function and total-derivative evaluations.
The time difference is of the order of default time tolerance $4\varepsilon$ and at most $2.3 \times 10^{-16}$ for every input from $a = 0.31$ to $0.71$.
The solution $y = t$ has exact dense output in this problem, so only localization determines the time difference.
Finite search does not establish that no other events exist.

## Summary

Continuous extensions represent accepted steps with polynomials, supplying arbitrary-time values and event times without reintegration.
Their errors follow method-specific extension orders; the cubic extensions of `Rkf45`, `Verner65`, `RadauIia`, and `RosenbrockW` have lower order than their primary solutions.
The seventh-order extension of `DormandPrince853` adds three evaluations for steps whose dense output is read.
Choose output through `OdeOutputSchedule` and send it to `OdeOutputSink`; requested times do not change step sizes.
TOMS 748 localizes event times on continuous extensions to the default $4\varepsilon$ time tolerance, but accuracy cannot exceed that of the extension.
Default event searches examine only step endpoints; for steps longer than zero spacing or for contacts, choose `Subdivide` or `DerivativeAssisted` and assess possible misses alongside evaluation counts in `EventSearchEvidence`.
