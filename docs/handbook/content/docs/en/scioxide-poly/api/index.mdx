`scioxide-poly` provides floating-point approximate polynomials and basis conversion, orthogonal polynomial families, rational functions and approximate GCDs, partial fractions, resultants and discriminants, root-sensitivity diagnostics, exact-coefficient polynomials, prepared coefficient operations and product trees, sparse multivariate polynomials, and Bernstein representations.
This guide identifies starting APIs and type relationships by purpose and lists all 124 public items in four tables organized by use.
Item-name links point to the version 0.1.0 API reference on docs.rs.

## APIs by purpose

Use `evaluate_batch` for many points | [Polynomial bases and evaluation](bases-and-evaluation/) |
| Values, derivatives, and backward residuals at complex points | `checked_basis_evaluation` | Uses Horner for monomials and recurrences for orthogonal bases, computing through second derivatives together. ## Type relationships

`ApproxPolynomial<C, B>` encodes coefficient scalar type `C` and prepared basis `B` (`MonomialBasis`, `NewtonBasis`, `BarycentricBasis`, `OrthogonalBasis`, `BernsteinBasis`) in its type.
Basis conversion is explicit through `to_*`; there are no implicit conversions.
Approximate polynomials carry `PolynomialApproximationPolicy` (coefficient tolerances and numerical-rank policy); binary operations require matching policies.
Data-only constructors use default policy; `_with_options` forms such as `monomial_with_options` accept another policy.
Policies determine degree and rank decisions without automatically removing coefficients.
`ExactPolynomial<C>` accepts only coefficient types implementing `ExactCoefficient` (`ExactField` for division); approximate and exact operations use separate types and functions.

Memory handling falls into three categories.
Plans such as `PolynomialOperationPlan`, `OrthogonalBasisPlan`, `ApproxPartialFractionPlan`, and `ExactPartialFractionPlan` allocate required tables during preparation, then execute without allocation using caller-owned workspaces (such as `PolynomialWorkspace`).
`SylvesterElimination` and `SylvesterDiscriminant` retain only validated degrees and policies, create fixed-size workspaces with `workspace()`, and compute without allocation inside the caller's scope through `_scoped` forms.
Query workspace requirements with `workspace_requirements`, expand with `try_reserve`, and check sufficiency without allocation with `check`.
The `&mut [C]` passed to `_into` forms such as batch evaluation is caller-owned scratch space that is not expanded; query its required length through `PolynomialScratchRequirements`.
Single-point evaluation takes no scratch space.
`ExactPolynomialProductTree` queries and one-shot functions returning owned polynomials (such as `div_rem` and `compose`) allocate result memory.

Prepared atomic execution takes `ExecutionContext` as the last argument and leaves output unchanged on failure.
No caller identity is passed as an argument.

## Minimal executable example

Ascending-power coefficients $[2, -3, 1]$ represent $p(x) = 2 - 3x + x^2 = (x-1)(x-2)$, with $p'(x) = 2x-3$.
The next cell calls `evaluate_with_derivative` at three points $x=4,\ 2.5,\ 2$, comparing values, derivatives, and conditioning reports with hand calculations.
A second table uses `kind()` to classify errors from evaluating a non-finite point and adding polynomials with different policies.

```rust
//| id: poly-api-horner-derivative
//| ref: poly-api-horner-derivative
//| title: "Reading values, derivatives, diagnostics, and errors"
//| run: reactive
//| crates: [scioxide-core, scioxide-poly]
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"evaluations","path":"/rows/0/1","approx":{"value":6,"atol":1e-12}}
//|       - {"artifact":"evaluations","path":"/rows/0/3","approx":{"value":5,"atol":1e-12}}
//|       - {"artifact":"evaluations","path":"/rows/1/6","approx":{"value":6.661338147750944e-16,"rtol":1e-6}}
//|       - {"artifact":"evaluations","path":"/rows/1/7","approx":{"value":21,"rtol":1e-12}}
//|       - {"artifact":"evaluations","path":"/rows/2/7","equals":null}
//|       - {"artifact":"errors","path":"/rows/0/1","equals":"NonFinite"}
//|       - {"artifact":"errors","path":"/rows/1/1","equals":"InvalidInput"}
use scioxide_core::Tolerance;
use scioxide_poly::{ApproxPolynomial, PolynomialApproximationPolicy};

// p(x) = 2 - 3x + x^2 from ascending-power coefficients [a0, a1, a2]
let polynomial =
    ApproxPolynomial::monomial(vec![2.0_f64, -3.0, 1.0]).map_err(|e| e.to_string())?;
// Also construct derivative polynomial p'(x) = -3 + 2x and compare with the derivative from evaluate_with_derivative.
let derivative = polynomial.derivative().map_err(|e| e.to_string())?;
// Show non-finite estimates (+∞ at a root) as None in the table.
let finite = |value: f64| value.is_finite().then_some(value);
let mut rows = Vec::new();
for x in [4.0, 2.5, 2.0] {
    let evaluation = polynomial
        .evaluate_with_derivative(x)
        .map_err(|e| e.to_string())?;
    let slope = derivative.evaluate(x).map_err(|e| e.to_string())?;
    let report = evaluation.condition();
    // Independent check: manually compute factored form (x - 1)(x - 2) and analytical derivative 2x - 3.
    rows.push((
        x,
        evaluation.value(),
        (x - 1.0) * (x - 2.0),
        evaluation.derivative(),
        slope,
        2.0 * x - 3.0,
        report.backward_error(),
        finite(report.condition_estimate()),
        finite(report.forward_error_estimate()),
    ));
}
let fixed2 = serde_json::json!({ "fractionDigits": 2 });
let sci3 = serde_json::json!({ "notation": "scientific", "significantDigits": 3 });
let columns = serde_json::json!([
    { "key": "0", "label": "Point x [-]", "type": "number", "format": fixed2 },
    { "key": "1", "label": "p(x) [-]", "type": "number", "format": fixed2 },
    { "key": "2", "label": "Hand-computed p(x) [-]", "type": "number", "format": fixed2 },
    { "key": "3", "label": "p'(x) [-]", "type": "number", "format": fixed2 },
    { "key": "4", "label": "p'(x) from derivative() [-]", "type": "number", "format": fixed2 },
    { "key": "5", "label": "Hand-computed p'(x) [-]", "type": "number", "format": fixed2 },
    { "key": "6", "label": "Backward error [-]", "type": "number", "format": sci3 },
    { "key": "7", "label": "Estimated condition number [-]", "type": "number", "format": fixed2, "nullText": "+∞" },
    { "key": "8", "label": "Estimated forward error [-]", "type": "number", "format": sci3, "nullText": "+∞" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "evaluations" })
);
// Failures return SciOxideError; read classification with kind(). Here failures are expected and their classifications are tabulated.
let nonfinite = polynomial
    .evaluate(f64::NAN)
    .map_or_else(|e| format!("{:?}", e.kind()), |_| "Success".to_string());
// Create another polynomial with a policy changing only the default policy's tolerance.
let tolerance = Tolerance::new(1e-12, 1e-12).map_err(|e| e.to_string())?;
let other_policy = PolynomialApproximationPolicy::default().with_tolerance(tolerance);
let other = ApproxPolynomial::monomial_with_options(vec![1.0_f64], other_policy)
    .map_err(|e| e.to_string())?;
let mismatch = polynomial
    .try_add(&other)
    .map_or_else(|e| format!("{:?}", e.kind()), |_| "Success".to_string());
emit_table_with_columns!(
    ["Call", "Error classification"],
    vec![
        ("evaluate(NaN)", nonfinite),
        ("try_add of polynomials with different policies", mismatch),
    ],
    metadata = serde_json::json!({ "id": "errors" })
);
```

Values and derivatives agree with hand calculations using factored form and the analytical derivative.
`evaluate_with_derivative` returns value and derivative in one Horner pass, so no derivative polynomial need be constructed with `derivative` when only its value is required.

The backward-error column is $\gamma_3=3\varepsilon/(1-3\varepsilon)\approx6.66\times10^{-16}$ ($\varepsilon=2^{-52}$ is machine epsilon; 3 is the coefficient count).
This is an indicator from the rounding model, not measured error.
The condition estimate is $\kappa(x)=\max\{1,\ \sum_k|a_k||x|^k/|p(x)|\}$: $30/6=5$ at $x=4$, and $15.75/0.75=21$ at $x=2.5$ near a root.
At root $x=2$, $p(x)=0$, making the relative condition number unbounded; the report returns positive infinity and the table shows `+∞`.
The forward-error estimate is $\gamma_3\kappa$; at $x=2.5$ it is $1.40\times10^{-14}$, 4.2 times that at $x=4$, and is infinite at a root.
Near roots, relative value-error indicators lose meaning; assess candidate-root reliability with the [root diagnostics items](oxref:poly-api-roots-sensitivity).

The error table shows `NonFinite` for evaluation at a non-finite point and `InvalidInput` for adding polynomials with different policies.

## Reading results, errors, and diagnostics

Failures return `SciOxideError`; read classifications through `e.kind()` (`SciOxideErrorKind`) and details through `e.view()`.
Common kinds follow.

| Classification | Main causes |
|---|---|
| `InvalidInput` | Empty coefficients or requests; duplicate nodes; zero divisor; out-of-range degree or index; negative or all-zero fitting weights; operations between polynomials with different policies or monomial orders; undeclared operation shapes; matrices whose eigenvalues are polynomial roots of degree 0 or with zero leading coefficient; noncoprime factors in exact partial fractions; certain shape mismatches (product/composition condition-estimate lengths, tensor Bernstein control-point counts and batch-output lengths, batch-evaluation point shapes) |
| `DimensionMismatch` | Mismatched output, workspace, or scratch lengths or shapes; different variable counts |
| `NonFinite` | NaN or infinity in coefficients, points, or nodes |
| `NumericalInstability` | Unrepresentable results (overflow or underflow); numerically inseparable partial-fraction factors, cancellation failing tolerance, or checked evaluation violating the rounding model (`IllConditioned`); violation of exact-field division-algorithm laws (`Breakdown`) |
| `DomainError` | Invalid orthogonal-family parameters or nonpositive scales; points outside weight-function support; rational evaluation with a zero denominator or one obscured by rounding error |
| `ResourceLimit` | Intermediate sparse-substitution term count exceeds `SparseExpansionLimits` |
| `OutOfBounds` | Out-of-range sparse-polynomial variable axis |
| `SizeOverflow`, `AllocationFailure` | Size-calculation overflow or allocation failure |
| `ConvergenceFailure` | Failure of orthogonal-zero eigenvalue computations or approximate-GCD and fitting SVD convergence; Legendre value recurrence exceeds its computation limit |
| `ExecutionStopped` | Cancellation through `ExecutionContext` |

Even an `Ok` result requires assessing quality through diagnostics.
`PolynomialConditionReport`, `ApproximateGcdReport`, `EliminationReport`, `PartialFractionReport`, `RootConditionReport`, and `RootDiagnostics` all provide estimates and decision evidence, not error upper bounds or root proofs.
The backward error of `PolynomialConditionReport` is the indicator $\gamma_N=N\varepsilon/(1-N\varepsilon)$ for coordinate count $N$; division alone uses reconstruction residuals of the computed quotient and remainder.
Unbounded relative diagnostics return positive infinity.
`PartialFractionReport::reciprocal_condition()` returns `None` when a constant denominator leaves no equations; approximate-GCD reports lack rank and reciprocal condition number for zero inputs.

## Summary

Choose items by purpose in the API tables, making policies explicit for approximation and coefficient types explicit for exact arithmetic.
Basis conversion, products, and interpolation are all explicit; prepared Plans use caller-owned workspaces, and batch scratch lengths are queried through requirements.
Classify errors with `kind()` and read backward error and condition estimates before using even `Ok` results.
