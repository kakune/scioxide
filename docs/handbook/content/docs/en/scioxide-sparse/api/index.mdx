`scioxide-sparse` provides sparse storage and conversion, products, sparse triangular systems, direct factorizations (LU, Cholesky, LDL, QR), preconditioners (Jacobi, incomplete factorization, AMG, Schwarz), ordering and coloring, and graph algorithms.
Matrix values support real and complex `f32`/`f64` scalars.
Graph weights are real, maximum-flow capacities are `u64` integers, and matching and connected components read structure alone.
This guide identifies entry points by purpose and organizes all 135 public items (132 root items and three `backend::hermitian` functions) into purpose-grouped tables.
Item-name links point to the version 0.1.0 API reference on docs.rs.

## Type relationships

For assembly, `SparseBuilder` collects triplets; `finish_coo`, `finish_csr`, and `finish_csc` accept duplicate policy `DuplicatePolicy` and zero policy `ExplicitZeroPolicy` and return canonical matrices.
`CsrMatrix::from_triplets` performs the same process directly with `(Sum, Preserve)` policies.
`CsrMatrix::from_raw` and `CscMatrix::from_raw` validate arrays already in canonical form.
Finalized matrix values can be changed without modifying structure.
`set_value`, `copy_values_from`, and `update_values` of `CooMatrix`, `CsrMatrix`, and `CscMatrix` replace only values after checking new-value finiteness.
Only `CsrMatrix::try_assign_pattern` replaces structure; all new values become zero, and symbolic analysis and factors for the old structure cannot serve the new one.
`BsrMatrix` and `DiaMatrix` are constructed from their own arrays with `from_raw` or converted from other formats with `from_sparse` and provide no value-update methods.
Every format returns borrowed view `SparseView` with `view()` without allocation.

For products, `CsrMatrix`, `CscMatrix`, `BsrMatrix`, `DiaMatrix`, `SparseView`, and `SparseOperator` implement scioxide-core's `LinearOperator`, `AdjointOperator`, and `BlockOperator`.
These trait actions use `Accuracy::Standard`; to select precision, use `SparseOperator` returned by `SparseView::with_accuracy`.
`CooMatrix` does not implement these traits; use it through `view()`.
Sparse matrix products first determine the product structure in `SparseProductPlan`, then compute values.
`CsrMatrix::multiply` performs both stages in one call.

Direct factorizations separate symbolic analysis, numerical factors, and workspace into three types.
Symbolic analysis (such as `SparseLuSymbolic`) reads only structure to determine column order and is immutable after construction.
Cholesky symbolic analysis also determines factor structure from the elimination tree, while LU and LDL numerical pivots determine actual fill.
Numerical `factor` and `factor_scoped` accept symbolic analysis by value; numerical factors such as `SparseLu` own it.
Refactorization `refactor` for another matrix of identical structure uses separately preallocated workspace such as `SparseLuWorkspace`.
All-in-one setup constructors such as `SparseLu::new(&a)` perform symbolic through numerical factorization; one-shot functions `solve` and `least_squares` additionally solve once and return the solution.
Numerical factors are created only after successful factorization.
Triangular, LU, Cholesky, LDL, and incomplete factors implement `LinearOperator`, `AdjointOperator`, and `BlockOperator` as actions of $\mathbf{A}^{-1}$ (an approximate inverse for incomplete factorization).
`SparseQr` does not implement these; solve equations through `SparseQrMinimumNormPlan`.
Factor/preconditioner solves and application, $\mathbf{Q}$ actions of `SparseQr`, and minimum-norm computation use shared workspace `SparseSolveWorkspace`.

For preconditioning, `IdentityPreconditioner`, `JacobiPreconditioner`, `IncompleteFactor`, `AmgCycle`, `AmgPreconditioner`, and `SchwarzPlan` implement scioxide-core's `Preconditioner`.
Factor and preconditioner actions through scioxide-core traits use default options (`Standard`) and do not count iterations in this crate.
The calling iterative solver counts preconditioner calls as preconditioner evaluations.

For graphs, `GraphPlan::new` (matrix values as edge weights) and `GraphPlan::from_pattern` (unit edge weights) construct `GraphPlan`, the API for shortest paths, traversal, components, spanning forests, and Laplacians.
The `LaplacianPlan` returned by `GraphPlan::laplacian` holds the Laplacian as CSR and also implements operator traits.
Maximum flow and assignment have dedicated Plans (`MaxFlowPlan`, `AssignmentPlan`); bipartite matching uses the Plan-free function `maximum_bipartite_matching`.

## Calling forms

An operation has the following forms distinguished by name suffixes.
Definitions and selection are in [calling forms](oxref:sparse-execution-forms).

| Form | Naming | Example |
|---|---|---|
| One-shot function | Free function | `solve(&a, &b)`, `least_squares(&a, &b)`, `shortest_paths(a.view(), 0)` |
| All-in-one setup constructor | `new`, `ilu0`, `ic0` | `SparseLu::new(&a)`, `IncompleteFactor::ilu0(&a)`, `AmgPreconditioner::new(&a)` |
| Standard form | No suffix | `SparseLu::factor(symbolic, a.view())`, `lu.solve(&b)`, `graph.shortest_paths(method)` |
| Options form | `*_with_options` | `a.add_with_options(&b, options)`, `maximum_bipartite_matching_with_options(pattern, options)` |
| Output-buffer API | `*_into` | `lu.solve_into(&b, operation, options, &mut x, &mut workspace, cx)`, `sparse_dense_into(…)` |
| Scoped API | `*_scoped` | `SparseLu::factor_scoped(symbolic, a.view(), options, cx)`, `graph.shortest_paths_scoped(method, options, &mut workspace, cx)` |

Standard forms execute their scoped or output-buffer counterparts with default options (`SparseSolveOptions` or `GraphExecutionOptions`), fresh workspace, and `ExecutionContext::sequential_native()`, returning the same values.
Output-buffer and scoped APIs accept either `ExecutionContext` as a new operation root or `&mut SolveContext` as a child of the calling solver, passed as `SolveScope`.
Traversal, components, and spanning forests have fixed work and accept no context.

## Minimal executable example: duplicate and zero-value policies

The following cell inserts contributions 2 and $c$ at $(0, 0)$ and 7 at $(1, 1)$ of an $2 \times 2$ matrix into `SparseBuilder` in arbitrary order, then finalizes CSR with `finish_csr`.
It compares duplicate policies `DuplicatePolicy::Sum` (sum) and `DuplicatePolicy::Reject` (reject), selecting zero-value policy `ExplicitZeroPolicy` by input.
The table shows finalized stored-entry count `nnz()` and three entries read with `get`.
Rejected rows show error classification `e.kind()` and reason from details `e.view()` instead of a matrix.
Default and case tests check that $a_{00}$ for `Sum` equals hand-computed $2 + c$ and that stored-entry counts follow the policies.

```rust
//| id: sparse-api-duplicate-assembly
//| ref: sparse-api-duplicate-assembly
//| title: "Finalize CSR with duplicate summation/rejection and zero-value policies"
//| run: reactive
//| crates: [scioxide-core, scioxide-sparse]
//| inputs:
//|   second: {"type":"range","label":"Second contribution c at (0, 0) [-]","description":"Add at the same position as the first contribution 2. At c = −2 the sum is exactly zero.","min":-5,"max":5,"step":1,"value":3}
//|   preserve_zeros: {"type":"checkbox","label":"Retain zero-valued entries (ExplicitZeroPolicy::Preserve)","description":"Disabling selects Drop, removing exactly zero entries after duplicate summation.","value":false}
//| cases:
//|   - {"id":"cancelled-drop","label":"c = −2, Drop","description":"Removing the entry with sum 2 + (−2) = 0 leaves one stored entry at (1, 1).","inputs":{"second":-2}}
//|   - {"id":"cancelled-preserve","label":"c = −2, Preserve","description":"Retaining the zero sum as an explicit zero leaves two stored entries.","inputs":{"second":-2,"preserve_zeros":true}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"policies","path":"/rows/0/1","equals":2}
//|       - {"artifact":"policies","path":"/rows/0/2","approx":{"value":5,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/0/3","approx":{"value":0,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/0/4","approx":{"value":7,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/1/1","equals":null}
//|       - {"artifact":"policies","path":"/rows/1/5","equals":"InvalidInput"}
//|       - {"artifact":"policies","path":"/rows/1/6","equals":"Malformed"}
//|   - case: cancelled-drop
//|     expect:
//|       - {"artifact":"policies","path":"/rows/0/1","equals":1}
//|       - {"artifact":"policies","path":"/rows/0/2","approx":{"value":0,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/1/5","equals":"InvalidInput"}
//|   - case: cancelled-preserve
//|     expect:
//|       - {"artifact":"policies","path":"/rows/0/1","equals":2}
//|       - {"artifact":"policies","path":"/rows/0/2","approx":{"value":0,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/1/5","equals":"InvalidInput"}
use scioxide_core::SciOxideErrorView;
use scioxide_sparse::{DuplicatePolicy, ExplicitZeroPolicy, SparseBuilder};

let zeros = if preserve_zeros {
    ExplicitZeroPolicy::Preserve
} else {
    ExplicitZeroPolicy::Drop
};
let mut rows = Vec::new();
for (name, duplicates) in [
    ("Sum", DuplicatePolicy::Sum),
    ("Reject", DuplicatePolicy::Reject),
] {
    // Insert two contributions 2 and c at (0, 0) and 7 at (1, 1) in arbitrary order.
    let mut builder = SparseBuilder::new(2, 2);
    for (i, j, value) in [(0, 0, 2.0_f64), (1, 1, 7.0), (0, 0, second)] {
        builder.push(i, j, value).map_err(|e| e.to_string())?;
    }
    // Specify duplicate and zero-value policies explicitly and finalize directly into CSR.
    match builder.finish_csr(duplicates, zeros) {
        Ok(matrix) => {
            // get returns exact zero even for unstored positions.
            let entry = |i, j| matrix.get(i, j).map_err(|e| e.to_string());
            rows.push((
                name,
                Some(matrix.nnz()),
                Some(entry(0, 0)?),
                Some(entry(0, 1)?),
                Some(entry(1, 1)?),
                None,
                None,
            ));
        }
        // Read rejections with classification e.kind() and details e.view(); propagate other failures unchanged.
        Err(error) => match error.view() {
            SciOxideErrorView::InvalidInput { reason, .. } => rows.push((
                name,
                None,
                None,
                None,
                None,
                Some(format!("{:?}", error.kind())),
                Some(format!("{reason:?}")),
            )),
            _ => return Err(error.to_string()),
        },
    }
}
let fixed1 = serde_json::json!({ "fractionDigits": 1 });
let columns = serde_json::json!([
    { "key": "0", "label": "Duplicate policy" },
    { "key": "1", "label": "Stored entries nnz [count]", "type": "integer", "nullText": "—" },
    { "key": "2", "label": "a₀₀ [-]", "type": "number", "format": fixed1, "nullText": "—" },
    { "key": "3", "label": "a₀₁ [-]", "type": "number", "format": fixed1, "nullText": "—" },
    { "key": "4", "label": "a₁₁ [-]", "type": "number", "format": fixed1, "nullText": "—" },
    { "key": "5", "label": "Error classification e.kind()", "nullText": "—" },
    { "key": "6", "label": "Reason e.view()", "nullText": "—" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "policies" })
);
```

In the `Sum` row at default $c = 3$, there are two stored entries, with $a_{00} = 5$, $a_{01} = 0$, and $a_{11} = 7$.
Summation accumulates contributions exactly and rounds once, independent of insertion order.
$(0, 1)$ is an unstored implicit zero; `get` returns exact zero at that in-bounds position and `OutOfBounds` for out-of-bounds positions.
The `Reject` row has classification `InvalidInput` and reason `Malformed`, and constructs no matrix.
At $c = -2$, the sum at $(0, 0)$ is exactly zero; `Drop` removes it structurally, reducing stored entries to one.
`Preserve` retains that same zero explicitly, leaving two stored entries.
`get(0, 0)` returns zero either way, so only structure differs, affecting factorization fill and graph-edge counts.

## Reading results, errors, and diagnostics

Output-writing operations (output-buffer APIs, `refactor`, and value updates) change output or factors only after all checks and computation finish.
On failure, output and previous successful factors, including permutations and values, remain unchanged.
Workspace contents may change on failure but remain usable for the next call.
However, if `try_reserve` or `reprepare_natural` of `SparseLuWorkspace` fails, call that method again before factorization.
In solve, factorization, and graph workspaces, `last_attempt()` returns `AttemptRecord` recording the last call.
Graph workspace `last_accepted()` returns a result only when the last call succeeded.
Detailed rules and experiments are in [output on failure](oxref:sparse-output-on-error).

Symbolic analysis (such as `SparseLuSymbolic::analyze`), incomplete-factorization analysis, and AMG hierarchy construction require limits such as `SparseLuLimits` on factor entries or workspace bytes.
Entry limits also determine preallocated factor capacity.
For Schwarz, `SchwarzOptions` selects Plan and workspace byte limits.
One-shot functions and constructors, Jacobi, and identity preconditioners take no limits.
`workspace_requirements` of symbolic analysis, factors, and Plans returns requirements before allocation.
Limit excess gives `ResourceLimit`; shape mismatch, insufficient workspace, or workspace preallocated for another analysis gives `DimensionMismatch`; allocation failure gives `AllocationFailure`.
Vector lengths must exactly match mathematical dimensions.
Borrowed workspace may exceed its required length, with the unused suffix unchanged ([limits and workspaces](oxref:sparse-limits-and-workspaces)).

Iteration limits are supplied through `SparseSolveOptions::with_budgets` and `GraphExecutionOptions::with_budgets` as `SolveBudgets`.
Output-buffer and scoped APIs charge usage to that limit and, if the context is a calling solver's `SolveContext`, to its limit too.
Iteration units depend on the algorithm: one per column for LU/QR factorization, per row for Cholesky/LDL, and per right-hand side for solves and preconditioner application.
At the limit, `ConvergenceFailure` (`ConvergenceReason::IterationLimit`) is returned, with usage so far in `e.view()` diagnostics.
Schwarz counts local-solver calls as one evaluation per subdomain; multiplicative Schwarz also counts residual updates as evaluations.
Reaching the evaluation limit gives `ConvergenceFailure` (`EvaluationLimit`).
Algorithm-specific units are listed in [iteration limits and execution contexts](oxref:sparse-iteration-limits).

Input and computational failures use the following classifications.
NaN or infinite input gives `NonFinite`; matrix values are checked on construction and right-hand sides on every call.
A column without a nonzero LU pivot, zero triangular/incomplete pivots, and zero-determinant LDL 2×2 pivots give `Singular`.
LDL accepts 1×1 zero pivots during factorization; solving with those factors gives `Singular`.
Cholesky and LDL reject nonreal diagonals or values lacking exact Hermitian symmetry with `InvalidInput`.
Nonpositive Cholesky pivots, overflow, and underflow of nonzero results give `NumericalInstability`.
Graph Laplacians with negative weights, reachable negative cycles (one-shot `shortest_paths`), and cost matrices without a complete assignment (`minimum_cost_assignment`) give `DomainError`.
Plan `GraphPlan::shortest_paths` and `AssignmentPlan::solve` instead return negative cycles and infeasibility as `PathOutcome::NegativeCycle` and `AssignmentOutcome::Infeasible` values, not errors.
Read classification with `e.kind()` and details with `e.view()`; errors carry no caller identity ([error classification](oxref:sparse-error-kinds)).

`IncompleteDiagnostics`, `AmgDiagnostics`, and `AssignmentResiduals` are observed quantities, not proofs of accuracy or optimality.
`AssignmentPlan::verify` likewise only recomputes optimality-condition residuals in floating point.
By contrast, `FlowView::verify` and `MatchingView::verify` check integer conditions exactly and establish optimality by equality of flow and cut capacity or matching and cover sizes.
Both return `false` when a result fails the conditions.

## Summary

For assembly, pass duplicate and zero-value policies to `finish_csr` and similar entry points, explicitly deciding whether cancellation zeros remain structural.
For one solve, use one-shot forms such as `solve`, `least_squares`, and `SparseLu::new`; for repeated solves with identical structure, prepare symbolic analysis and workspace once and repeat `refactor` and output-buffer APIs.
Supply factor-entry and workspace-byte limits to bounded analyses, checking requirements with `workspace_requirements` before allocation.
Failed operations preserve output and previous factors; read causes with `e.kind()` and `e.view()`, adjust inputs or limits, and retry.
Diagnostic values are observations; only maximum-flow and matching `verify` provide exact optimality checks.
