Maps that rotate and translate an object (rigid transformations) appear in coordinate transfer from robot joints to end effectors, point-cloud coordinate-frame changes, and representations of molecular-superposition results.
Rigid-transformation composition depends on order; inversion must undo both rotation and translation.
When transforming many points, deciding when to allocate result storage is also part of the computational design.
This page explains the mathematics and construction of `RigidTransform` and checks workspace preparation for transforming many points with `apply_batch_into`.

## Definition of a rigid transformation

A three-dimensional rigid transformation combines rotation $R \in \mathrm{SO}(3)$ and translation $t \in \mathbb{R}^3$ into the map:

$$
T(p) = R\,p + t
$$

Rigid transformations form the special Euclidean group $\mathrm{SE}(3)$, preserving pairwise distances and orientation (right- or left-handedness).
Like `Rotation`, `RigidTransform` in `scioxide-spatial` is active, moving points in a fixed coordinate frame.
[Rotation matrices and unit quaternions](oxref:spatial-rotation-quaternion) explains rotation representations and sign conventions.

## Composition and inversion

For $T_1 = (R_1, t_1)$ and $T_2 = (R_2, t_2)$, applying $T_2$ first and $T_1$ afterward gives

$$
(T_1 \circ T_2)(p) = R_1(R_2\,p + t_2) + t_1 = R_1R_2\,p + (R_1 t_2 + t_1)
$$

so their composition is $(R_1R_2,\ R_1t_2 + t_1)$.
The rotational part is the product of rotations; the translational part includes multiplication by the later rotation $R_1$.
Even if rotations commute (for example, about the same axis), the translation parts generally satisfy $R_1t_2 + t_1 \ne R_2t_1 + t_2$, so rigid-transformation composition is noncommutative.

Solving $q = R\,p + t$ for $p$ gives $p = R^\top(q - t)$, so the inverse is:

$$
T^{-1} = (R^\top,\ -R^\top t)
$$

Negating translation alone does not undo it; the inverse rotation is also required.

## Homogeneous coordinates and 4×4 matrices

Appending 1 to point $p$ gives homogeneous coordinates $[p;\,1]$, expressing a rigid transformation as the 4×4 matrix product:

$$
\begin{pmatrix} T(p) \\ 1 \end{pmatrix}
= \begin{pmatrix} R & t \\ 0 & 1 \end{pmatrix}
\begin{pmatrix} p \\ 1 \end{pmatrix}
$$

Composition $T_1 \circ T_2$ corresponds to matrix product $M_1M_2$, and inversion to matrix inverse $\begin{pmatrix} R^\top & -R^\top t \\ 0 & 1 \end{pmatrix}$.
These homogeneous matrices are often used to exchange transformations with other libraries or file formats.

Direction vectors such as point differences $p - p'$ are unaffected by translation, changing only by $R$.
Their homogeneous form is vector $[v;\,0]$ with final component 0.
`RigidTransform` distinguishes points through `apply` and directions through `apply_direction`.

## Constructing and checking RigidTransform

| Function | Behavior |
|---|---|
| `RigidTransform::new(rotation, translation)` | NaN or infinity in translation gives `NonFinite` |
| `RigidTransform::identity()`, `rotation()`, `translation()` | Identity map, rotation $R$, translation $t$ |
| `apply(p)` | Point map $Rp + t$. Rounds each component once from an exact sum of products including translation. NaN or infinity in `p` gives `NonFinite` |
| `apply_direction(v)` | Direction-vector rotation $Rv$ (no translation) |
| `compose(other)` | Map $(R_1, t_1)\circ(R_2, t_2) = (R_1R_2,\ R_1t_2 + t_1)$ applying `other` first |
| `inverse()` | Inverse map $p \mapsto R^\top(p - t)$, namely $(R^\top, -R^\top t)$ |
| `as_matrix()` | Row-major 4×4 homogeneous matrix acting on column vector $[x, y, z, 1]$ |
| `RigidTransform::from_matrix(m, tolerance)` | Accepts only matrices with last row $[0, 0, 0, 1]$ and upper-left 3×3 block passing `Rotation::from_matrix` checks. Scaling, shear, or reflection gives `InvalidInput` |

`apply` constructs rotation-matrix entries with ordinary floating-point arithmetic, then rounds each component $\sum_j R_{ij}p_j + t_i$ of $Rp + t$ once as an exact four-term sum of products ([Error guarantees for checked arithmetic functions](oxref:core-checked-arithmetic)).
Intermediate products and sums do not overflow, so even cancellation between $R_{ij}p_j$ and $t_i$ producing a small result succeeds whenever that result is representable.
Only an unrepresentable result component returns `NumericalInstability`; no memory is allocated.
`apply_direction` is `Rotation::apply`, performing the same computation without translation.
Translation $R_1t_2 + t_1$ of `compose` and translation $-R^\top t$ of `inverse` use the same sum of products as `apply`, returning `NumericalInstability` if unrepresentable.
The rotational part of `compose` uses `Rotation::compose`, renormalizing quaternion products so repeated composition does not let rotations drift from unit length.

`from_matrix` does not project matrices to the nearest rigid transformation.
It compares differences of last-row components from $[0, 0, 0, 1]$, components of upper-left 3×3 $MM^\top - I$, and $\det - 1$ with the `tolerance` threshold $\mathrm{atol} + \mathrm{rtol}\cdot 1$.
For numerically constructed matrices, supply a tolerance matching the rounding scale (for example, `Tolerance::from_sqrt_epsilon()`).

## Batch transformations and workspaces

Use `Rotation::apply_batch_into` and `RigidTransform::apply_batch_into` to apply rotations or rigid transformations to many points.
They accept a three-dimensional `PointSet` and write results to an output array.
`apply_batch(&points)` performs the same transformation sequentially with default settings, allocating workspace and the returned result `Vec<[S; 3]>` on each call.
Results are first written to `TransformWorkspace` and copied to output only after every point succeeds, leaving output unchanged on error.
Prepare workspace in the following order.

1. `TransformOptions::new()` returns sequential-execution settings without a byte limit.
   Change execution policy with `with_execution_policy` and the workspace's retained-byte limit with `with_max_workspace_bytes`.
2. `TransformWorkspaceRequest::apply(count, options)` requests transformations of `count` points, `euler(count, options)` Euler-angle extraction, and `rotations(count, options)` batch evaluation of Slerp and rotation splines; each determines one buffer's size.
3. `TransformWorkspace::workspace_requirements(request)` returns `TransformWorkspaceRequirements`.
   `bytes::<S>()` is the required byte count; exceeding the limit gives `ResourceLimit` and exceeding `usize` gives `SizeOverflow`.
4. `TransformWorkspace::new()` returns an empty workspace without allocating.
   `check(&requirements)` returns `Capacity::Sufficient` or `Capacity::NeedsGrowth`; `try_reserve(&requirements)` allocates the missing capacity.
   `TransformWorkspace::workspace(request)` combines steps 3 and 4.

Batch transformations do not grow the workspace.
Non-three-dimensional points, output length differing from point count, or insufficient workspace return `DimensionMismatch`; total retained capacity exceeding the limit returns `ResourceLimit`.
This total includes capacity retained from previous larger reservations and buffers unused by the current call.
Each point uses the same computation as `apply`; unrepresentable results return `NumericalInstability` and cancellation or deadlines return `ExecutionStopped`.
After one reservation, calls of that size or smaller allocate no memory.
With `ExecutionPolicy::Auto`, at least 256 outputs can trigger parallel execution; cancellation and deadlines are checked every 256 points.

The next cell follows these steps for batch transformation of $n$ points (90° about $z$ and translation $(1, 0, 0)$ m).
Points are $p_i = (i, 0, 0)$ m, borrowed without array cloning through `PointSet::from_points`.
Table `steps` shows capacity status, required bytes, transformed-point count, transformed last point's $y$ coordinate [m], and error classification at each stage.
Workspace reserved for $n$ points can be reused as is to transform $n/2$ points, but is insufficient for $2n$, giving `DimensionMismatch`.
The output array then remains unchanged at its initial value $-1$.
The last row gives requirements with byte limit 1024 B; a requirement of $24n$ B exceeding the limit gives `ResourceLimit`.

```rust
//| id: spatial-transform-workspace
//| ref: spatial-transform-workspace
//| title: "Prepare a batch-transformation workspace by requesting, determining requirements, checking, and reserving"
//| run: reactive
//| crates: [scioxide-core, scioxide-spatial]
//| inputs:
//|   batch: {"type":"range","label":"Points to reserve n","description":"Three f64 values per point use 24 B.","min":2,"max":200,"step":2,"value":100}
//| cases:
//|   - {"id":"small-batch","label":"n = 40","description":"24n = 960 B fits within 1024 B, so the last row succeeds too.","inputs":{"batch":40}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"steps","path":"/rows/0/1","equals":"NeedsGrowth"}
//|       - {"artifact":"steps","path":"/rows/1/1","equals":"Sufficient"}
//|       - {"artifact":"steps","path":"/rows/1/2","equals":2400}
//|       - {"artifact":"steps","path":"/rows/2/4","approx":{"value":99,"atol":1e-12}}
//|       - {"artifact":"steps","path":"/rows/3/3","equals":50}
//|       - {"artifact":"steps","path":"/rows/4/5","equals":"DimensionMismatch"}
//|       - {"artifact":"steps","path":"/rows/4/4","equals":-1}
//|       - {"artifact":"steps","path":"/rows/5/5","equals":"ResourceLimit"}
//|   - case: small-batch
//|     expect:
//|       - {"artifact":"steps","path":"/rows/5/2","equals":960}
use scioxide_core::{ExecutionContext, SciOxideError, RealScalar};
use scioxide_spatial::{
    PointSet, RigidTransform, Rotation, TransformOptions, TransformWorkspace,
    TransformWorkspaceRequest,
};

let n = batch as usize;
let quarter = Rotation::from_axis_angle([0.0, 0.0, 1.0], 0.5 * <f64 as RealScalar>::PI)
    .map_err(|e| e.to_string())?;
let map = RigidTransform::new(quarter, [1.0, 0.0, 0.0]).map_err(|e| e.to_string())?;
// Batch-transform m points p_i = (i, 0, 0), returning the result and the last point's output y.
// Output is prefilled with −1, exposing whether a failure overwrites it.
let run = |m: usize, workspace: &mut TransformWorkspace<f64>| -> Result<_, SciOxideError> {
    let data: Vec<[f64; 3]> = (0..m).map(|i| [i as f64, 0.0, 0.0]).collect();
    let points = PointSet::from_points(&data)?;
    let mut output = vec![[-1.0; 3]; m];
    let result = map.apply_batch_into(
        &points,
        TransformOptions::new(),
        &mut output,
        workspace,
        ExecutionContext::sequential(),
    );
    Ok((result, output[m - 1][1]))
};
let kind = |e: &SciOxideError| Some(format!("{:?}", e.kind()));

let options = TransformOptions::new();
let request = TransformWorkspaceRequest::apply(n, options);
let requirements =
    TransformWorkspace::<f64>::workspace_requirements(request).map_err(|e| e.to_string())?;
let bytes = requirements.bytes::<f64>().map_err(|e| e.to_string())?;
let mut workspace = TransformWorkspace::<f64>::new();
let mut rows: Vec<(
    &str,
    Option<String>,
    Option<usize>,
    Option<usize>,
    Option<f64>,
    Option<String>,
)> = Vec::new();
let before = workspace.check(&requirements).map_err(|e| e.to_string())?;
rows.push((
    "Before reservation",
    Some(format!("{before:?}")),
    Some(bytes),
    None,
    None,
    None,
));
workspace
    .try_reserve(&requirements)
    .map_err(|e| e.to_string())?;
let after = workspace.check(&requirements).map_err(|e| e.to_string())?;
rows.push((
    "After reservation",
    Some(format!("{after:?}")),
    Some(bytes),
    None,
    None,
    None,
));
for (label, m) in [
    ("Transform n points", n),
    ("Transform n/2 points", n / 2),
    ("Transform 2n points", 2 * n),
] {
    let (result, y) = run(m, &mut workspace).map_err(|e| e.to_string())?;
    rows.push(match result {
        Ok(()) => (label, None, None, Some(m), Some(y), None),
        Err(e) => (label, None, None, None, Some(y), kind(&e)),
    });
}
let limited = TransformWorkspaceRequest::apply(n, options.with_max_workspace_bytes(1024));
rows.push(
    match TransformWorkspace::<f64>::workspace_requirements(limited) {
        Ok(r) => {
            let b = r.bytes::<f64>().map_err(|e| e.to_string())?;
            ("Requirements with 1024 B limit", None, Some(b), None, None, None)
        }
        Err(e) => ("Requirements with 1024 B limit", None, None, None, None, kind(&e)),
    },
);
let columns = serde_json::json!([
    { "key": "0", "label": "Stage" },
    { "key": "1", "label": "Capacity status", "nullText": "—" },
    { "key": "2", "label": "Required bytes [B]", "type": "integer", "nullText": "—" },
    { "key": "3", "label": "Transformed-point count", "type": "integer", "nullText": "—" },
    { "key": "4", "label": "Last point's output y [m]", "type": "number", "nullText": "—" },
    { "key": "5", "label": "Error classification", "nullText": "None" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "steps" })
);
```

With default $n = 100$, requirements are $24 \times 100 = 2400$ B; capacity status is `NeedsGrowth` before reservation and `Sufficient` afterward.
Transforming $n$ and $n/2$ points succeeds with the same workspace; last point $(n - 1, 0, 0)$ maps to $(1, n - 1, 0)$, giving table $y$ values 99 and 49.
Transforming $2n$ points fails with `DimensionMismatch`, leaving output $y$ unchanged at −1.
A 1024 B limit disallows 2400 B, giving `ResourceLimit` while determining requirements.
At $n = 40$, requirements are 960 B and fit the limit, so the last row succeeds too.

## Summary

Rigid transformation $p \mapsto Rp + t$ composes as $(R_1R_2,\ R_1t_2 + t_1)$ and inverts as $(R^\top, -R^\top t)$; `RigidTransform::compose` applies its argument first.
Even commuting rotations give noncommuting rigid transformations through translation; check application order algebraically before calling `compose` in computations such as joint chains.
Obtain a 4×4 homogeneous matrix with `as_matrix`; `from_matrix` accepts only matrices passing tolerance checks.
For repeated transformations of many points, derive requirements from `TransformOptions` and `TransformWorkspaceRequest`, reserve workspace once, and call `apply_batch_into`.
Insufficient workspace gives `DimensionMismatch` and exceeded byte limits give `ResourceLimit`, both leaving output unchanged.
