`scioxide-validated` provides outward-rounded interval arithmetic and verification built on it.
The central type [`DecoratedInterval<S>`](https://docs.rs/scioxide-validated/0.1.0/scioxide_validated/struct.DecoratedInterval.html) pairs `ExtendedInterval<S>` (`scioxide-core`), which stores a real set, with [`Decoration`](https://docs.rs/scioxide-validated/0.1.0/scioxide_validated/enum.Decoration.html), which conservatively records domain and continuity; repeated operations never strengthen decorations.
`ElementaryEnclosure` handles elementary functions, and `AffineForm` handles correlation-preserving operations.
To prove a linear system, roots, or an integral once with default settings, use one-shot functions `solve`, `roots`, `polynomial_roots`, and `integrate`.
To verify approximate proposals against the original problem, use verifiers `LinearVerifier`, `ScalarRootVerifier`, `SystemRootVerifier`, and `QuadratureVerifier` and Plan `PolynomialRootPlan`.
One-shot functions return only successfully proved results; verifiers and Plans own execution policies, computation limits, and byte limits as `ValidatedOptions` and return reports of decisions, including inconclusive ones.
Computations using outward rounding return results only after passing rounding-environment checks on x86 (SSE2), x86_64, or AArch64; wasm32 produces errors of `InvalidInput` (`UnsupportedConfiguration`).

## Type structure and invariants: DecoratedInterval and Decoration

Interval results need geometric information about the numerical range and topological or analytic information about whether evaluation involved domain violations or discontinuities.


[`Decoration`](https://docs.rs/scioxide-validated/0.1.0/scioxide_validated/enum.Decoration.html) is a four-level enum ordered from weak to strong:

1. **`Trv` (Trivial)**: Asserts inclusion only.
   Attached to empty sets, computations excluding singularities (division by zero or square roots of negative numbers), partly defined elementary functions, and set-operation results (`hull`, `intersection`, and `restrict`).
2. **`Def` (Defined)**: The evaluated map is consistently defined over the reals throughout the input interval, without proof of continuity.
3. **`Dac` (Defined and continuous)**: The function is defined and continuous throughout the input interval.
   This is the strongest decoration when unbounded intervals are involved.
4. **`Com` (Compact)**: Input and output are both nonempty, bounded closed sets (compact sets), and the map is continuous throughout.
   This expresses the strongest mathematical evidence.

A compound operation's decoration is determined by the minimum input decoration $\min(\text{dec}_1, \text{dec}_2)$, operation-specific restrictions (`Trv` when singularities are excluded), and the cap permitted by the resulting set (`Trv` if empty, `Dac` if unbounded).
Operations never strengthen decorations.
Constructor `with_decoration` pairs a caller-specified set and decoration, rejecting only decorations stronger than the set permits (`Com` on unbounded sets or anything except `Trv` on empty sets) with `InvalidInput` (`Inconsistent`).
The caller is responsible for justifying other decorations; the type does not check them.

## Primary API lookup table

The following table lists mathematical operations, methods, signature outlines, and usage considerations.
Arithmetic and elementary functions returning `Result` round outward and return `InvalidInput` (`UnsupportedConfiguration`) when rounding-environment checks fail.
Construction, membership, set operations, and accessors use no rounding and also run in wasm32.

| Desired operation | Type or method | Signature outline | Essential invariants and behavior |
|---|---|---|---|
| Construct a bounded interval | `DecoratedInterval::new` | `(S, S) -> Result<Self, SciOxideError>` | Finite endpoints with $a \le b$. NaN or infinity gives `NonFinite`; $a > b$ gives `InvalidInput` (`Inconsistent`). Decoration `Com` |
| Construct a singleton interval | `DecoratedInterval::point` | `(S) -> Result<Self, SciOxideError>` | Constructs $[v, v]$ with `Com`. NaN or infinity gives `NonFinite` |
| Construct with a specified decoration | `DecoratedInterval::with_decoration` | `(ExtendedInterval<S>, Decoration) -> Result<Self, SciOxideError>` | Decorations stronger than the set permits give `InvalidInput` (`Inconsistent`). The caller provides justification |
| Construct an empty interval | `DecoratedInterval::empty` | `() -> Self` | Element-free interval $\emptyset$. Always `Trv` |
| Construct the entire real interval | `DecoratedInterval::entire` | `() -> Self` | Entire real line $(-\infty, +\infty)$. Automatically `Dac` |
| Construct a half-infinite interval | `DecoratedInterval::from` | `(ExtendedInterval<S>) -> Self` | Construct from a set with unbounded endpoints specified by `None`, such as `ExtendedInterval::new(Some(a), None)`. Strongest decoration permitted by the set (`Com` if bounded, `Dac` if unbounded, `Trv` if empty) |
| Add two intervals | `add` | `(&self, &Self) -> Result<Self, SciOxideError>` | Outward-rounded $[\operatorname{down}(a+c), \operatorname{up}(b+d)]$ |
| Negate | `neg` | `(&self) -> Result<Self, SciOxideError>` | Exact negation $[-b, -a]$. Preserves Decoration |
| Subtract two intervals | `sub` | `(&self, &Self) -> Result<Self, SciOxideError>` | `add(&other.neg())`. Cancellation of the same variable widens the result |
| Multiply independent variables | `mul` | `(&self, &Self) -> Result<Self, SciOxideError>` | Outward enclosure of four corner products. Apply only to two independent variables |
| Square the same variable | `square` | `(&self) -> Result<Self, SciOxideError>` | Uses identity of the two factors. Lower endpoint 0 when $0 \in X$ |
| Divide intervals | `div` | `(&self, &Self) -> Result<Self, SciOxideError>` | Excludes denominator 0; convex hull of defined quotients. Exclusion gives `Trv` |
| Compute a reciprocal | `reciprocal` | `(&self) -> Result<Self, SciOxideError>` | Equivalent to $[1, 1].\operatorname{div}(self)$ |
| Interval absolute value | `abs` | `(&self) -> Result<Self, SciOxideError>` | If $0 \in X$, lower endpoint 0 and upper endpoint $\max(\lvert a \rvert, \lvert b \rvert)$ |
| Compute a square root | `sqrt` | `(&self) -> Result<Self, SciOxideError>` | Excludes the negative part. $a < 0$ gives `Trv`. Entirely negative inputs give `empty()` |
| Univariate elementary functions | `exp`, `ln`, `sin`, `cos`, `tan`, `atanh`, etc. | `(&self) -> Result<ElementaryEnclosure<S>, SciOxideError>` | Return at most two pieces and `EnclosureStatus`. Out-of-domain inputs are indicated by status rather than error. Internal enclosure-procedure breakdown gives `NumericalInstability` |
| Bivariate elementary functions and powers | `hypot`, `atan2`, `powf`, `log`, `powi` | `(&self, &Self)`; `powi` uses `(&self, i32)`. Return value as above | `atan2` excludes the origin, `log` excludes base 1 and nonpositive values, and `powf` excludes combinations outside the real domain, indicating these by status. Crossing the negative real axis in `atan2` gives two pieces near $-\pi$ and $+\pi$ |
| Test real-point membership | `contains` | `(&self, S) -> bool` | Tests $a \le x \le b$. Empty sets, NaN, and infinity give `false` |
| Test interval inclusion | `contains_interval` | `(&self, &Self) -> bool` | Tests $\text{other} \subseteq \text{self}$. Empty intervals belong to every interval |
| Construct the smallest convex hull | `hull` | `(&self, &Self) -> Self` | Smallest interval containing both inputs. Decoration `Trv` |
| Extract an intersection | `intersection` | `(&self, &Self) -> Self` | Set intersection $X \cap Y$. Decoration `Trv` |
| Restrict to an external domain | `restrict` | `(&self, &ExtendedInterval<S>) -> Self` | Intersection with an a priori physical domain. Decoration `Trv` |
| Retrieve the set representation | `set` | `(&self) -> ExtendedInterval<S>` | Copies internal `ExtendedInterval` by value |
| Retrieve the decoration | `decoration` | `(&self) -> Decoration` | Retrieves the current `Decoration` variant |
| Convert to a bounded interval | `Interval::try_from` | `(DecoratedInterval<S>) -> Result<Interval<S>, SciOxideError>` | Discards decoration and extracts finite endpoints. Empty or unbounded sets give `InvalidInput` (argument `interval`). No allocation |

Enclosure widths depend on the operation.
The four arithmetic operations, reciprocal, square, square root, absolute value, and negation return the narrowest interval formed by outward rounding exact image endpoints to neighboring `f32` or `f64` values.
For point arguments, elementary-function widths are at most two floating-point spacings, checked for 21 univariate functions against correctly rounded references in `f32` and `f64`.
There is no general width bound for elementary functions of interval arguments or compound expressions.

## Minimal executable example and reading results

This minimal cell constructs an interval, tests point membership, and checks the initial decoration.

The example constructs finite closed interval $[1.0, 2.0]$, checks inclusion of interior point $1.5$ and exclusion of exterior point $3.0$, and checks initial decoration `Com`.
Construction and membership are set comparisons without rounding, so they skip rounding-environment checks and run in browser wasm32.
Outputs are true for `inside`, false for `outside`, and `Com` for `decoration`.

```rust
//| id: validated-api-membership
//| ref: validated-api-membership
//| title: "Reading interval sets and initial decorations"
//| run: button
//| crates: [scioxide-validated]
//| tests:
//|   - case: default
//|     expect:
//|       - {"path":"/outputs/0/value/inside","equals":true}
//|       - {"path":"/outputs/0/value/outside","equals":false}
//|       - {"path":"/outputs/0/value/checked_point","equals":1.5}
//|       - {"path":"/outputs/0/value/decoration","equals":"Com"}
use scioxide_validated::DecoratedInterval;

// 1. Construct DecoratedInterval with finite endpoints [1.0, 2.0]
let interval = DecoratedInterval::new(1.0_f64, 2.0).map_err(|e| e.to_string())?;

// 2. Check that real point 1.5 belongs to the interval (true)
let inside = interval.contains(1.5);

// 3. Check that real point 3.0 is outside the interval (false)
let outside = interval.contains(3.0);

// 4. Output membership results and decoration (Com) as JSON
emit_json!(&serde_json::json!({
    "inside": inside,
    "outside": outside,
    "checked_point": 1.5,
    "decoration": format!("{:?}", interval.decoration())
}));
```

## Entry points beyond interval arithmetic

Verification built on interval arithmetic separates proposal construction (candidate certificates) from verification that recomputes bounds from the original problem to check those proposals.
Owning a proposal or certificate storage alone is not proof; only the verification status is the decision.

| Goal | One-shot function | Verifier or Plan and related items | Method | Verification decision |
|---|---|---|---|---|
| Evaluate expressions while preserving correlations | — | `AffineContext` (`AffineOptions`), `AffineForm`, `AffineWorkspace` | Affine arithmetic | `AffineReport` (outward enclosure, domain classification, and whether correlation was lost) |
| Enclose solutions of linear system $Ax=b$ | `solve` (dense point-coefficient matrix) | `LinearVerifier` (interval extensions of system matrix $A$ and approximate inverse $R$), `DenseIntervalOperator`, `SparseIntervalOperator`, `LuIntervalInverse`, `LinearCertificate` | Contraction map preconditioned by an approximate inverse | `LinearVerificationReport::is_verified()` (`status` is `Verified`) |
| Establish univariate root existence, uniqueness, or absence | `roots` (isolates all roots in an interval) | `ScalarRootVerifier`, `ScalarRootCertificate`; isolation uses `RootIsolation` | Interval Newton | `RootVerificationReport::is_proved()`; isolation uses `RootIsolationReport::is_complete()` |
| Establish existence, uniqueness, or absence for nonlinear-system roots | — | `SystemRootVerifier`, `SystemRootCertificate`; isolation uses `RootIsolation` | Krawczyk method | As above |
| Establish polynomial root counts by disk | `polynomial_roots` | `PolynomialRootPlan`, `PolynomialRootCertificate`, `RootDisk`; isolation uses `PolynomialRootCover` | Rouché inclusion test and Pellet test | `PolynomialVerificationReport::is_proved()`; isolation uses `PolynomialIsolationReport::is_complete()` |
| Enclose definite integrals on finite or infinite intervals | `integrate` (finite intervals, twice continuously differentiable functions) | `QuadratureVerifier`, `QuadraturePiece`, `QuadratureAssumption`, `QuadratureCertificate` | Adaptive bisection with interval rectangle rules and remainder bounds for trapezoidal and Gauss–Legendre rules | `QuadratureVerificationStatus::Verified` |

One-shot functions return no decision; they return errors if verification does not succeed.
Proposals may come from any source, such as approximate solutions from `scioxide-linalg` or root estimates from `scioxide-rootfind`.
`verify` recomputes all required bounds from the original problem, so a certificate is meaningful only paired with a successful verification report.
`LinearVerifier::solve` proves solution enclosures, `ScalarRootVerifier::isolate` and `SystemRootVerifier::isolate` prove isolated leaf claims, and `PolynomialRootPlan::isolate` proves per-disk counts before returning them.
`LinearVerifier::propose` adds error bounds around your approximate solution's center and returns a certificate only after a successful proof.
`QuadratureVerifier::generate` only constructs a proposal; pass it to `verify` for proof.

## Proofs with one-shot functions

For one proof with default settings, use one-shot functions `solve`, `roots`, `polynomial_roots`, and `integrate`.
Each internally constructs one verifier or Plan, allocates workspace and output, runs with `ExecutionContext::sequential_native()`, and returns `Ok` only for successfully verified results.
Inconclusive decisions, capacity limits, and intervals that cannot be subdivided return errors instead of reports in `Ok`.

| Function | Problem and defaults | Returned value | When proof fails |
|---|---|---|---|
| `solve(a, b)` | Dense square point-coefficient matrix $A$ and right-hand side $b$. Constructs an approximate inverse from LU and proves nonsingularity and error bounds with $2n + 3$ operator applications. $O(n^3)$ operations and $O(n^2)$ storage | `LinearCertificate` (center and componentwise error radii) | A zero LU pivot gives `Singular` (a floating-point factorization property, not a singularity proof); unproved nonsingularity or bound overflow gives `NumericalInstability` |
| `roots(f, df, lower, upper)` | Isolates all real roots on `[lower, upper]` from interval extension `f` and derivative interval extension `df`. At most 1023 nodes; leaf $[a, b]$ has subdivision threshold $\sqrt{\varepsilon}(1 + \max(\lvert a \rvert, \lvert b \rvert))$ | Ascending, pairwise nonoverlapping `Vec<Interval>`. Exactly one root per interval and no others. An empty vector proves absence of roots | Insufficient node capacity or leaves undecided at the threshold (including multiple roots) give `ConvergenceFailure`. Empty enclosures or unknown continuity give `DomainError` |
| `polynomial_roots(coefficients, approximations)` | Ascending coefficients and approximate roots. Starts a radius-$\sqrt{\varepsilon}\max(\lvert \operatorname{Re} z \rvert, \lvert \operatorname{Im} z \rvert, 1)$ disk at each approximation, doubles radii when the Rouché test is undecided, and merges overlaps | `PolynomialRootCover`. Per-disk root counts, including multiplicity, sum to the degree | Count sum below the degree or inability to expand radii gives `ConvergenceFailure`; the zero polynomial gives `InvalidInput` |
| `integrate(f, d2f, lower, upper)` | Interval extension `f` of a twice continuously differentiable real function and second-derivative extension `d2f`. Adaptive bisection with the trapezoidal rule and remainder $-(h^3/12) f''$, up to 4096 panels. Independently verifies the generated certificate | `Interval` with radius at most $\sqrt{\varepsilon}(1 + \lvert \text{midpoint} \rvert)$. Equal endpoints give $[0, 0]$ | Capacity or resolution limits and noncontracting bounds give `ConvergenceFailure`; empty enclosures or unknown continuity give `DomainError`; an unbounded proof gives `NumericalInstability` |

Callbacks for `roots` and `integrate` are `Fn(DecoratedInterval<S>) -> Result<DecoratedInterval<S>, SciOxideError>` without context arguments.
`roots` returns a root at endpoint $m$ shared by two leaves as $[m, m]$; other intervals are the first leaves establishing uniqueness, and need not be narrower than `upper − lower`.
For a narrow enclosure, call again on a narrow interval around an approximation inside the returned interval.
For interval coefficients, sparse matrices, multiple right-hand sides, infinite intervals, singularities, multicomponent integrals, computation limits, workspace reuse, or proposal verification, use verifiers and `PolynomialRootPlan` ([Verifier configuration and invocation](oxref:validated-api-index-configuration)).

The next two cells each use the four functions once on small problems and compare proved enclosures with uncertified f64 references.
In wasm32, all four return `InvalidInput` (reason `UnsupportedConfiguration`, argument `rounding_environment`).
The two cells share a function recognizing this rejection through the following definition.

```rust
//| id: validated-api-environment
//| kind: definitions
//| title: "Recognizing rounding-environment rejection"
//| crates: [scioxide-core]
use scioxide_core::{SciOxideError, SciOxideErrorView, InvalidInputReason};

/// Return true only for rejection in an environment where outward-rounding assumptions cannot be checked.
pub(crate) fn unsupported(error: &SciOxideError) -> bool {
    matches!(
        error.view(),
        SciOxideErrorView::InvalidInput {
            argument,
            reason: InvalidInputReason::UnsupportedConfiguration,
            ..
        } if argument == scioxide_core::argument!("rounding_environment")
    )
}
```

The first cell uses the three functions that return intervals.
The linear system has $A = \begin{pmatrix} 4 & 1 & 0 \\ 1 & 4 & 1 \\ 0 & 1 & 4 \end{pmatrix}$ and $b = (1, 2, 3)$; Cramer's rule gives exact solution $x = (5/28, 2/7, 19/28)$.
The roots are zeros $(2k + 1)\pi/2$ of $\cos x$ on $[0, b]$, and the integral is $\int_0^1 e^x\,dx = e - 1$.
Combine cosine and exponential enclosures into one interval with `ElementaryEnclosure::hull()`.
Varying input $b$ changes the number of isolated roots.
Reference columns appear everywhere, but enclosure columns are populated only in native environments; wasm32 displays “Not executed” and gives outcome `unavailable`.

```rust
//| id: validated-api-one-shot
//| ref: validated-api-one-shot
//| title: "Prove linear systems, roots, and integrals with one-shot functions"
//| run: button
//| uses: [validated-api-environment]
//| crates: [scioxide-core, scioxide-linalg, scioxide-validated]
//| inputs:
//|   upper: {"type":"range","label":"Right endpoint b of cos x interval [rad]","min":1,"max":20,"step":0.5,"value":10}
//| cases:
//|   - {"id":"wide","label":"b = 20","description":"Zeros (2k + 1)π/2 ≤ 20 give 6 roots for k = 0, …, 5.","inputs":{"upper":20}}
//|   - {"id":"no-root","label":"b = 1.5","description":"Since π/2 ≈ 1.571 > 1.5, there are no zeros; an empty result proves absence of roots.","inputs":{"upper":1.5}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"one-shot-intervals","path":"/rows/0/0","equals":"solve"}
//|       - {"artifact":"one-shot-intervals","path":"/rows/0/4","approx":{"value":0.17857142857142858,"atol":1e-15}}
//|       - {"artifact":"one-shot-intervals","path":"/rows/5/1","equals":"cos x zero 3"}
//|       - {"artifact":"one-shot-intervals","path":"/rows/6/4","approx":{"value":1.718281828459045,"atol":1e-15}}
//|   - case: wide
//|     expect:
//|       - {"artifact":"one-shot-intervals","path":"/rows/8/1","equals":"cos x zero 6"}
//|   - case: no-root
//|     expect:
//|       - {"artifact":"one-shot-intervals","path":"/rows/3/0","equals":"integrate"}
use scioxide_core::{SciOxideError, Interval};
use scioxide_linalg::Matrix;
use scioxide_validated::{DecoratedInterval as D, integrate, roots, solve};
use serde_json::json;

let fixed15 = json!({ "fractionDigits": 15 });
let sci3 = json!({ "notation": "scientific", "significantDigits": 3 });
// 1. References (f64, uncertified): Cramer's-rule fractions, cos zeros (2k + 1)π/2, and e − 1
let half_pi = std::f64::consts::FRAC_PI_2;
let zeros: Vec<f64> = (0..)
    .map(|k| f64::from(2 * k + 1) * half_pi)
    .take_while(|&z| z <= upper)
    .collect();
let mut references = vec![
    ("solve", "x₁".to_string(), 5.0 / 28.0),
    ("solve", "x₂".to_string(), 2.0 / 7.0),
    ("solve", "x₃".to_string(), 19.0 / 28.0),
];
for (k, &z) in zeros.iter().enumerate() {
    references.push(("roots", format!("cos x zero {}", k + 1), z));
}
references.push((
    "integrate",
    "∫₀¹ eˣ dx".to_string(),
    std::f64::consts::E - 1.0,
));
// 2. Three one-shot functions. Each returns Ok only for results with successful verification.
let proof = || -> Result<_, SciOxideError> {
    let a = Matrix::from_vec(3, 3, vec![4.0, 1.0, 0.0, 1.0, 4.0, 1.0, 0.0, 1.0, 4.0])?;
    let mut found = Vec::new();
    for x in solve(&a, &[1.0, 2.0, 3.0])?.enclosure()? {
        found.push(Interval::try_from(x.re)?);
    }
    let cos = |x: D<f64>| -> Result<D<f64>, SciOxideError> { Ok(x.cos()?.hull()) };
    let minus_sin = |x: D<f64>| x.sin()?.hull().neg();
    let zeros = roots(cos, minus_sin, 0.0, upper)?;
    let isolated = zeros.len();
    found.extend(zeros);
    let exp = |x: D<f64>| -> Result<D<f64>, SciOxideError> { Ok(x.exp()?.hull()) };
    found.push(integrate(exp, exp, 0.0, 1.0)?);
    Ok((found, isolated))
};
let proved = match proof() {
    Ok(results) => Some(results),
    Err(error) if unsupported(&error) => None,
    Err(error) => return Err(error.to_string()),
};
// 3. Interval table. If root counts differ from the reference, extra rows have None enclosures.
let found = proved.as_ref().map(|(found, _)| found.as_slice());
let mut contained = found.is_some_and(|found| found.len() == references.len());
let mut rows = Vec::new();
for (index, (call, target, reference)) in references.into_iter().enumerate() {
    let x = found.and_then(|found| found.get(index).copied());
    contained &= x.is_some_and(|x| x.contains(reference));
    let width = x.map(|x| x.upper() - x.lower());
    rows.push((
        call,
        target,
        x.map(|x| x.lower()),
        x.map(|x| x.upper()),
        reference,
        width,
    ));
}
let columns = json!([
    { "key": "0", "label": "Function" },
    { "key": "1", "label": "Object" },
    { "key": "2", "label": "Enclosure lower endpoint", "type": "number", "format": fixed15, "nullText": "Not executed" },
    { "key": "3", "label": "Enclosure upper endpoint", "type": "number", "format": fixed15, "nullText": "Not executed" },
    { "key": "4", "label": "Reference (f64, uncertified)", "type": "number", "format": fixed15 },
    { "key": "5", "label": "Width", "type": "number", "format": sci3, "nullText": "Not executed" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = json!({ "id": "one-shot-intervals" })
);
let outcome = match proved {
    None => Outcome::unavailable("Proof computation not executed in this environment")
        .explanation("Run in an x86, x86_64, or AArch64 native environment."),
    Some((_, isolated)) if contained => Outcome::satisfied(
        "Three functions returned proved enclosures, each containing the reference",
    )
    .diagnostic("Isolated cos x zeros", isolated as f64, None),
    Some(_) => Outcome::failed("Some enclosures exclude references, or root counts differ from the reference"),
};
emit_outcome!(outcome);
```

In an x86_64 native environment, the enclosures for the three linear-system components have widths $5.6 \times 10^{-17}$, $1.1 \times 10^{-16}$, and $2.2 \times 10^{-16}$, and each contains its exact solution component.
With default $b = 10$, the zeros of $\cos x$ are isolated into three intervals $[1.25, 2.5]$, $[3.75, 5]$, and $[7.5, 8.75]$, of width 1.25.
These are the first leaves establishing uniqueness, rather than intervals narrowed around roots.
$b = 20$ returns 6 intervals; $b = 1.5$ returns an empty vector, proving no roots in $[0, 1.5]$.
The integral enclosure has width $7.7 \times 10^{-8}$ and contains $e - 1$, with radius at most the promised $\sqrt{\varepsilon}(1 + \lvert \text{midpoint} \rvert) \approx 4.0 \times 10^{-8}$.

The next cell counts roots of $p(z) = (z - 1)^2(z + 2) = 2 - 3z + z^3$ with `polynomial_roots`.
Approximate roots are $1 + \delta$, $1 - \delta$, and $-2 - \delta$, with offset $\delta$ selected by input.
For each reference root $-2$ (simple) and $1$ (double), the table shows the center and radius of its containing disk and the root count proved in that disk.
Disk membership is an uncertified check using f64 distances.
In wasm32, disk columns display “Not executed” with outcome `unavailable`.

```rust
//| id: validated-api-one-shot-polynomial
//| ref: validated-api-one-shot-polynomial
//| title: "Count polynomial roots by disk with a one-shot function"
//| run: button
//| uses: [validated-api-environment]
//| crates: [scioxide-core, scioxide-validated]
//| inputs:
//|   offset: {"type":"range","label":"Approximation offset δ [-]","min":0.0001,"max":0.5,"step":0.0001,"value":0.0001}
//| cases:
//|   - {"id":"coarse","label":"δ = 0.3","description":"As approximations move away from roots, disk radii double until the Rouché test succeeds, giving radii several times δ.","inputs":{"offset":0.3}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"one-shot-disks","path":"/rows/0/0","equals":-2}
//|       - {"artifact":"one-shot-disks","path":"/rows/1/1","equals":2}
use scioxide_core::{Complex, SciOxideError};
use scioxide_validated::polynomial_roots;
use serde_json::json;

let fixed6 = json!({ "fractionDigits": 6 });
let sci3 = json!({ "notation": "scientific", "significantDigits": 3 });
// Ascending coefficients 2 − 3z + z³ and approximate roots with offset δ
let seeds = [1.0 + offset, 1.0 - offset, -2.0 - offset].map(|x| Complex::new(x, 0.0));
let cover = match polynomial_roots(&[2.0_f64, -3.0, 0.0, 1.0], &seeds) {
    Ok(cover) => Some(cover.view().to_vec()),
    Err(error) if unsupported(&error) => None,
    Err(error) => return Err(error.to_string()),
};
let mut rows = Vec::new();
for (root, multiplicity) in [(-2.0_f64, 1_usize), (1.0, 2)] {
    // Find disks containing reference roots with f64 distances (uncertified check)
    let disk = cover.as_ref().and_then(|cover| {
        cover
            .iter()
            .find(|c| (c.disk.center.re - root).hypot(c.disk.center.im) <= c.disk.radius)
            .copied()
    });
    let center = disk.map(|c| c.disk.center.re);
    rows.push((
        root,
        multiplicity,
        center,
        disk.map(|c| c.disk.radius),
        disk.map(|c| c.count),
    ));
}
let columns = json!([
    { "key": "0", "label": "Reference root (uncertified)", "type": "number" },
    { "key": "1", "label": "Multiplicity", "type": "integer" },
    { "key": "2", "label": "Disk-center real part", "type": "number", "format": fixed6, "nullText": "Not executed" },
    { "key": "3", "label": "Disk radius", "type": "number", "format": sci3, "nullText": "Not executed" },
    { "key": "4", "label": "Root count proved in disk", "type": "integer", "nullText": "Not executed" }
]);
emit_table_with_columns!(columns, rows, metadata = json!({ "id": "one-shot-disks" }));
let outcome = match cover {
    None => Outcome::unavailable("Proof computation not executed in this environment")
        .explanation("Run in an x86, x86_64, or AArch64 native environment."),
    Some(cover) => Outcome::satisfied("Proved a covering whose per-disk root counts sum to degree 3")
        .diagnostic("Disk count", cover.len() as f64, None),
};
emit_outcome!(outcome);
```

In an x86_64 native environment with default $\delta = 10^{-4}$, the two disks near $1 \pm \delta$ merge; a disk centered at $1.0001$ with radius $3.2 \times 10^{-4}$ is proved to contain 2 roots, and one centered at $-2.0001$ with radius $1.2 \times 10^{-4}$ contains 1 root.
At $\delta = 0.3$, the two radii widen to 1.1 and 0.575, but counts remain unchanged.
Disks certify regions containing roots; their radii depend on approximation offsets.

## Verifier configuration and invocation

The four verifiers and `PolynomialRootPlan` are immutable, accepting and owning `ValidatedOptions` at construction.
A verifier only pairs a problem with settings; it does not prepare reusable numerical data.
Only `PolynomialRootPlan` scales and stores coefficients by a power of 2 at construction, taking $O(d)$ operations and storage for degree $d$.
`ValidatedOptions::new()` uses sequential execution with no computation or byte limits; these three settings can be changed.

- Execution policy (`with_execution_policy`) partitions independent batch proofs across executor workers into at most 64 partitions.
  Single proofs always run sequentially; results depend on neither policy nor worker count.
- Computation limits (`with_budgets`) locally bound evaluations and iterations available in each call's epoch.
  In batches, limits remaining after shared preparation are allocated deterministically among proofs.
  Reaching a computation limit returns an inconclusive decision rather than an error.
- Byte limits (`with_byte_limit`) cap retained workspace capacity and prepared storage such as `LuIntervalInverse`.
  Exceeding them produces an error of `ResourceLimit`.

Each operation has one form that allocates its own workspace and output and another accepting caller-provided workspace and scope.
The former (such as `verify`, `solve`, `propose`, `generate`, and `isolate`) allocates required storage itself and runs with `ExecutionContext::sequential_native()`.
The latter is either a `_scoped` form such as `verify_scoped(…, workspace, scope)` returning only a report, or a `_into` form such as `solve_into(…, out, workspace, scope)` also writing output; scope is the last argument.
Passing `ExecutionContext` as scope starts a new epoch; `&mut SolveContext` creates a child epoch of the caller's solve.
Callers do not create solve identities.
Calls rejected by preliminary checks and calls returning errors leave every output unchanged.
Linear-system output changes only when the report is `Verified`.
Isolation writes the tree or disks reached so far even on stopped calls returning `Ok`; quadrature generation writes only when a full-domain proposal is available.

Batch forms (`verify_batch_into`, `solve_block_into`) accept one report entry per proof.
Initialize entries with `LinearVerificationReport::not_run()`, `RootVerificationReport::not_run()`, or `PolynomialVerificationReport::not_run()`; status `NotRun` means the entry's proof has not run yet.
If batch quadrature verification stops for cancellation or a deadline, every status becomes `Inconclusive(Stopped(_))`, including completed verifications.

## Workspace requirements

The three workspaces, `LinearWorkspace`, `RootWorkspace`, and `QuadratureWorkspace`, follow the same preparation steps.

1. Verifier and Plan `workspace_requirements` return requirements (`LinearRequirements`, `RootRequirements`, and `QuadratureRequirements`).
   Linear systems take the number of right-hand-side columns; roots and quadrature take `ProofRequest`.
2. `ProofRequest::proofs(k)` covers single verification and batches of up to k proofs.
   `ProofRequest::refinement(c)` covers one isolation, covering, or generation with c output nodes, disks, or panels, and its replay.
3. Reserve with workspace `try_reserve` and use `check` to check for `Capacity::Sufficient` or `Capacity::NeedsGrowth`.
   Verifier and Plan `workspace(…)` combine requirement computation and reservation.
4. Insufficient workspace capacity grows before callbacks are called.
   Once workspace requirements are met, subsequent calls do not allocate.
5. `last_attempt` returns the last call's epoch, result (`Succeeded`, `Stopped`, `Failed`, or `PreflightRejected`), and work counts.

Requirement `required_bytes` gives allocation for a new workspace, while `check` compares the byte limit against a reused workspace including capacity retained for other verifiers.
One workspace can serve multiple verifiers, retaining the largest reserved capacity.
A requirement exceeding the byte limit gives `ResourceLimit`, failed growth gives `AllocationFailure`, and short borrowed output gives `DimensionMismatch`.

## Providing interval extensions and preserving correlations

Callers supply the interval extensions used in verification.
Univariate functions use `IntervalScalarFunction` and quadrature requests use `QuadratureOracle`, implemented respectively by context-free closures `Fn(DecoratedInterval<R>)` and `Fn(QuadratureRequest<R>, &mut [IntervalBox<R>])`.
Linear operators, residuals, and Jacobian operators implement `IntervalLinearOperator`, `IntervalResidualOperator`, and `IntervalJacobianOperator`, respectively.
For your own implementation, write methods without `_scoped` in their names (`enclose`, `residual_enclosure_into`, and `jvp_enclosure_into`); `_scoped` methods can retain their default implementation, discarding context and calling these methods.
The verifier counts evaluation limits before calling `_scoped` methods; providers override `_scoped` methods to account for work through context only for nested operations, such as forwarding context to another crate's `_scoped` function.
In `IntervalLinearOperator`, implementing `apply_enclosure_into` gives `apply_enclosure_into_scoped` its default implementation that checks stop requests before invoking it.
Correct extensions are the caller's mathematical responsibility; the verifier cannot detect violations.
An extension must return a set enclosing values at every point of the input set, including rounding errors in its own evaluation.
Point evaluations and error estimates are not enclosures and cannot serve as extensions.
Unbounded operator output makes the proof inconclusive; empty output or an operator whose shape changes gives an error of `InvalidInput`.

Affine arithmetic has configuration separate from verifiers.
`AffineContext::new(input_symbols, AffineOptions)` prepares input noise symbols; `AffineOptions` sets symbols retained per form (default 16) and the workspace byte limit.
Excess terms move into an anonymous remainder, preserving inclusion while being reported as lost correlation.
`context.workspace::<T>()` allocates temporary storage for $2(2m+2)$ terms, where $m$ is the retained symbol count; exceeding limits gives `ResourceLimit`.
Use `unary` (`AffineUnary`), `binary` (`AffineBinary`), `project` (`AffineProjection`), and `reduce` of `AffineForm`; each operation takes $O(n)$ for $n$ terms and allocates a result.
`AffineBinary::Atan2` and `AffineBinary::Hypot` accept only real forms; complex forms give `InvalidInput`.
`unary_into`, `binary_into`, `project_into`, and `reduce_into` of `AffineView` write to caller-provided `AffineViewMut` without allocation.

## Reading results, errors, and diagnostics

- **Errors**: Failures return `SciOxideError`.
  Classify with `kind()` and read arguments and reasons with `view()`.
  Errors carry no caller identity.
  - `InvalidInput`: Failed rounding-environment checks or unsupported architectures (reason `UnsupportedConfiguration`, argument `rounding_environment`), reversed endpoints or decorations forbidden by the set (reason `Inconsistent`), invalid proposals such as negative radii or centers outside intervals, quadrature pieces with gaps or overlaps, affine values from separate contexts, or interval extensions changing shape or returning empty or invalid enclosures.
  - `NonFinite`: NaN or infinite endpoints, centers, radii, or coefficients.
  - `DimensionMismatch`: Proposals, outputs, or right-hand sides whose lengths mismatch the problem.
  - `ResourceLimit`: Storage exceeding `ValidatedOptions::byte_limit` or `AffineOptions::byte_limit`.
  - `SizeOverflow` and `AllocationFailure`: Unrepresentable storage sizes and failed storage allocations, respectively.
  - `NumericalInstability`: Required enclosures are unbounded (`Overflow`), a one-shot function cannot establish nonsingularity (`IllConditioned`), or internal consistency checks fail (`Breakdown`).
  - `ConvergenceFailure`: A one-shot function reaches computation, capacity, or resolution limits (reasons `EvaluationLimit`, `IterationLimit`, `ResourceLimit`, or `StepSizeLimit`), or finishes without a decision (reason `Stagnation`).
  - `ExecutionStopped`: A one-shot function stops for cancellation or a deadline.
  - `DomainError`: A one-shot callback returns an empty enclosure or unknown continuity (decoration below `Dac`), with reason `Undefined`.
  - `Singular`: LU factorization in `solve` encounters a zero pivot.
    This is a floating-point factorization property, not proof of matrix singularity.

  Errors returned by callbacks propagate unchanged.
- **Out-of-domain inputs**: Denominators containing zero and negative square-root inputs are excluded, returning decoration `Trv` rather than errors.
  Elementary functions indicate these through `EnclosureStatus` (such as `PartiallyDefined`, `Undefined`, or `Inconclusive`).
- **Verification status**: Each verifier or Plan report has one status, with three kinds of results.
  These return in `Ok`; reaching computation limits and stop requests are not errors.
  One-shot functions return `Ok` only on success, converting other results to the `NumericalInstability`, `ConvergenceFailure`, `ExecutionStopped`, or `DomainError` errors above.
  - Success: `Verified` for linear systems and quadrature, `Proved` for roots.
  - Checks establish that the proposal is incorrect: `Rejected` for linear systems and quadrature, `Refuted` for roots.
    `Rejected` only indicates overly narrow proposed radii or bounds; it establishes neither system singularity nor an integral outside the bounds.
    `Refuted` proves the claim false.
  - Neither: `Inconclusive` with reasons from `ProofInconclusive`.
    Reasons are `Unbounded` (required bounds not finite), `EvaluationLimit` or `IterationLimit` (computation limits reached), `Stopped` (cancellation or deadline), or `Reason` (method-specific test failure); `Reason` contains linear-system `LinearProofFailure`, root `RootProofFailure`, or quadrature `QuadratureProofFailure` reasons.

  Failure to prove a claim does not prove its opposite; an inconclusive root proof says nothing about root presence or absence.
  Only proposal-checking `verify` returns linear-system `Rejected`; radii computed by the verifier itself (`solve`, `propose`, and `propose_into`) are never rejected.
- **Isolation and generation termination**: Root isolation and polynomial covering return `RootIsolationTermination` (`Complete`, `Inconclusive`, `Limit`, `Refuted`); quadrature generation returns `QuadratureTermination` (`ToleranceReached`, `Inconclusive`, `Limit`, `FixedBounds`).
  Reasons `RefinementLimit` in `Limit` are `Capacity` for exhausted output capacity and `Resolution` for unrepresentable subdivision points or radii.
  Quadrature proposal-generation termination diagnoses how the proposal was constructed; it is not proof.
- **Diagnostics**: Linear-system `LinearVerificationReport` contains norm upper bounds `LinearBounds`, residual upper bound `residual` at the center, and preconditioned-residual upper bound `correction`.
  Only `bounds` computes inverse and condition-number bounds; reports stopped before completing the matrix scan may lack bounds.
  Root `RootVerificationReport` stores the strongest fact established in this call (`evidence`) and an upper bound (`defect`) on Krawczyk $\lVert I - R J(X) \rVert$; polynomial `PolynomialVerificationReport` stores the proved count (`count`).
  Workspace `last_attempt` returns the last call's result and work counts.

## Summary and further reading

Arithmetic and elementary functions of `DecoratedInterval` return outward-rounded enclosures; environments failing rounding-environment checks return `InvalidInput` (`UnsupportedConfiguration`).
Construction, membership, and set operations use no rounding and run in every environment.
To prove linear systems, roots, or integrals once with defaults, use one-shot functions `solve`, `roots`, `polynomial_roots`, and `integrate`, receiving errors if no conclusion is reached.
Verifiers and Plans own `ValidatedOptions`; reserving workspace to `workspace_requirements` requirements avoids allocation in subsequent calls.
Verification distrusts proposals and recomputes bounds from the original problem; only report status is the proof decision.
Distinguish success (`Verified`, `Proved`), rejected proposals or refuted claims (`Rejected`, `Refuted`), and inconclusive results (`Inconclusive`) with reasons from `ProofInconclusive`; inconclusiveness does not negate a claim.
