輸送網の容量や、ワーカーと処理の対応のように、グラフの上の組合せ最適化の多くは疎な構造の上で解ける。
このページの二つの問題はどちらも線形計画として書け、その双対問題の解が最適性の**証拠**になる。
最大流では最小切断、二部マッチングでは最小頂点被覆が証拠で、どちらも整数なので厳密に比べられる。
計算した解と証拠を見比べると、解が最適であることを、解いたアルゴリズムとは独立に確かめられる。
組に費用の付いた割当ては[線形割当て問題](../linear-assignment/)で扱い、その証拠は浮動小数点の残差として解釈する。
ワンショット関数、標準形式、オプション付き形式、スコープ付き API といった呼び出しの形の呼び方は、[共通仕様と構成](oxref:sparse-execution-forms)で定義している。

## 最大流と最小切断

有向グラフ $G = (V, E)$ の各辺 $e$ に非負の整数の容量 $c(e)$ があるとする。
始点 $s$ から終点 $t$ への**流れ** $f$ は、容量の条件 $0 \le f(e) \le c(e)$ と、$s$、$t$ 以外の頂点での保存則（入る量と出る量が等しいこと）を満たす辺の値である。
$s$ から出る正味の量を流れの値 $\lvert f \rvert$ と呼ぶ。
$s \in S$、$t \notin S$ となる頂点の集合 $S$ による分割 $(S, V \setminus S)$ を**切断**と呼び、$S$ から外へ向かう辺の容量の和を切断の容量 $\mathrm{cap}(S)$ と呼ぶ。

$S$ に属する頂点で保存則を足し合わせると、$S$ の中を結ぶ辺の流れは打ち消し合い、

$$
\lvert f \rvert = \sum_{e:\, S \to V \setminus S} f(e) - \sum_{e:\, V \setminus S \to S} f(e) \le \mathrm{cap}(S)
$$

が残る。
したがって、任意の流れの値は任意の切断の容量を超えない。
最大流最小切断定理は、この不等式が最大値と最小値で等号になることを述べる。

$$
\max_f \lvert f \rvert = \min_S \mathrm{cap}(S)
$$

証明は増加路による。
残余グラフは各辺で、まだ流せる量 $c(e) - f(e)$ を順向きの弧に、戻せる量 $f(e)$ を逆向きの弧に持つグラフである。
残余グラフに $s$ から $t$ への道（増加路）があれば、その道に沿って流れを増やせる。
増加路がなければ、残余グラフで $s$ から届く頂点の集合を $S$ とすると、$S$ から外へ向かう辺はすべて飽和し（流れが容量に等しく）、外から $S$ へ入る辺の流れは 0 である。
上の式の不等号が等号になり、$\lvert f \rvert = \mathrm{cap}(S)$ となる。
容量が整数なら、増加路で流す量はいつも整数なので、整数の最大流が存在する（整数性）。

### Dinic 法

Dinic 法は残余グラフで $s$ から幅優先探索を行い、各頂点に $s$ からの最短の弧の数（レベル）を付ける。
レベルが 1 ずつ増える弧だけを残したレベルグラフで、それ以上増加路がなくなるまで深さ優先探索で流す。
この流れをブロッキングフローという。
ブロッキングフローを流した後も、レベルグラフの外の弧を使う増加路は残りうるので、レベルグラフを作り直して繰り返す。
各頂点で次に試す弧を覚えておくと、一つのブロッキングフローは $O(VE)$ で求まる。
一回ごとに $s$ から $t$ への残余グラフでの最短の弧の数が増えるので、繰り返しは高々 $V - 1$ 回で、全体の計算量は $O(V^2 E)$ である。

`MaxFlowPlan::new(vertices, edges)` は、容量付きの辺 `CapacityEdge { source, target, capacity }`（容量は `u64`）の列から、各辺に順向きと逆向きの弧を持つ Plan を $O(V + E)$ で作る。
範囲外の端点は `OutOfBounds` で拒む。
容量 0 の辺、自己ループ、平行な辺は許し、平行な辺は別々に扱う。
各頂点から出る弧は入力の順に試すので、同じ入力に対して結果は一通りに決まる。
`vertex_count()` は頂点の数、`edges()` は入力の順の辺を返す。
標準形式 `maximum_flow(source, sink)` は最大流と最小切断を `MaximumFlow` として返す。
始点や終点が頂点でなければ `OutOfBounds`、始点と終点が同じなら `InvalidInput` で拒み、流れの値や残余容量が `u64::MAX` を超えれば `SizeOverflow` で失敗する。
ワンショット関数 `maximum_flow(vertices, edges, source, sink)` は、Plan の作成と求解を一度に行う。
同じ網で別の始点と終点の組を解くときは、Plan を残して使い回す。

`MaximumFlow::as_view()` が返す `FlowView` は、公開フィールドとして、始点 `source`、終点 `sink`、流れの値 `value`、入力の辺の順の流れ `edge_flows`、切断の始点側の頂点を `true` で示す `source_side` を持つ。
計算した流れの `source_side` は最後の残余グラフで始点から届く頂点の集合である。
`FlowView::verify(&plan)` は、次のすべてを整数で確かめ、成り立てば `Ok(true)`、どれかが成り立たなければ `Ok(false)` を返す。

- 始点と終点が異なる頂点で、配列の長さが Plan と合う。
- 各辺の流れが容量を超えない。
- 始点と終点以外の頂点で保存則が成り立つ。
- 始点から出る正味の量と終点に入る正味の量がどちらも `value` に等しい。
- `source_side` が始点を含み、終点を含まない。
- その切断の容量が `value` に等しい。

和は 128 ビットの整数で計算し、128 ビットでもあふれたときは `SizeOverflow`、頂点ごとの和の配列を確保できなければ `AllocationFailure` で失敗する。
流れの値と切断の容量が厳密に等しければ、上の不等式から、その流れは最大でその切断は最小である。
したがって `verify` が真を返すことは最適性の証明になる。
フィールドは公開なので、他の方法で計算した流れも同じように確かめられる。

### 最大流と最小切断の検算

次のセルは 6 頂点の網（$s = 0$、$t = 5$）で最大流を求める。
辺は $0 \to 1$: 10、$0 \to 2$: 8、$1 \to 2$: 2、$1 \to 3$: 5、$2 \to 4$: $c$、$3 \to 5$: 7、$4 \to 3$: 4、$4 \to 5$: 6 で、入力は辺 $2 \to 4$ の容量 $c$（0〜12）である。
一つ目の表は辺ごとの流れと、`source_side` が示す切断 $S$ を渡る向きを示す。
二つ目の表は流れの値、切断の容量、`verify` の結果を示す。
独立な検算として、$s$ と $t$ 以外の 4 頂点を $S$ に入れるかどうかの 16 通りの切断をすべて数え、最小の容量を辺の一覧から求める。

```rust
//| id: sparse-flow-matching-certificates
//| ref: sparse-flow-matching-certificates
//| title: 最大流と最小切断の証拠
//| run: reactive
//| crates: [scioxide-core, scioxide-sparse]
//| inputs:
//|   capacity: {"type":"range","label":"辺 2→4 の容量 c","description":"c = 8 を境に最小切断が移る。","min":0,"max":12,"step":1,"value":5}
//| cases:
//|   - {"id":"closed","label":"c = 0","description":"辺 2→4 が使えず、流れは辺 1→3 を通る 5 だけになる。","inputs":{"capacity":0}}
//|   - {"id":"wide","label":"c = 12","description":"最小切断が終点の手前の辺 3→5 と 4→5 に移る。","inputs":{"capacity":12}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"summary","path":"/rows/0/0","equals":10}
//|       - {"artifact":"summary","path":"/rows/0/1","equals":"{0, 1, 2}"}
//|       - {"artifact":"summary","path":"/rows/0/2","equals":10}
//|       - {"artifact":"summary","path":"/rows/0/3","equals":10}
//|       - {"artifact":"summary","path":"/rows/0/4","equals":true}
//|       - {"artifact":"edges","path":"/rows/3/2","equals":5}
//|       - {"artifact":"edges","path":"/rows/4/2","equals":5}
//|   - case: closed
//|     expect:
//|       - {"artifact":"summary","path":"/rows/0/0","equals":5}
//|       - {"artifact":"summary","path":"/rows/0/3","equals":5}
//|       - {"artifact":"summary","path":"/rows/0/4","equals":true}
//|   - case: wide
//|     expect:
//|       - {"artifact":"summary","path":"/rows/0/0","equals":13}
//|       - {"artifact":"summary","path":"/rows/0/1","equals":"{0, 1, 2, 3, 4}"}
//|       - {"artifact":"summary","path":"/rows/0/3","equals":13}
//|       - {"artifact":"edges","path":"/rows/5/2","equals":7}
//|       - {"artifact":"edges","path":"/rows/7/2","equals":6}
use scioxide_sparse::{CapacityEdge, MaxFlowPlan};

// 辺の一覧（始点, 終点, 容量）。s = 0、t = 5。
let network = |c: u64| {
    [
        (0, 1, 10),
        (0, 2, 8),
        (1, 2, 2),
        (1, 3, 5),
        (2, 4, c),
        (3, 5, 7),
        (4, 3, 4),
        (4, 5, 6),
    ]
};
let edges_of = |c: u64| -> Vec<CapacityEdge> {
    network(c)
        .iter()
        .map(|&(source, target, capacity)| CapacityEdge {
            source,
            target,
            capacity,
        })
        .collect()
};
// 独立検算: s を含み t を含まない 16 通りの切断の容量の最小を、辺の一覧から求める。
let min_cut = |c: u64| -> u64 {
    (0..16_usize)
        .map(|mask| {
            let inside = |v: usize| v == 0 || (v != 5 && mask >> (v - 1) & 1 == 1);
            network(c)
                .iter()
                .filter(|e| inside(e.0) && !inside(e.1))
                .map(|e| e.2)
                .sum::<u64>()
        })
        .min()
        .unwrap_or(0)
};

let c = capacity.round() as u64;
let list = network(c);
let plan = MaxFlowPlan::new(6, &edges_of(c)).map_err(|e| e.to_string())?;
let flow = plan.maximum_flow(0, 5).map_err(|e| e.to_string())?;
let view = flow.as_view();
let side = view.source_side;
let rows: Vec<_> = list
    .iter()
    .zip(view.edge_flows)
    .map(|(&(u, v, cap), &f)| {
        let crossing = match (side[u], side[v]) {
            (true, false) => "S から外へ",
            (false, true) => "外から S へ",
            _ => "渡らない",
        };
        (format!("{u} → {v}"), cap, f, crossing)
    })
    .collect();
let columns = serde_json::json!([
    { "key": "0", "label": "辺", "type": "string" },
    { "key": "1", "label": "容量", "type": "integer" },
    { "key": "2", "label": "流れ", "type": "integer" },
    { "key": "3", "label": "切断 S との関係", "type": "string" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "edges" })
);

let members: Vec<String> = (0..6).filter(|&v| side[v]).map(|v| v.to_string()).collect();
let cut: u64 = list
    .iter()
    .filter(|e| side[e.0] && !side[e.1])
    .map(|e| e.2)
    .sum();
let verified = view.verify(&plan).map_err(|e| e.to_string())?;
let columns = serde_json::json!([
    { "key": "0", "label": "流れの値 |f|", "type": "integer" },
    { "key": "1", "label": "切断の始点側 S", "type": "string" },
    { "key": "2", "label": "cap(S)（辺の一覧から）", "type": "integer" },
    { "key": "3", "label": "全探索の最小切断容量", "type": "integer" },
    { "key": "4", "label": "FlowView::verify", "type": "boolean" }
]);
emit_table_with_columns!(
    columns,
    vec![(
        view.value,
        format!("{{{}}}", members.join(", ")),
        cut,
        min_cut(c),
        verified
    )],
    metadata = serde_json::json!({ "id": "summary" })
);
```

既定の $c = 5$ では最大流の値は 10 で、最小切断の始点側は $S = \{0, 1, 2\}$ になる。
$S$ から出る辺は $1 \to 3$（容量 5）と $2 \to 4$（容量 5）で、どちらも流れが容量に等しく、飽和している。
辺の一覧から足した切断の容量 10 は流れの値と一致して `verify` は真を返し、全探索の最小切断容量も 10 である。
$c = 0$ にすると辺 $2 \to 4$ は使えず、流れは $1 \to 3$ を通る 5 だけになる。
$c = 12$ では流れが 13 に増え、最小切断は終点の手前の $S = \{0, 1, 2, 3, 4\}$ に移る。
このとき $S$ から出る辺は $3 \to 5$（容量 7）と $4 \to 5$（容量 6）である。
$S = \{0, 1, 2\}$ の容量は $5 + c$、$S = \{0, 1, 2, 3, 4\}$ の容量は 13 なので、最大流の値は $\min(5 + c, 13)$ になり、$c = 8$ を境に最小切断が移る。

## 二部マッチングと König の定理

頂点が二つの集合 $U$（行）と $W$（列）に分かれ、辺が $U$ と $W$ の間にしかないグラフを二部グラフという。
端点を共有しない辺の集合を**マッチング** $M$、すべての辺の少なくとも一方の端点を含む頂点の集合を**頂点被覆** $C$ と呼ぶ。
マッチングの辺は互いに端点を共有しないので、それらを覆うには別々の頂点が要り、$\lvert M \rvert \le \lvert C \rvert$ が常に成り立つ。
二部グラフでは、König の定理により最大値と最小値で等号が成り立つ。

$$
\max_M \lvert M \rvert = \min_C \lvert C \rvert
$$

したがって、同じ大きさのマッチングと頂点被覆を示せば、どちらも最適であることが分かる。

最大マッチング $M$ から、同じ大きさの被覆は次のように作れる。
マッチングの辺とそうでない辺を交互にたどる道を交互路と呼び、相手のない行から交互路で届く頂点（出発した行を含む）の集合を $Z$ とする。
$C = (U \setminus Z) \cup (W \cap Z)$ と置く。
辺 $(u, w)$ を考える。
$u \notin Z$ なら $u \in C$ となる。
$u \in Z$ のとき、マッチングでない辺なら交互路を $w$ まで延ばせるので $w \in Z$ になる。
マッチングの辺なら、相手のある行 $u$ には相手の列 $w$ を通ってしか届かないので、やはり $w \in Z$ である。
どちらの場合も $w \in C$ となり、$C$ はすべての辺を覆う。
次に、$C$ の頂点はどれも相手を持つ。
$W \cap Z$ の列に相手がなければ、その交互路でマッチングを一本増やせて、$M$ が最大であることに反する。
また、相手のない行はすべて $Z$ に入るので、$U \setminus Z$ の行も相手を持つ。
さらに、列が $Z$ に入ればその相手の行もマッチングの辺をたどって $Z$ に入るので、各マッチングの辺はちょうど一方の端点だけが $C$ に入る。
したがって $\lvert C \rvert = \lvert M \rvert$ である。

Hopcroft–Karp 法はまだ相手のない行と列を結ぶ交互路（増加路）に沿ってマッチングを反転し、辺を一本ずつ増やす。
一回の段では相手のない行から幅優先探索を行って最短の増加路の長さを求め、その長さの頂点を共有しない増加路を深さ優先探索でまとめて反転する。
段の数は $O(\sqrt{V})$ なので、全体の計算量は $O((V + E)\sqrt{V})$ である。

ワンショット関数 `maximum_bipartite_matching(pattern)` は、構造の行を $U$、列を $W$ とし、保存された成分（0 を含む）を辺とする二部グラフの最大マッチングと最小頂点被覆を求め、`BipartiteMatching` を返す。
マッチングは Plan を持たない。
構造は長方形でもよい。
`as_view()` の `MatchingView` は、公開フィールドとして、行ごとの相手の列 `left`、列ごとの相手の行 `right`、被覆に入る行と列を示す `left_cover` と `right_cover` を持つ。
`cardinality()` がマッチングの辺の数を返す。
`MatchingView::verify(pattern)` は `bool` を返し、次のすべてが成り立つときだけ真になる。
配列の長さが構造と合い、相手の組がすべて保存された成分で、`left` と `right` が食い違わず、すべての成分の少なくとも一方の端点が被覆に入り、被覆の頂点の数がマッチングの辺の数に等しい。
どれも整数の比較なので、真なら König の定理からマッチングが最大で被覆が最小であることの証明になる。
オプション付き形式 `maximum_bipartite_matching_with_options(pattern, options)` は反復回数の上限を取る。

最大マッチングの大きさは成分の値を選んで達成できる最大の階数（構造階数）に等しい。
正方な構造に完全なマッチングがあることは、値を選べば正則になりうること（構造的に正則であること）にあたる。

### 実験のための可否の表

次の二つのセルは作業員 5 人（行）と仕事 5 件（列）の可否を表す $5 \times 5$ の構造を使う。
ワーカー 0 は処理 0 と 1、ワーカー 1 は処理 0、ワーカー 2 は処理 1、ワーカー 3 は処理 2、3、4、ワーカー 4 は処理 2 をできる。
定義のブロックの `allowed(extra_pair)` はワーカーごとにできる処理の一覧を返し、`extra_pair` が真ならワーカー 2 は処理 3 もできる。
`workers_matrix` は、その可否を値 1 の成分とする CSR 行列を組み立てる。

```rust
//| id: sparse-matching-workers
//| kind: definitions
//| title: 作業員 5 人と仕事 5 件の可否
//| crates: [scioxide-core, scioxide-sparse]
use scioxide_core::SciOxideError;
use scioxide_sparse::{CsrMatrix, DuplicatePolicy, ExplicitZeroPolicy, SparseBuilder};

/// ワーカー i（行）ができる処理（列）の一覧。extra_pair ならワーカー 2 は処理 3 もできる。
pub(crate) fn allowed(extra_pair: bool) -> [Vec<usize>; 5] {
    let worker2 = if extra_pair { vec![1, 3] } else { vec![1] };
    [vec![0, 1], vec![0], worker2, vec![2, 3, 4], vec![2]]
}

/// ワーカー i が処理 j をできるとき成分 (i, j) を 1 とする 5 × 5 の CSR 行列。
pub(crate) fn workers_matrix(jobs: &[Vec<usize>; 5]) -> Result<CsrMatrix<f64>, SciOxideError> {
    let mut builder = SparseBuilder::new(5, 5);
    for (i, row) in jobs.iter().enumerate() {
        for &j in row {
            builder.push(i, j, 1.0)?;
        }
    }
    builder.finish_csr(DuplicatePolicy::Reject, ExplicitZeroPolicy::Preserve)
}
```

### 二部マッチングと頂点被覆

次のセルはワンショット関数 `maximum_bipartite_matching` で最大マッチングと頂点被覆を求める。
入力は、ワーカー 2 が処理 3 もできるかどうかである。
一つ目の表は番号ごとの相手と被覆、二つ目の表はマッチングと被覆の大きさと `verify` の結果を示す。
独立な検算として、被覆に入らない成分の数を可否の一覧から数え、$5! = 120$ 通りの割当てを全探索して、許される組の数の最大を求める。
正方な構造では、どのマッチングも置換に広げられるので、この最大が最大マッチングの大きさになる。

```rust
//| id: sparse-bipartite-matching-cover
//| ref: sparse-bipartite-matching-cover
//| title: 二部マッチングと König の頂点被覆
//| run: reactive
//| uses: [sparse-matching-workers]
//| crates: [scioxide-core, scioxide-sparse]
//| inputs:
//|   extra_pair: {"type":"checkbox","label":"ワーカー 2 が処理 3 もできる","value":false}
//| cases:
//|   - {"id":"perfect","label":"ワーカー 2 が処理 3 もできる","description":"完全なマッチングができ、構造は構造的に正則になる。","inputs":{"extra_pair":true}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"matching","path":"/rows/1/1","equals":null}
//|       - {"artifact":"matching","path":"/rows/3/2","equals":true}
//|       - {"artifact":"summary","path":"/rows/0/0","equals":4}
//|       - {"artifact":"summary","path":"/rows/0/1","equals":4}
//|       - {"artifact":"summary","path":"/rows/0/2","equals":0}
//|       - {"artifact":"summary","path":"/rows/0/3","equals":4}
//|       - {"artifact":"summary","path":"/rows/0/4","equals":true}
//|   - case: perfect
//|     expect:
//|       - {"artifact":"matching","path":"/rows/2/1","equals":3}
//|       - {"artifact":"summary","path":"/rows/0/0","equals":5}
//|       - {"artifact":"summary","path":"/rows/0/3","equals":5}
//|       - {"artifact":"summary","path":"/rows/0/4","equals":true}
use scioxide_sparse::maximum_bipartite_matching;

let n = 5;
let jobs = allowed(extra_pair);
let matrix = workers_matrix(&jobs).map_err(|e| e.to_string())?;
let pattern = matrix.structural_pattern();
let matching = maximum_bipartite_matching(pattern).map_err(|e| e.to_string())?;
let m = matching.as_view();
let rows: Vec<_> = (0..n)
    .map(|k| (k, m.left[k], m.left_cover[k], m.right[k], m.right_cover[k]))
    .collect();
let columns = serde_json::json!([
    { "key": "0", "label": "番号 k", "type": "integer" },
    { "key": "1", "label": "ワーカー k の処理", "type": "integer", "nullText": "なし" },
    { "key": "2", "label": "ワーカー k が被覆に入る", "type": "boolean" },
    { "key": "3", "label": "処理 k のワーカー", "type": "integer", "nullText": "なし" },
    { "key": "4", "label": "処理 k が被覆に入る", "type": "boolean" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "matching" })
);

let cover = m
    .left_cover
    .iter()
    .chain(m.right_cover)
    .filter(|&&c| c)
    .count();
// 独立検算: 被覆に入らない成分の数と、120 通りの置換での許される組の数の最大。
let uncovered: usize = (0..n)
    .map(|i| {
        let open = |&&j: &&usize| !m.left_cover[i] && !m.right_cover[j];
        jobs[i].iter().filter(open).count()
    })
    .sum();
let best = (0..n.pow(5))
    .map(|code| {
        (0..n)
            .map(|i| code / n.pow(i as u32) % n)
            .collect::<Vec<_>>()
    })
    .filter(|p| (0..n).all(|j| p.contains(&j)))
    .map(|p| (0..n).filter(|&i| jobs[i].contains(&p[i])).count())
    .max()
    .unwrap_or(0);
let columns = serde_json::json!([
    { "key": "0", "label": "|M|", "type": "integer" },
    { "key": "1", "label": "|C|", "type": "integer" },
    { "key": "2", "label": "覆われない成分の数（一覧から）", "type": "integer" },
    { "key": "3", "label": "全探索の最大の大きさ", "type": "integer" },
    { "key": "4", "label": "MatchingView::verify", "type": "boolean" }
]);
emit_table_with_columns!(
    columns,
    vec![(m.cardinality(), cover, uncovered, best, m.verify(pattern))],
    metadata = serde_json::json!({ "id": "summary" })
);
```

既定では、ワーカー 0、1、2 ができる処理が 0 と 1 の二つしかないので、三人のうち一人は割り当てられず、最大マッチングの大きさは 4 になる。
計算したマッチングではワーカー 1 に相手がなく、被覆はワーカー 3、4 と処理 0、1 の 4 頂点である。
ワーカー 1 から交互路で届くのは処理 0、1 とワーカー 0、2 なので、被覆は上の構成 $C = (U \setminus Z) \cup (W \cap Z)$ のとおりになっている。
覆われない成分は 0 個で、$\lvert M \rvert = \lvert C \rvert = 4$ は全探索の最大 4 と一致し、`verify` も真を返す。
ワーカー 2 が処理 3 もできるようにすると、完全なマッチングができる。
このとき被覆は作業員 5 人全員で、構造は構造的に正則になる。

## スコープ付き API と作業領域

二つの問題は作業領域を内部で確保する形（最大流のワンショット関数と標準形式 `maximum_flow`、マッチングのワンショット関数とオプション付き形式）のほかに、事前確保した作業領域だけを使うスコープ付き API `maximum_flow_scoped`、`maximum_bipartite_matching_scoped` を持つ。
スコープ付き API はオプション `GraphExecutionOptions`、作業領域、根のコンテキストか外側の解法のコンテキスト `scope` を受け取り、作業領域を借用した結果（`FlowView`、`MatchingView`）を返す。

最大流の作業領域は Plan の `workspace(())` で作るか、`workspace_requirements(())` が返す `FlowWorkspaceRequirements` に対して `FlowWorkspace::try_reserve` で事前確保する。
マッチングは Plan を持たないので、`MatchingWorkspace::workspace(pattern)` で作るか、`MatchingWorkspace::workspace_requirements(pattern)` が返す `MatchingWorkspaceRequirements` に対して事前確保する。
要件の `bytes()` は論理バイト数を返し、作業領域の `check` で足りるかを確かめられる。
空の作業領域は各型の `new()` で作り、`try_reserve` で事前確保する。
足りない作業領域は広げずに `DimensionMismatch` で拒む。
作業領域は縮まないので、一つの作業領域を複数の Plan や構造に使い回せる。

`GraphExecutionOptions::with_budgets` で反復回数の上限を与えると、反復は次の単位で数える（章に共通の規則は[反復回数の上限と実行コンテキスト](oxref:sparse-iteration-limits)）。

- 最大流：レベルグラフを作る幅優先探索ごとと、ブロッキングフローの中で増加路を探す深さ優先探索ごとに 1 回。
  どちらも、何も見つからずに終わる最後の探索を含む。
- マッチング：Hopcroft–Karp 法の段ごとに 1 回。
  増加路がないことを確かめる最後の幅優先探索も 1 回と数える。

上限に達すると `ConvergenceFailure`、取り消しや期限では `ExecutionStopped` を返す。
最大流のワンショット関数と標準形式、マッチングのワンショット関数は上限を持たないので、この二つのエラーを返さない。
マッチングのオプション付き形式は与えた上限に達すると `ConvergenceFailure` を返す。
二つの問題はどの実行方針でも逐次に実行する。
失敗したときは部分的な結果を出力に反映せず、作業領域の `last_accepted()` は `None` を返す。
`last_attempt()` は、始まる前に拒まれた呼び出しを含めて、最後の試行の記録を返す。

### 反復回数の上限と試行の記録

次のセルは同じ可否の表でスコープ付き API `maximum_bipartite_matching_scoped` を呼ぶ。
入力は、ワーカー 2 が処理 3 もできるかどうかと、反復回数の上限である。
作業領域の `last_attempt()` から数えた反復の回数を、`last_accepted()` から成功した結果のマッチングの大きさを読む。

```rust
//| id: sparse-matching-iteration-limit
//| ref: sparse-matching-iteration-limit
//| title: スコープ付き API のマッチングと反復回数の上限
//| run: reactive
//| uses: [sparse-matching-workers]
//| crates: [scioxide-core, scioxide-sparse]
//| inputs:
//|   extra_pair: {"type":"checkbox","label":"ワーカー 2 が処理 3 もできる","value":false}
//|   phase_limit: {"type":"select","label":"反復回数の上限","options":[{"label":"なし","value":"none"},{"label":"2","value":"2"},{"label":"3","value":"3"}],"value":"none"}
//| cases:
//|   - {"id":"limit-two","label":"上限 2","description":"増加路がないことを確かめる 3 回目の探索で上限に達する。","inputs":{"phase_limit":"2"}}
//|   - {"id":"perfect-limit-three","label":"処理 3 を加えて上限 3","description":"完全なマッチングは 3 回の段でできるが、増加路がないことを確かめる 4 回目の探索で上限に達する。","inputs":{"extra_pair":true,"phase_limit":"3"}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"attempt","path":"/rows/0/0","equals":"成功"}
//|       - {"artifact":"attempt","path":"/rows/0/1","equals":3}
//|       - {"artifact":"attempt","path":"/rows/0/2","equals":4}
//|   - case: limit-two
//|     expect:
//|       - {"artifact":"attempt","path":"/rows/0/0","equals":"ConvergenceFailure"}
//|       - {"artifact":"attempt","path":"/rows/0/1","equals":2}
//|       - {"artifact":"attempt","path":"/rows/0/2","equals":null}
//|   - case: perfect-limit-three
//|     expect:
//|       - {"artifact":"attempt","path":"/rows/0/0","equals":"ConvergenceFailure"}
//|       - {"artifact":"attempt","path":"/rows/0/1","equals":3}
use scioxide_core::{Budget, BudgetKind, ExecutionContext, SolveBudgets};
use scioxide_sparse::{
    GraphExecutionOptions, MatchingWorkspace, maximum_bipartite_matching_scoped,
};

let jobs = allowed(extra_pair);
let matrix = workers_matrix(&jobs).map_err(|e| e.to_string())?;
let pattern = matrix.structural_pattern();
let mut budgets = SolveBudgets::unbounded();
if phase_limit != "none" {
    let limit: usize = phase_limit
        .parse()
        .map_err(|_| "上限が整数でない".to_string())?;
    let limit = Budget::try_from(limit).map_err(|e| e.to_string())?;
    budgets = budgets.with_limit(BudgetKind::Iteration, limit);
}
let options = GraphExecutionOptions::new().with_budgets(budgets);
let mut workspace = MatchingWorkspace::workspace(pattern).map_err(|e| e.to_string())?;
let failure = maximum_bipartite_matching_scoped(
    pattern,
    options,
    &mut workspace,
    ExecutionContext::sequential(),
)
.err()
.map(|e| format!("{:?}", e.kind()));
// 試行の記録には、失敗した呼び出しでもそれまでに数えた反復が残る。
let iterations = workspace
    .last_attempt()
    .map(|record| record.counts().own().iterations());
// 最後の呼び出しが成功したときだけ、作業領域から結果を読める。
let accepted = workspace.last_accepted().map(|m| m.cardinality());
let result = failure.unwrap_or_else(|| "成功".to_string());
let columns = serde_json::json!([
    { "key": "0", "label": "呼び出しの結果", "type": "string" },
    { "key": "1", "label": "数えた反復 [回]", "type": "integer", "nullText": "-" },
    { "key": "2", "label": "last_accepted の |M|", "type": "integer", "nullText": "None" }
]);
emit_table_with_columns!(
    columns,
    vec![(result, iterations, accepted)],
    metadata = serde_json::json!({ "id": "attempt" })
);
```

既定では反復は 3 回と数えられ、増加路を反転した 2 回の段と、増加路がないことを確かめる最後の探索からなる。
上限を 2 にすると 3 回目の探索で上限に達して `ConvergenceFailure` が返り、`last_accepted()` は `None` になる。
ワーカー 2 が処理 3 もできるようにすると、完全なマッチングは 3 回の段でできるが、増加路がないことを確かめる 4 回目の探索も数えるので、上限 3 では同じく `ConvergenceFailure` になる。
失敗した呼び出しでも、`last_attempt()` の記録には上限に達するまでに数えた反復が残る。

## まとめ

最大流と二部マッチングは、どちらも線形計画の双対を持ち、最小切断と最小頂点被覆が解の最適性の証拠になる。
最大流は Dinic 法で $O(V^2 E)$、最大マッチングは Hopcroft–Karp 法で $O((V + E)\sqrt{V})$ で求まる。
`FlowView::verify` と `MatchingView::verify` は整数の比較で最適性を厳密に確かめ、フィールドが公開なので他の方法で求めた解にも使える。
正方な構造では、完全なマッチングがあるかどうかで構造的に正則かどうかが分かる。
反復の回数には何も見つからずに終わる最後の探索も入るので、マッチングでは上限を増加路を反転する段の数より 1 回多く与える。
