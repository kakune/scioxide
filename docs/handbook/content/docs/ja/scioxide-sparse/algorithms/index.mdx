この章のアルゴリズムは格納、積、直接分解、前処理、並べ替え、グラフのどれも、いくつかの共通の約束の上に作られている。
構造と値を分けて扱うこと、構造だけを見る段と値を使う段を分けること、使うメモリの上限を呼び出し側が決めること、失敗したときに出力を変えないことである。
このページでは、各アルゴリズムのページが前提とするこれらの約束、記号、呼び出しの形の名前をまとめ、ページ一覧を示す。
エラー、作業領域、許容誤差のクレートに共通の考え方は [エラー仕様と部分結果](../../concepts/errors-and-partial-results/) と [実行形式・作業領域・再現性](../../concepts/workspaces-and-reproducibility/) にある。

## 記号

| 記号 | 意味 |
|---|---|
| $\mathbf{A} \in \mathbb{R}^{m \times n}$（または $\mathbb{C}^{m \times n}$） | 疎行列 |
| $\mathcal{S}(\mathbf{A})$ | 値を保存する位置の集合（非零パターン、構造） |
| $\mathrm{nnz}(\mathbf{A}) = \lvert \mathcal{S}(\mathbf{A}) \rvert$ | 保存した成分の数 |
| $G(\mathbf{A})$ | 正方な $\mathbf{A}$ の構造を辺とするグラフ |
| $p[\text{新}] = \text{旧}$ | 置換 `Permutation` の向き（`new_to_old()`）。$\mathbf{B}_{ij} = \mathbf{A}_{p[i], p[j]}$ のように元の番号を集める |
| $\varepsilon = 2^{-52}$ | 倍精度の計算機イプシロン |
| $u = \varepsilon/2 = 2^{-53}$ | 倍精度の単位丸め |
| $\gamma_k = ku/(1 - ku)$ | $k$ 回の丸めを重ねたときの誤差限界の係数（Higham の記法） |
| $\kappa_2(\mathbf{A})$ | 2 ノルムの条件数 |

## 構造と値

`scioxide-sparse` の格納形式はどれも正準で、各位置は一度だけ決まった順に現れ、保存された値はすべて有限である（[疎行列の格納形式と組立て](storage-and-assembly/)）。
確定した行列に成分を挿入する方法も、成分を削除する方法もない。
値は `CooMatrix`、`CsrMatrix`、`CscMatrix` の `set_value`、`copy_values_from`、`update_values` で、有限性を検査してから書き換えられる。
`BsrMatrix` と `DiaMatrix` は値を更新する方法を持たないので、正準な形式で更新してから変換し直す。
`CsrMatrix::try_assign_pattern` は形と構造を丸ごと別のものに置き換えて値をすべて 0 にし、メモリ領域だけを使い回す。
置き換えたあとの行列には前の構造から作った解析、因子、Plan を使えない。

構造が変わらなければ、構造から計算したもの（並べ替え、消去木、積の構造、作業領域の大きさ）はすべてそのまま使える。
係数だけが変わる時間発展や Newton 法では、構造の計算を一度だけ済ませ、値の計算を繰り返す。

## 格納されていないゼロ成分と明示的に格納されたゼロ成分

**格納されていないゼロ成分**は $\mathcal{S}(\mathbf{A})$ に含まれない位置で、メモリを使わず、アルゴリズムはその位置を訪れない。
**明示的に格納されたゼロ成分**は $\mathcal{S}(\mathbf{A})$ に含まれ、値がちょうど 0 の位置である。
明示的に格納されたゼロ成分は構造の一部として扱われ、記号解析ではフィルの計算に、グラフでは重み 0 の辺に、構造の比較では一致の判定に入る。
どちらにするかは組立ての `ExplicitZeroPolicy::Preserve` と `Drop` で選び、値の打ち消しで 0 になった位置も同じ規則に従う。
係数の値によって構造が変わらないようにしたいときは `Preserve` を選ぶ。

## 記号段と数値段

多くのアルゴリズムは構造だけを見る段（記号段）と値を使う段（数値段）に分かれる。
記号段は値によらないので、構造が同じなら一度だけ実行すればよい。
何を記号段で確定できるかはアルゴリズムによって違う。

| アルゴリズム | 記号段で決まること | 数値段で決まること |
|---|---|---|
| 疎行列の積（`SparseProductPlan`） | 出力の構造（打ち消しを無視） | 値 |
| Cholesky（`SparseSymmetricSymbolic`） | 並べ替え、消去木、構造上のフィル | 値 |
| LDL（同上） | 並べ替え、Cholesky の構造 | 1×1 と 2×2 のピボットの選択と、それに伴う追加のフィル |
| LU（`SparseLuSymbolic`） | 列の順序 | 行のピボット、フィル |
| QR（`SparseQrSymbolic`） | 列の順序 | Householder ベクトルと $\mathbf{R}$ の構造と値、最小ノルム Plan での階数 |
| 不完全分解（`IncompleteSymbolic`） | 入力の構造の写しとブロックの大きさ | レベルか閾値で決まるフィルの位置と値 |
| AMG（`AmgHierarchy`） | なし（集約は値で決まる） | 階層全体 |

積と Cholesky では、数値段で使うメモリの大きさが記号段で決まる。
LU と LDL ではピボットの選び方で因子の大きさが変わり、QR と不完全分解では因子の構造を数値段で求めるので、因子の大きさは数値段が終わるまで分からない。
これらの分解では、使うメモリを呼び出し側が与える上限で抑える（[上限と作業領域](#上限と作業領域)）。
数値段をやり直す `refactor` は、記号段と構造が厳密に一致する行列だけを受け付け、違う構造の行列は `InvalidInput` で拒む。

## 呼び出しの形

同じ計算を、必要な制御の量に応じていくつかの形で呼べる。
この章では引数と戻り値の形を次の名前で呼ぶ。

| 形 | 例 | 受け取るもの | 返すもの | 実行コンテキスト |
|---|---|---|---|---|
| ワンショット関数 | `solve(&a, &b)`、`least_squares`、`shortest_paths`、`connected_components`、`maximum_flow`、`maximum_bipartite_matching`、`minimum_cost_assignment`、`laplacian` | 問題のデータだけ | 答え | `sequential_native()` |
| 準備を一括して行うコンストラクター | `SparseLu::new(&a)`、`SparseCholesky::new`、`SparseLdl::new`、`SparseQrMinimumNormPlan::new`、`IncompleteFactor::ilu0`・`ic0`、`AmgPreconditioner::new`、`JacobiPreconditioner::new` | 行列だけ | 因子、Plan、前処理 | `sequential_native()` |
| 標準形式 | `SparseLu::factor(symbolic, a.view())`、`lu.solve(&b)`、`solve_transpose`、`solve_adjoint`、前処理の `apply(&r)`、`graph.shortest_paths(method)` | 準備した値と入力だけ | 新しく確保した結果 | `sequential_native()` |
| オプション付き形式 | `maximum_bipartite_matching_with_options(pattern, options)`、`a.add_with_options(&b, options)`、`SparseProductPlan::with_options(&a, &b, options)` | 入力と、最後にオプション | 新しく確保した結果 | `sequential_native()` |
| 出力先を指定する API | `lu.solve_into(&b, operation, options, &mut x, &mut ws, scope)`、`plan.evaluate_into(&a, &b, options, &mut c, &mut ws, context)` | 入力、オプション、出力、作業領域、コンテキストの順 | 出力に書く | 渡したコンテキスト |
| スコープ付き API | `SparseLu::factor_scoped(symbolic, a.view(), options, scope)`、`graph.shortest_paths_scoped(method, options, &mut ws, scope)` | 入力、オプション、作業領域（あれば）、最後にコンテキスト | 値 | 渡したコンテキスト |

ワンショット関数は問題を一回解いて答えだけを返す自由関数である。
内部の解析、分解、Plan は、その関数が定める設定で作る。
たとえば `solve(&a, &b)` は `SparseLu::new` と `solve` を続けて呼ぶ。
`least_squares` は閾値 $\tau = \min(\max(m, n)\,\varepsilon,\ 1/2) \max_j \lVert \mathbf{A}_{:,j} \rVert_2$ で数値階数を決め、最小ノルム解を返す。
`shortest_paths` は、負の重みがなければ Dijkstra 法、あれば Bellman–Ford 法を使い、始点から届く負の閉路があると `DomainError` を返す。
グラフの Plan の標準形式 `GraphPlan::shortest_paths` は同じ負の閉路をエラーではなく結果の値として返す。

準備を一括して行うコンストラクターは上限を取らずに解析から分解や構築までを済ませる `new` などの関数である。
直接分解の `new` は因子の要素数の上限を自分で選ぶ。
`SparseCholesky::new` は、記号解析が予測した因子の要素数をそのまま上限にする。
`SparseLu::new`、`SparseLdl::new`、`SparseQrMinimumNormPlan::new` は上限を見積もりから始め、`ResourceLimit` で失敗するたびに倍にして、その行列のどの因子も超えない大きさで止める。
見積もりと止める大きさは、LU が $\mathrm{nnz}(\mathbf{A}) + n$ と $n^2$、LDL が Cholesky の要素数と $n(n-1)/2$、$m \times n$ の QR が $\mathrm{nnz}(\mathbf{A}) + \max(m, n)$ と $\min(m, n)\,(m + n)$ である（QR は消去中の非零の上限も同時に倍にし、$mn$ で止める）。
上限は容量と比較にしか使わないので、どちらの選び方でも、十分な上限を与えて解析と分解をした場合と同じ因子が返る。
失敗した試行は計算をやり直させるだけで、結果を変えない。
`IncompleteFactor::ilu0` と `ic0` は、自然順、ブロックの大きさ 1、$\mathrm{nnz}(\mathbf{A}) + n$ ブロックの上限、バイト数の上限なしで解析する。
`AmgPreconditioner::new` は、定数ベクトルを近零空間とする既定の設定で階層を作る。

標準形式は解析、因子、前処理、グラフの Plan のように準備した値のメソッドで、オプション、作業領域、コンテキストを取らない。
対応するスコープ付き API か出力先を指定する API を、既定のオプション（`SparseSolveOptions::new()` か `GraphExecutionOptions::new()`）、新しく確保した作業領域、`ExecutionContext::sequential_native()` で呼んだときと同じ数値を返す。
`sequential_native()` は呼び出したスレッドで逐次に動くコンテキストで、`std` があれば CPU 固有の命令を使うカーネルに振り分け、クロック、取り消し、乱数源を持たない。

オプション付き形式は名前が `_with_options` で終わり、最後の引数にオプションを受け取る。
この章では反復回数の上限を受け取る `maximum_bipartite_matching_with_options`、精度と零の方針を受け取る `CsrMatrix` の `add_with_options`・`subtract_with_options`・`hadamard_with_options` と `SparseView::scaled_with_options` がこれにあたる。
コンストラクターの `SparseProductPlan::with_options`（出力の要素数の上限）と `SchwarzPlan::with_options`（メモリの上限と重みの許容誤差）も同じ形である。
結果は標準形式と同じく新しく確保する。

出力先を指定する API は名前が `_into` で終わり、呼び出し側が用意した出力と作業領域に書く。
`solve_into`、`solve_block_into`、前処理の `apply_into`・`apply_block_into`、`SparseProductPlan::evaluate_into`、`sparse_dense_into` は、オプションとコンテキストも受け取る。
scioxide-core の作用素のトレイトが定める `LinearOperator::apply_into(x, y, workspace)` と `Preconditioner::precondition_into` は、オプションとコンテキストを取らず、既定のオプションで逐次に計算する。
精度は `Standard` で、`SparseView::with_accuracy` が返す `SparseOperator` だけは結び付けた精度を使う。
数値分解をやり直す `refactor(matrix, options, workspace, scope)` は、名前は違うが、因子を出力として出力先を指定する API と同じ規則で書き換える。
事前確保した作業領域を使う出力先を指定する API と `refactor` は確保しない。

スコープ付き API は名前が `_scoped` で終わり、オプションとコンテキストを受け取って、配列に書くのではなく値を返す。
`factor_scoped` は因子を返す。
グラフの `shortest_paths_scoped`、`maximum_flow_scoped`、`AssignmentPlan::solve_scoped` と `maximum_bipartite_matching_scoped` は作業領域も受け取り、作業領域を借りた結果のビューを返す。
このビューは同じ作業領域を次の呼び出しに渡すまで使える。
`AmgHierarchy::build`、`AmgPreconditioner::build`、`SparseQrMinimumNormPlan::build` も、最後にオプションとコンテキストを受け取って値を返す。

分解、求解、前処理、グラフの出力先を指定する API とスコープ付き API には、`ExecutionContext::sequential()` などの根のコンテキストか、外側の解法の `SolveContext` を渡す。
外側の解法のコンテキストを渡すと、その呼び出しの反復は外側の解法の上限にも数えられる。
積の出力先を指定する API `evaluate_into` と `sparse_dense_into` は `ExecutionContext` だけを受け取り、反復を数えない。
並列のエグゼキューター、取り消し通知、期限はコンテキストを通じて参照するので、これらを使えるのは出力先を指定する API とスコープ付き API だけである。

答えだけが要る一回の計算にはワンショット関数を、同じ行列で何度も解くときは準備を一括して行うコンストラクターか標準形式の分解を使う。
反復の内側で確保をなくすとき、並列実行や取り消しを使うとき、反復回数の上限を外側の解法と共有するときは、出力先を指定する API とスコープ付き API を使う。

## 上限と作業領域

疎な直接分解のフィルは悪い順序では $O(n^2)$ の密行列にまで増える。
そのため、記号解析やコンストラクターに上限を与えて分解と前処理を作る形は、使ってよいメモリの上限を必須の引数として受け取り、超えると `ResourceLimit` で止まる。
上限の型はアルゴリズムごとに異なる。

| 型 | コンストラクター | 制限するもの |
|---|---|---|
| `SparseLuLimits` | `new(max_factor_entries, max_workspace_bytes)` | 因子の要素数、論理バイト数 |
| `SparseSymmetricLimits` | `new(max_factor_entries, max_active_entries, max_workspace_bytes)` | 因子、消去中の Schur 補行列の非零、バイト数 |
| `SparseQrLimits` | `new(max_factor_entries, max_active_entries, max_workspace_bytes)` | Householder ベクトルと $\mathbf{R}$、未消去の部分行列、バイト数 |
| `IncompleteLimits` | `new(max_factor_blocks, max_workspace_bytes)` | 保存するブロックの数、バイト数 |
| `AmgLimits` | `new(max_levels, max_entries, max_setup_bytes)` | 階層の深さ、各行列と積の要素数、構築のバイト数 |
| `SchwarzOptions` | `new().with_max_plan_bytes(…).with_max_workspace_bytes(…)` | Plan と作業領域のバイト数（既定は上限なし） |

`JacobiPreconditioner::new` は次元に比例するメモリしか使わず、`IdentityPreconditioner::new` はメモリを確保しないので、どちらも上限を取らない。
ワンショット関数とコンストラクターも上限を取らず、直接分解では[呼び出しの形](#呼び出しの形)で述べた規則で因子の要素数の上限を選ぶ。
バイト数はメモリのアロケーターの付随情報を含まない論理的な量で、`usize` の幅によって変わるので、32 ビットと 64 ビットの環境で同じ上限が通るとは限らない。

必要な量は確保の前に問い合わせられる。
各アルゴリズムの `workspace_requirements(...)` は `*Requirements`（バイト数や要素数）を返し、作業領域の型（`SparseLuWorkspace` など）の `check` で足りるかを確かめ、`try_reserve` で事前確保する。
`workspace(...)` は問い合わせと事前確保を一度に済ませる。
事前確保した作業領域を使う数値段は確保しない。
一方、`SparseBuilder::push`、標準形式の `solve` や `multiply`、形式の変換などは必要に応じて確保する。
直接分解、不完全分解、三角系、前処理の求解は共通の `SparseSolveWorkspace` を使い、`SparseSolveWorkspace::borrowed(&mut scratch)` で呼び出し側の配列を借りることもできる。
借りた配列は長さだけを検査し、必要量より長ければ先頭の必要量だけを使う。

## 失敗したときの出力

出力を書き込む演算（出力先を指定する API、`refactor`、値の更新）は、すべての検査と計算を作業領域で終えてから、出力や因子を一度に書き換える。
そのため、失敗したときは呼び出し側の出力も、以前に成功した因子や行列の値も変わらない。
作業領域の中身は失敗のあとで不定になりうるが、そのまま次の呼び出しに使える。
作業領域の `last_attempt()` は最後の試行の記録を返す。
部分的な結果を出力に反映することはない。

### 失敗した演算の前後の値

次のセルは $3 \times 3$ の上三角行列 $\mathbf{A}$ の LU 因子と $\mathbf{A}$ そのものに対して、四つの演算を順に試す。
一つ目は長さ 2 の右辺を渡す求解、二つ目は長さを必要量 $+\,d$ にした借用の作業領域を渡す求解である。
三つ目は一つ目の失敗に使った因子と作業領域をそのまま使って $\mathbf{b} = (1, 1, 1)$ を解き直す。
四つ目は候補の一つに NaN を書く `update_values` である。
入力は出力の配列に前もって入れておく値 $c$ と、作業領域の長さの差 $d$ である。
表は、演算ごとに結果の分類、書き込み先の成分のうち値が変わった数、成功した求解の残差 $\lVert \mathbf{b} - \mathbf{A}\hat{\mathbf{x}} \rVert_\infty$ を示す。

```rust
//|       - {"artifact":"attempts","path":"/rows/1/1","equals":"成功"}
//|       - {"artifact":"attempts","path":"/rows/1/3","equals":3}
//|       - {"artifact":"attempts","path":"/rows/1/5","range":{"max":1e-15}}
use scioxide_core::{ExecutionContext, SciOxideError};
use scioxide_sparse::{
    CsrMatrix, DuplicatePolicy, ExplicitZeroPolicy, SparseBuilder, SparseLu, SparseLuLimits,
    SparseLuSymbolic, SparseOperation, SparseOrdering, SparseSolveOptions,
    SparseSolveWorkspace,
};

// 求解を 1 回試し、(結果の分類, 値が変わった成分の数, 残差) を返す。
fn solve_attempt(
    lu: &SparseLu<f64>,
    a: &CsrMatrix<f64>,
    rhs: &[f64],
    start: [f64; 3],
    workspace: &mut SparseSolveWorkspace<'_, f64>,
) -> Result<(String, usize, Option<f64>), String> {
    let (options, scope) = (SparseSolveOptions::new(), ExecutionContext::sequential());
    let mut x = start;
    let result = lu.solve_into(
        rhs,
        SparseOperation::Normal,
        options,
        &mut x,
        workspace,
        scope,
    );
    let changed = x.iter().zip(&start).filter(|(u, v)| u != v).count();
    match result {
        Ok(()) => {
            // 独立検算: 求解とは別に積 A x̂ を作り、‖b − A x̂‖∞ を求める。
            let ax = a.apply(&x).map_err(|e| e.to_string())?;
            let r = rhs
                .iter()
                .zip(&ax)
                .fold(0.0_f64, |m, (u, v)| m.max((u - v).abs()));
            Ok(("成功".to_string(), changed, Some(r)))
        }
        Err(e) => Ok((format!("{:?}", e.kind()), changed, None)),
    }
}

// A = [[2, 0, 0], [0, 3, 1], [0, 0, 4]] の LU 因子を自然順で作る。
let mut builder = SparseBuilder::new(3, 3);
builder
    .extend(&[0, 1, 1, 2], &[0, 1, 2, 2], &[2.0_f64, 3.0, 1.0, 4.0])
    .map_err(|e| e.to_string())?;
let mut a = builder
    .finish_csr(DuplicatePolicy::Reject, ExplicitZeroPolicy::Drop)
    .map_err(|e| e.to_string())?;
let symbolic = SparseLuSymbolic::analyze(
    a.structural_pattern(),
    SparseOrdering::Natural,
    SparseLuLimits::new(16, 1 << 16),
)
.map_err(|e| e.to_string())?;
let lu = SparseLu::factor(symbolic, a.view()).map_err(|e| e.to_string())?;
let (b, start) = ([1.0_f64, 1.0, 1.0], [initial_value; 3]);
let needed = lu
    .workspace_requirements(1)
    .map_err(|e| e.to_string())?
    .scalar_len();
let mut scratch = vec![0.0_f64; needed];
let mut workspace = SparseSolveWorkspace::borrowed(&mut scratch);
let mut rows = Vec::new();

// 1. 長さ 2 の右辺。
let (kind, changed, r) = solve_attempt(&lu, &a, &b[..2], start, &mut workspace)?;
rows.push(("長さ 2 の右辺で求解", kind, "出力 x", changed, 3, r));
// 2. 長さが必要量 + d の借用の作業領域。
let mut other = vec![0.0_f64; (needed as f64 + scratch_offset) as usize];
let mut short = SparseSolveWorkspace::borrowed(&mut other);
let (kind, changed, r) = solve_attempt(&lu, &a, &b, start, &mut short)?;
rows.push(("必要量 + d の作業領域で求解", kind, "出力 x", changed, 3, r));
// 3. 一つ目の失敗に使った因子と作業領域で、正しい右辺を解き直す。
let (kind, changed, r) = solve_attempt(&lu, &a, &b, start, &mut workspace)?;
rows.push((
    "同じ因子と作業領域で再び求解",
    kind,
    "出力 x",
    changed,
    3,
    r,
));
// 4. 候補の一つに NaN を書く値の更新。
let before = a.values().to_vec();
let mut values = a.workspace(()).map_err(|e| e.to_string())?;
let result = a.update_values(
    |old, next| {
        next.copy_from_slice(old);
        next[1] = f64::NAN;
        Ok::<_, SciOxideError>(())
    },
    &mut values,
);
let kind = result.map_or_else(|e| format!("{:?}", e.kind()), |()| "成功".to_string());
let changed = a
    .values()
    .iter()
    .zip(&before)
    .filter(|(u, v)| u != v)
    .count();
rows.push((
    "NaN を書く update_values",
    kind,
    "行列の値",
    changed,
    4,
    None,
));

let sci3 = serde_json::json!({ "notation": "scientific", "significantDigits": 3 });
let columns = serde_json::json!([
    { "key": "0", "label": "演算" },
    { "key": "1", "label": "結果 e.kind()" },
    { "key": "2", "label": "書き込み先" },
    { "key": "3", "label": "値が変わった成分 [個]", "type": "integer" },
    { "key": "4", "label": "成分の数 [個]", "type": "integer" },
    { "key": "5", "label": "残差 ‖b − Ax̂‖∞ [-]", "type": "number", "format": sci3, "nullText": "解なし" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "attempts" })
);
```

既定の $c = 7$、$d = -1$ では、一つ目と二つ目の求解はどちらも `DimensionMismatch` で拒まれ、出力の 3 成分はどれも $c$ のまま変わらない。
二つ目は、作業領域が足りないことを出力に書き込む前の検査で見つけている。
三つ目の求解は成功し、出力の 3 成分が解に変わり、残差は 0 になる。
失敗した呼び出しのあとも、因子 `lu` と作業領域はそのまま次の計算に使える。
四つ目の値の更新は `NonFinite` で拒まれ、行列の 4 個の値は更新の前のまま残る。
$d = 1$ にすると、必要量より長い作業領域は受け付けられ、二つ目の求解も成功する。
借りた配列のうち、必要量を超える部分は使われない。

## 反復回数の上限と実行コンテキスト

分解、求解、前処理、グラフの出力先を指定する API とスコープ付き API は、`SparseSolveOptions::with_budgets`（グラフでは `GraphExecutionOptions::with_budgets`）で与えた `SolveBudgets` の反復回数の上限に従う。
各アルゴリズムは決まった単位で反復を数える。

| アルゴリズム | 1 回の反復として数えるもの |
|---|---|
| LU、QR の数値分解 | 1 列 |
| QR の最小ノルム Plan の作成（`build`） | 二つの分解で調べる 1 列 |
| Cholesky、LDL の数値分解 | 因子の 1 行（LDL の 2×2 のピボットは 2 行） |
| 不完全分解 | 1 ブロック行 |
| AMG の階層の作成（`AmgHierarchy::build`） | 各段の 1 行、1 集約、積の出力の 1 行（内訳は[代数的多重格子による前処理](oxref:sparse-amg-smoothed-aggregation)） |
| 求解、前処理の適用 | 1 本の右辺 |
| Bellman–Ford 法 | 全辺を緩和する 1 回（全点対の方法が最初に行う負の閉路の探索を含む） |
| Dijkstra 法 | ヒープから取り出す 1 頂点 |
| Floyd–Warshall 法 | 1 個のピボット |
| Dinic 法（最大流） | レベルグラフを作る幅優先探索 1 回、増加路を探す深さ優先探索 1 回（どちらも何も見つからずに終わる最後の探索を含む） |
| Hopcroft–Karp 法（マッチング） | 1 段（増加路がないことを確かめる最後の探索を含む） |
| 割当て | 探索の木に小さい側の頂点を 1 個加えること |

Schwarz 法は右辺 1 本を反復 1 回と数えるほかに、局所の解 1 回と、乗法 Schwarz 法の残差の更新 1 回を、それぞれ評価 1 回と数える。

上限に達すると `ConvergenceFailure`（理由は `IterationLimit`）を返し、取り消しや期限では `ExecutionStopped` を返す。
どちらの場合も、出力先を指定する API の出力と `refactor` の因子は上の規則のとおり変わらず、グラフのスコープ付き API では作業領域の `last_accepted()` が `None` を返す。
Johnson 法はポテンシャルを求める Bellman–Ford 法の反復を呼び出しの上限に数え、各始点からの Dijkstra 法には同じ上限を始点ごとに別々に当てる。
各始点の探索は入れ子のコンテキストで動くので、その反復は外側の呼び出しの上限には数えない。
探索、連結成分、全域森、ラプラシアンは手間の決まった計算なので、コンテキストを取らない。

## エラーの分類

エラーは scioxide-core の `SciOxideError` で、分類を `e.kind()`（`SciOxideErrorKind`）、詳細を `e.view()` で読む。
エラーは呼び出し元を識別する情報を持たない。
この章でよく現れる分類は次のとおりである。

| 分類 | 主な原因 |
|---|---|
| `DimensionMismatch` | 正方でない行列、長さの合わないベクトル、足りない作業領域、別の解析のために事前確保した作業領域 |
| `InvalidInput` | 形の崩れた格納配列、重複の拒否、三角の外の成分、範囲外のオプション、解析と構造の違う行列での `refactor`、負の重みを含むグラフでの Dijkstra 法 |
| `OutOfBounds` | 三つ組、`get`、頂点（始点・終点）の範囲外の添字、`set_value` の範囲外の格納位置 |
| `NonFinite` | NaN や無限大の入力、更新の候補 |
| `Singular` | 0 でないピボットの候補がない LU の列、三角行列と Jacobi 前処理の欠けた対角か 0 の対角、`Strict` の方針で破綻した不完全分解のピボット、行列式が 0 の LDL の 2×2 ピボット、特異な LDL 因子での求解 |
| `NumericalInstability` | 正でない Cholesky のピボット（`Breakdown`）、表せない積・和・逆数（`Overflow`）、0 に落ちた 0 でない乗数（`Underflow`）、丸めで負になった Johnson 法の重み（`LossOfSignificance`） |
| `ResourceLimit` | 上限を超えるフィル、消去中の非零、事前確保 |
| `SizeOverflow`、`AllocationFailure` | 表せない大きさ、確保の失敗 |
| `ConvergenceFailure` | 反復回数の上限に達した |
| `ExecutionStopped` | コンテキストの取り消しや期限 |
| `DomainError` | 負の重みのラプラシアン、ワンショット呼び出しの `shortest_paths` で始点から届く負の閉路、完全な割当てを持たない費用行列での `minimum_cost_assignment` |

診断の値（`IncompleteDiagnostics`、`AmgDiagnostics`、`AssignmentResiduals` など）は観測した量で、精度や最適性の証明ではない。
最適性を厳密に確かめられるのは、整数で比べる `FlowView::verify` と `MatchingView::verify` だけである。

## まとめ

疎行列のアルゴリズムは確定した構造を変えずに値だけを更新し、構造から計算したものを使い回すことを前提にしている。
記号段で何が確定するかはアルゴリズムによって違い、LU と LDL ではピボットのためにフィルが数値段で変わるので、上限はその分を見込んで与える。
答えだけが要るならワンショット関数を、確保をなくしたり反復回数の上限を外側の解法と共有したりするなら出力先を指定する API とスコープ付き API を選ぶ。
上限の型はアルゴリズムごとに異なり、バイト数は `usize` の幅に依存するので、必要な量は `workspace_requirements` で問い合わせてから決める。
失敗した演算は出力も以前の因子も変えないので、エラーを分類 `e.kind()` で読み分け、直前の状態から計算を続けられる。
