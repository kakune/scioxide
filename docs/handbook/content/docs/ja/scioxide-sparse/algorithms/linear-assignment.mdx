ワーカーと処理、送り手と出力先、測定点と候補のように、二つの集合の要素を一対一に対応させ、費用の和を最小にする問題を線形割当て問題という。
これは二部グラフのマッチング（[最大流と二部マッチング](oxref:sparse-bipartite-matching-konig)）の各組に費用を付けた問題で、線形計画として書ける。
双対問題の解であるポテンシャルは、割当てが最適であることの証拠になり、アルゴリズムの中では最短路の辺の長さを非負に保つためにも使う。
このページでは定式化と双対、ポテンシャルを使う最短増加路法、結果と残差の読み方を説明する。
ワンショット関数、標準形式、スコープ付き API といった呼び出しの形の呼び方は、[共通仕様と構成](oxref:sparse-execution-forms)で定義している。

## 主問題と双対問題

$k$ 人のワーカーを $l$ 件の処理（$k \le l$）に一人一件ずつ割り当て、許された組 $(i, j) \in E$ の費用 $c_{ij}$ の和を最小にする問題を、線形割当て問題という。
頂点の少ないワーカーの側を小さい側、処理の側を大きい側と呼ぶ。
変数 $x_{ij} \in \{0, 1\}$ で書くと

$$
\min \sum_{(i, j) \in E} c_{ij} x_{ij}
\quad \text{subject to} \quad
\sum_j x_{ij} = 1 \ (\text{各 } i),
\quad \sum_i x_{ij} \le 1 \ (\text{各 } j),
\quad x_{ij} \ge 0
$$

である。
制約の行列は二部グラフの接続行列で、どの正方な小行列の行列式も 0、1、−1 のどれかになる（完全単模である）ので、0 と 1 の条件を外した線形計画でも、実行可能領域の頂点はすべて整数になり、整数の最適解がある。
その双対問題は、ワーカーのポテンシャル $u_i$ と処理のポテンシャル $v_j$ について

$$
\max \sum_i u_i + \sum_j v_j
\quad \text{subject to} \quad
u_i + v_j \le c_{ij} \ \ ((i, j) \in E),
\quad v_j \le 0
$$

である。
$v_j \le 0$ は、処理の側の制約が不等式 $\le 1$ であることから来る。
正方な $k = l$ ではどの実行可能解でも処理の側の制約が等号になるので、この符号の条件はなくてもよい。

$c_{ij} - u_i - v_j$ を組 $(i, j)$ の**被約費用**と呼ぶ。
任意の割当て $x$ と双対の実行可能解 $(u, v)$ について、

$$
\sum_{(i, j)} c_{ij} x_{ij}
= \sum_{(i, j)} (c_{ij} - u_i - v_j)\,x_{ij} + \sum_i u_i + \sum_j v_j \sum_i x_{ij}
\ge \sum_i u_i + \sum_j v_j
$$

が成り立つ。
第 1 項は被約費用が非負なので 0 以上で、$v_j \le 0$ と $\sum_i x_{ij} \le 1$ から $v_j \sum_i x_{ij} \ge v_j$ だからである。
したがって、次の二つを満たす割当てと $(u, v)$ は、どちらも最適である。

1. 双対の実行可能性：すべての許された組で被約費用が 0 以上で、$v_j \le 0$。
2. 相補性：割り当てた組の被約費用が 0 で、割り当てていない処理で $v_j = 0$。

1 は上の不等式が成り立つための条件で、2 は等号が成り立つための条件である。
相補性だけでは最適性は言えず、双対の実行可能性と組み合わせて初めて最適性の証拠になる。

## 最短増加路法

`AssignmentPlan` は最短増加路法で解く。
以下では小さい側の頂点を行、大きい側の頂点を列と呼ぶ。
初めに各行のポテンシャルを、その行の許された組の費用の最小 $u_i = \min_j c_{ij}$ に、各列を $v_j = 0$ に置くと、被約費用はすべて 0 以上になる。
許された組を一つも持たない行があれば、この時点で完全な割当てはない。
割り当てていない組と割り当てた組を交互にたどる道を交互路という。
次に、まだ割り当てていない行 $i$ を番号の順に一つずつ選び、被約費用を辺の長さとして、$i$ から相手のない列で終わる最短の交互路（増加路）を Dijkstra 法で求める。
被約費用は 0 以上なので、[最短路と負の閉路](oxref:sparse-path-methods)の Dijkstra 法がそのまま使える。
相手のない列に届かなければ、小さい側をすべて覆うマッチングはないので、そこで止まる。
見つけた交互路に沿って割当てを反転すると、割り当てた行が一つ増える。
最後に、探索で距離が確定した列のポテンシャルを、その列の距離と交互路の長さの差だけ下げ、探索の木に入った行（始点の行と、距離が確定した列の相手の行）のポテンシャルを割り当てた組の費用から $u_i = c_{i\sigma(i)} - v_{\sigma(i)}$ で計算し直す。
ここで $\sigma(i)$ は行 $i$ に割り当てた列である。
この更新で、被約費用は 0 以上、割り当てた組の被約費用は 0 に保たれ、$v_j$ は減るだけなので $v_j \le 0$ も保たれる。
距離が確定した列は反転のあとですべて相手を持つので、相手のない列のポテンシャルは $v_j = 0$ のままで、相補性の条件のうち「割り当てていない処理で $v_j = 0$」も成り立つ。
小さい側に $k$ 頂点、大きい側に $l$ 頂点、許された組が $E$ 個あるとき、計算量は $O(kE\log(l + 1) + k + l)$ である。

浮動小数点では、被約費用の計算とポテンシャルの更新に丸めが入る。
探索の木に入った行のポテンシャルは割り当てた組の費用から毎回計算し直すので、割り当てた組の被約費用は丸め 1 回分の範囲で 0 に保たれる。
割り当てていない組の被約費用は、更新のたびに丸めが積み重なる。
そのため、計算した被約費用が負でも

$$
-\bigl(8\varepsilon \cdot \max(\lvert c_{ij} \rvert, \lvert u_i \rvert, \lvert v_j \rvert) + \Delta\bigr)
$$

以上なら 0 とみなす。
$\varepsilon$ は計算機イプシロンで、許容量 $\Delta$ は 0 から始まり、割当てを一つ増やすたびに $64\varepsilon(D + M)$ だけ増える。
$D$ はその増加路の被約費用での長さ、$M$ はその更新で読み書きしたポテンシャルの絶対値の最大である。
これは最悪の場合の見積もりで、ふつうのずれはずっと小さい。
これより負の被約費用は双対が食い違っている証拠なので、`NumericalInstability`（`Breakdown`）で失敗する。
小さな整数のように計算が厳密な費用では、丸めは生じない。

## Plan、結果、残差

`AssignmentPlan::new(pattern)` は疎な構造の保存された成分（0 を含む）を許された組とし、`from_dense(n)` はすべての組を許す正方な問題の Plan を作る。
疎な構造は列より行が多くてもよく、そのときは行列の列の側が小さい側で、前の節で「行」と呼んだ側にあたる。
Plan は構造だけを持つので、同じ構造の多くの費用に使い回せる。
標準形式 `solve(costs, objective)` の `costs` は、疎な Plan では構造の格納順、密な Plan では行優先の $n \times n$ の値である。
長さが合わなければ `DimensionMismatch`、NaN や無限大があれば `NonFinite` で拒む。
結果は、完全な割当てがあれば `AssignmentOutcome::Full(FullAssignment)`、小さい側をすべて覆うマッチングが構造にないときは `AssignmentOutcome::Infeasible` である。
割当てがないことはエラーではなく結果の一つとして返る。
被約費用、距離、ポテンシャル、費用の和のどれかが表せなければ `NumericalInstability`（`Overflow`）で失敗する。

`AssignmentObjective::Maximize` は費用の符号を反転した最小化として解く。
`FullAssignment::as_view()` の `AssignmentView` は、公開フィールドとして、行ごとの相手 `left`、列ごとの相手 `right`、元の符号の費用の和 `objective`、小さい側のポテンシャル `small_potentials`、大きい側の非正のポテンシャル `large_potentials` を持つ。
ポテンシャルは符号を反転した問題のものなので、最大化では最適な割当てで $\sum_i u_i + \sum_j v_j = -\texttt{objective}$ になる。
ワンショット関数 `minimum_cost_assignment(&costs)` は、CSR 行列の保存された成分を許された組と費用として最小化し、`FullAssignment` を返す。
割当てがないときは `DomainError`（引数 `costs`）で返す。

`AssignmentPlan::verify(costs, objective, view)` は、割当ての形を確かめてから、すべての許された組の被約費用を浮動小数点で計算し直し、`AssignmentResiduals` を返す。
費用は `solve` と同じく `DimensionMismatch` と `NonFinite` で検査し、`left`、`right`、二つのポテンシャルの長さが Plan と合わなければ `DimensionMismatch` で拒む。
小さい側に相手のない頂点がある、相手の組が許されていない、`left` と `right` が食い違う、ポテンシャルや `objective` が有限でない場合は、残差ではなく `InvalidInput` で失敗する。
計算し直す和が表せなければ `NumericalInstability`（`Overflow`）で失敗する。
残差は三つである。

- `dual_violation`：負の被約費用の絶対値の最大と、大きい側の正のポテンシャルの最大のうち大きい方。
  双対の実行可能性の違反を表す。
- `complementary_slackness`：割り当てた組の被約費用の絶対値の最大と、大きい側の相手のない頂点のポテンシャルの絶対値の最大のうち大きい方。
- `objective_gap`：主問題と双対問題の目的関数の差の絶対値（最大化では費用の符号を反転して比べる）と、計算し直した費用の和と `objective` の差の絶対値のうち大きい方。

三つとも、厳密な計算で最適な割当てとポテンシャルなら 0 になる。
浮動小数点では丸めの大きさを測る近似の診断で、最適性の証明ではない。
厳密な証明になるのは、整数で比べる `FlowView::verify` と `MatchingView::verify` である。
フィールドは公開なので、他の方法で計算した割当ても確かめられる。

### 割当ての双対の残差と全探索

次のセルは $4 \times 4$ の費用の表で割当て問題を解く。
ワーカー 3 は処理 0 をできないので、その組は構造に置かない。
入力は、ワーカー 0 が処理 2 を行う費用 $b$（1〜10）、最小化か最大化か、処理 0 をだれにも許さないかどうかである。
最後の入力を選ぶと、4 人に対して処理が 3 件しか残らないので、完全な割当てはない。
一つ目の表はワーカーごとの割当てとポテンシャル、二つ目の表は目的関数、双対の目的関数 $\sum_i u_i + \sum_j v_j$、`verify` の三つの残差を示す。
独立な検算として、$4^4 = 256$ 通りの添字の組から置換で許された組だけからなるものを全探索し、費用の和の最小（最大化では最大）を求める。

```rust
//| id: sparse-assignment-duality
//| ref: sparse-assignment-duality
//| title: 線形割当ての双対の残差と全探索による照合
//| run: reactive
//| crates: [scioxide-sparse]
//| inputs:
//|   bonus_task2: {"type":"range","label":"ワーカー 0 が処理 2 を行う費用 b","min":1.0,"max":10.0,"step":1.0,"value":3.0}
//|   direction: {"type":"select","label":"目的","options":[{"label":"最小化","value":"minimize"},{"label":"最大化","value":"maximize"}],"value":"minimize"}
//|   close_job: {"type":"checkbox","label":"処理 0 をだれにも許さない","value":false}
//| cases:
//|   - {"id":"expensive","label":"b = 10","description":"処理 2 をワーカー 1 に回す割当て（費用 13）に切り替わる。","inputs":{"bonus_task2":10}}
//|   - {"id":"maximize","label":"最大化","description":"ポテンシャルは符号を反転した問題のもので、Σu + Σv は費用の和の符号を変えた値になる。","inputs":{"direction":"maximize"}}
//|   - {"id":"infeasible","label":"処理 0 を閉じる","description":"4 人に 3 件しか処理がなく、AssignmentOutcome::Infeasible が返る。","inputs":{"close_job":true}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"assignment","path":"/rows/0/1","equals":2}
//|       - {"artifact":"summary","path":"/rows/0/1","approx":{"value":12,"atol":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/2","approx":{"value":12,"atol":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/3","approx":{"value":12,"atol":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/4","range":{"max":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/5","range":{"max":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/6","range":{"max":1e-12}}
//|   - case: expensive
//|     expect:
//|       - {"artifact":"assignment","path":"/rows/1/1","equals":2}
//|       - {"artifact":"summary","path":"/rows/0/1","approx":{"value":13,"atol":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/2","approx":{"value":13,"atol":1e-12}}
//|   - case: maximize
//|     expect:
//|       - {"artifact":"summary","path":"/rows/0/1","approx":{"value":21,"atol":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/2","approx":{"value":21,"atol":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/3","approx":{"value":-21,"atol":1e-12}}
//|       - {"artifact":"summary","path":"/rows/0/6","range":{"max":1e-12}}
//|   - case: infeasible
//|     expect:
//|       - {"artifact":"summary","path":"/rows/0/0","equals":"割当てなし"}
//|       - {"artifact":"summary","path":"/rows/0/1","equals":null}
//|       - {"artifact":"summary","path":"/rows/0/2","equals":null}
use scioxide_sparse::{
    AssignmentObjective, AssignmentOutcome, AssignmentPlan, DuplicatePolicy,
    ExplicitZeroPolicy, SparseBuilder,
};

let n = 4;
// 処理 0 を閉じると、その列の組をすべて構造から外す。
let job0 = |c: f64| if close_job { None } else { Some(c) };
// 費用の表。None の組は構造に置かない（ワーカー 3 は処理 0 をできない）。
let table = [
    [job0(4.0), Some(2.0), Some(bonus_task2), Some(7.0)],
    [job0(3.0), Some(3.0), Some(5.0), Some(6.0)],
    [job0(2.0), Some(4.0), Some(6.0), Some(3.0)],
    [None, Some(5.0), Some(6.0), Some(4.0)],
];
// sign は最小化の向きにそろえる符号（最大化では費用の符号を反転する）。
let (objective, sign) = if direction == "maximize" {
    (AssignmentObjective::Maximize, -1.0)
} else {
    (AssignmentObjective::Minimize, 1.0)
};
let mut builder = SparseBuilder::new(n, n);
for (i, row) in table.iter().enumerate() {
    for (j, cost) in row.iter().enumerate() {
        if let Some(c) = cost {
            builder.push(i, j, *c).map_err(|e| e.to_string())?;
        }
    }
}
let costs = builder
    .finish_csr(DuplicatePolicy::Reject, ExplicitZeroPolicy::Preserve)
    .map_err(|e| e.to_string())?;
let plan = AssignmentPlan::new(costs.structural_pattern()).map_err(|e| e.to_string())?;
let outcome = plan
    .solve(costs.values(), objective)
    .map_err(|e| e.to_string())?;

// 独立検算: 4^4 通りの添字の組のうち、置換で許された組だけのものの和の最小（最大）。
let mut best: Option<f64> = None;
for code in 0..n.pow(4) {
    let p: Vec<usize> = (0..n).map(|i| code / n.pow(i as u32) % n).collect();
    let total: Option<f64> = (0..n).map(|i| table[i][p[i]]).sum();
    if let (true, Some(t)) = ((0..n).all(|j| p.contains(&j)), total) {
        let better = best.is_none_or(|b| sign * t < sign * b);
        best = if better { Some(t) } else { best };
    }
}

let sci3 = serde_json::json!({ "notation": "scientific", "significantDigits": 3 });
let summary = serde_json::json!([
    { "key": "0", "label": "結果", "type": "string" },
    { "key": "1", "label": "費用の和 objective", "type": "number", "nullText": "なし" },
    { "key": "2", "label": "全探索の最適値", "type": "number", "nullText": "なし" },
    { "key": "3", "label": "Σu + Σv", "type": "number", "nullText": "なし" },
    { "key": "4", "label": "双対の違反", "type": "number", "format": sci3, "nullText": "なし" },
    { "key": "5", "label": "相補性の残差", "type": "number", "format": sci3, "nullText": "なし" },
    { "key": "6", "label": "目的関数の差", "type": "number", "format": sci3, "nullText": "なし" }
]);
let mut report = ("割当てなし", None, best, None, None, None, None);
if let AssignmentOutcome::Full(result) = outcome {
    let view = result.as_view();
    let residuals = plan
        .verify(costs.values(), objective, view)
        .map_err(|e| e.to_string())?;
    // 最小化の向きにそろえた費用での被約費用。
    let mut rows = Vec::new();
    for (i, partner) in view.left.iter().enumerate() {
        let j = partner.ok_or("相手のないワーカーがいる")?;
        let c = table[i][j].ok_or("許されていない組が選ばれた")?;
        let (u, v) = (view.small_potentials[i], view.large_potentials[j]);
        rows.push((i, j, c, u, v, sign * c - u - v));
    }
    let columns = serde_json::json!([
        { "key": "0", "label": "ワーカー i", "type": "integer" },
        { "key": "1", "label": "処理 σ(i)", "type": "integer" },
        { "key": "2", "label": "費用 c", "type": "number" },
        { "key": "3", "label": "u_i", "type": "number" },
        { "key": "4", "label": "v_σ(i)", "type": "number" },
        { "key": "5", "label": "被約費用", "type": "number" }
    ]);
    emit_table_with_columns!(
        columns,
        rows,
        metadata = serde_json::json!({ "id": "assignment" })
    );
    let dual: f64 = view
        .small_potentials
        .iter()
        .chain(view.large_potentials)
        .sum();
    report = (
        "完全な割当て",
        Some(view.objective),
        best,
        Some(dual),
        Some(residuals.dual_violation),
        Some(residuals.complementary_slackness),
        Some(residuals.objective_gap),
    );
}
emit_table_with_columns!(
    summary,
    vec![report],
    metadata = serde_json::json!({ "id": "summary" })
);
```

ワーカー 0 が処理 2 を行う割当ての最良の費用は $b + 9$（残りは $1 \to 1$、$2 \to 0$、$3 \to 3$ の $3 + 2 + 4$）である。
行わない割当ての最良は 13（$0 \to 1$、$1 \to 2$、$2 \to 0$、$3 \to 3$ の $2 + 5 + 2 + 4$）なので、最小値は $\min(b + 9, 13)$ になる。
既定の $b = 3$ では、割当て $0 \to 2$、$1 \to 1$、$2 \to 0$、$3 \to 3$ の費用 12 が全探索の最小と一致する。
双対の目的関数も 12 で、割り当てた組の被約費用はすべて 0、三つの残差もすべて 0 である。
費用がすべて小さな整数なので丸めが生じず、残差は厳密に 0 になる。
$b = 10$ にすると、処理 2 をワーカー 1 に回す割当て（費用 13）に切り替わる。
最大化では費用の和が 21 の割当て $0 \to 3$、$1 \to 0$、$2 \to 2$、$3 \to 1$ が選ばれる。
$0 \to 0$、$1 \to 3$、$2 \to 2$、$3 \to 1$ も和が 21 で最適解は一つではないが、アルゴリズムはこのうち一つを返し、全探索の最大とも一致する。
ポテンシャルは符号を反転した費用のものなので、$\sum_i u_i + \sum_j v_j = -21$ になる。
処理 0 をだれにも許さないと、4 人に 3 件の処理しかないので `AssignmentOutcome::Infeasible` が返り、全探索でも許される置換は見つからない。

## スコープ付き API と作業領域

標準形式 `solve` のほかに、スコープ付き API `solve_scoped(costs, objective, options, workspace, scope)` は事前確保した `AssignmentWorkspace` だけを使い、作業領域を借用した `AssignmentOutcome<AssignmentView>` を返す。
オプションは `GraphExecutionOptions`、`scope` は根のコンテキストか外側の解法のコンテキストである。
作業領域は Plan の `workspace(())` で作るか、`workspace_requirements(())` が返す `AssignmentWorkspaceRequirements` に対して、`AssignmentWorkspace::new()` で作った空の作業領域を `try_reserve` で事前確保する。
要件の `bytes::<S>()` は費用の型 `S` での論理バイト数を返し、作業領域の `check` で足りるかを確かめられる。
足りない作業領域は広げずに `DimensionMismatch` で拒む。
作業領域は縮まないので、一つの作業領域を複数の Plan に使い回せる。

`GraphExecutionOptions::with_budgets` で反復回数の上限を与えると、最短路の探索が小さい側の頂点を木に加えるたびに反復を 1 回と数える（章に共通の規則は[反復回数の上限と実行コンテキスト](oxref:sparse-iteration-limits)）。
上限に達すると `ConvergenceFailure`、取り消しや期限では `ExecutionStopped` を返す。
標準形式とワンショット関数は上限を持たないので、この二つのエラーを返さない。
どの実行方針でも逐次に実行する。
失敗したときと、完全な割当てがない結果のあとは、作業領域の `last_accepted()` が `None` を返す。
`last_attempt()` は、始まる前に拒まれた呼び出しを含めて、最後の試行の記録を返す。

## まとめ

線形割当ては二部グラフのマッチングに費用を付けた線形計画で、双対のポテンシャルが最適性の証拠になる。
`AssignmentPlan` は構造だけを持つので同じ構造の多くの費用に使い回せ、`solve` は割当てがない場合を `AssignmentOutcome::Infeasible` として返すので、呼び出し側で分岐する。
`AssignmentPlan::verify` の三つの残差は、費用の大きさに対する丸めの程度に収まっているかで読み、最適性の厳密な証明としては使わない。
相補性だけでは最適性は言えないので、双対の実行可能性の違反と合わせて確かめる。
最大化ではポテンシャルが符号を反転した問題のものになるので、双対の目的関数は費用の和の符号を変えた値と比べる。
