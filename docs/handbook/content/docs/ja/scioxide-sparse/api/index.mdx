`scioxide-sparse` は、疎行列の格納と変換、積、疎三角系、直接分解（LU、Cholesky、LDL、QR）、前処理（Jacobi、不完全分解、AMG、Schwarz）、並べ替えと彩色、グラフアルゴリズムを提供する。
行列の値には実数と複素数の `f32`・`f64` を使える。
グラフアルゴリズムの重みは実数に限り、最大流の容量は `u64` の整数で、マッチングと連結成分は構造だけを読む。
このガイドでは目的ごとに最初に使う項目を示し、公開されている 135 項目（ルートの 132 項目と `backend::hermitian` の 3 関数）を用途別の表にまとめる。
表の項目名のリンクは、docs.rs の 0.1.0 の API リファレンスを指す。

## 目的別の API

| 形式を変換し、成分と構造を読む | `CooMatrix`、`CsrMatrix`、`CscMatrix`、`BsrMatrix`、`DiaMatrix`、`SparseView` | [格納・組立て・積](storage-and-products/) |

このクレートが使う scioxide-core の型は、scioxide-core の API ガイドで引く。
三角格納の向き `Triangle`、対角の扱い `DiagonalKind`、構造 `StructuralPattern`・`StructuralPatternView`、置換 `Permutation`、作用素のトレイト（`LinearOperator`、`AdjointOperator`、`BlockOperator`、`Preconditioner`）は[レイアウト・作用素・組合せ](../../scioxide-core/api/layouts-operators-combinatorics/)にある。
積の精度 `Accuracy` は[算術・安定変換・対数和](../../scioxide-core/api/arithmetic-and-reductions/)に、上限 `SolveBudgets` は[定義域・許容誤差・上限](../../scioxide-core/api/domains-tolerances-budgets/)に、実行コンテキスト（`ExecutionContext`、`SolveContext`、`SolveScope`）は[求解の回数の集計と実行](../../scioxide-core/api/solve-and-execution/)にある。
前処理を使う Krylov 法（CG、GMRES など）は scioxide-linalg が提供する（[反復法](../../scioxide-linalg/api/iterative-solvers/)）。

## 型の関係

組立てでは、`SparseBuilder` が三つ組を集め、`finish_coo`・`finish_csr`・`finish_csc` が重複の方針 `DuplicatePolicy` と値 0 の方針 `ExplicitZeroPolicy` を受け取って正準な行列を返す。
`CsrMatrix::from_triplets` は同じ処理を `(Sum, Preserve)` の方針で一度に行う。
`CsrMatrix::from_raw` と `CscMatrix::from_raw` はすでに正準な形の配列を検査して受け取る。
確定した行列の値は構造を変えずに書き換えられる。
`CooMatrix`・`CsrMatrix`・`CscMatrix` の `set_value`、`copy_values_from`、`update_values` は、新しい値の有限性を確かめてから値だけを書き換える。
構造を取り替えるのは `CsrMatrix::try_assign_pattern` だけで、新しい構造の値はすべて 0 になり、古い構造に対して作った記号解析と因子は新しい構造には使えない。
`BsrMatrix` と `DiaMatrix` は自分の配列から `from_raw` で作るか、ほかの形式から `from_sparse` で変換し、値を更新する方法を持たない。
どの形式も `view()` で、確保なしに借用ビュー `SparseView` を返す。

積では、`CsrMatrix`・`CscMatrix`・`BsrMatrix`・`DiaMatrix`・`SparseView`・`SparseOperator` が scioxide-core の `LinearOperator`、`AdjointOperator`、`BlockOperator` を実装する。
これらのトレイトの作用は `Accuracy::Standard` で計算し、精度を選ぶときは `SparseView::with_accuracy` が返す `SparseOperator` を使う。
`CooMatrix` はこれらのトレイトを実装しないので、`view()` を通して使う。
疎行列どうしの積は積の構造を `SparseProductPlan` に求めてから値を計算する。
`CsrMatrix::multiply` はこの二段を一度に行う。

直接分解は記号解析、数値因子、作業領域の三つの型に分かれる。
記号解析（`SparseLuSymbolic` など）は構造だけを読んで列の順序を決め、作成後は変わらない。
Cholesky の記号解析は消去木から因子の構造も求めるが、LU と LDL では数値分解のピボットの選択が実際のフィルを決める。
数値分解の `factor` と `factor_scoped` は記号解析を値として受け取り、数値因子（`SparseLu` など）がそれを所有する。
同じ構造の別の行列での再分解 `refactor` は別に事前確保した作業領域（`SparseLuWorkspace` など）を使う。
準備を一括して行うコンストラクター `SparseLu::new(&a)` などは記号解析から数値分解までを一度に行い、ワンショット関数 `solve` と `least_squares` はさらに一度だけ解いて解を返す。
数値因子は分解に成功したときだけ作られる。
三角系、LU、Cholesky、LDL、不完全分解の因子は、$\mathbf{A}^{-1}$（不完全分解では近似の逆）の作用として `LinearOperator`、`AdjointOperator`、`BlockOperator` を実装する。
`SparseQr` はこれらを実装せず、方程式は `SparseQrMinimumNormPlan` で解く。
因子と前処理の求解・適用、`SparseQr` の $\mathbf{Q}$ の作用、最小ノルム解の計算は、共通の作業領域 `SparseSolveWorkspace` を使う。

前処理では、`IdentityPreconditioner`、`JacobiPreconditioner`、`IncompleteFactor`、`AmgCycle`、`AmgPreconditioner`、`SchwarzPlan` が scioxide-core の `Preconditioner` を実装する。
scioxide-core のトレイトを通した因子と前処理の作用は、既定のオプション（`Standard`）で実行し、このクレートでは反復回数を数えない。
反復法が前処理を呼ぶ回数は、呼び出し側の解法が前処理の評価として数える。

グラフでは、`GraphPlan::new`（行列の値を辺の重みとする）と `GraphPlan::from_pattern`（どの辺の重みも 1 とする）が作る `GraphPlan` が、最短路、探索、連結成分、全域森、ラプラシアンの API になる。
`GraphPlan::laplacian` が返す `LaplacianPlan` はラプラシアンを CSR 行列として持ち、作用素のトレイトも実装する。
最大流と割当ては専用の Plan（`MaxFlowPlan`、`AssignmentPlan`）を持ち、二部マッチングは Plan を持たない関数 `maximum_bipartite_matching` で求める。

## 呼び出しの形

一つの操作は名前の末尾で区別する次の形を持つ。
形の定義と使い分けは[呼び出しの形](oxref:sparse-execution-forms)にある。

| 形 | 名前 | 例 |
|---|---|---|
| ワンショット関数 | 自由関数 | `solve(&a, &b)`、`least_squares(&a, &b)`、`shortest_paths(a.view(), 0)` |
| 準備を一括して行うコンストラクター | `new`、`ilu0`、`ic0` | `SparseLu::new(&a)`、`IncompleteFactor::ilu0(&a)`、`AmgPreconditioner::new(&a)` |
| 標準形式 | 接尾辞なし | `SparseLu::factor(symbolic, a.view())`、`lu.solve(&b)`、`graph.shortest_paths(method)` |
| オプション付き形式 | `*_with_options` | `a.add_with_options(&b, options)`、`maximum_bipartite_matching_with_options(pattern, options)` |
| 出力先を指定する API | `*_into` | `lu.solve_into(&b, operation, options, &mut x, &mut workspace, cx)`、`sparse_dense_into(…)` |
| スコープ付き API | `*_scoped` | `SparseLu::factor_scoped(symbolic, a.view(), options, cx)`、`graph.shortest_paths_scoped(method, options, &mut workspace, cx)` |

標準形式は既定のオプション（`SparseSolveOptions` か `GraphExecutionOptions`）、新しい作業領域、`ExecutionContext::sequential_native()` で対応するスコープ付き API か出力先を指定する API を実行し、同じ値を返す。
出力先を指定する API とスコープ付き API は、新しい操作の根となる `ExecutionContext` か、呼び出し元の解法の子としての `&mut SolveContext` を `SolveScope` として受け取る。
探索、連結成分、全域森は手間の決まった計算で、コンテキストを取らない。

## 最小の実行例：重複と値 0 の方針

次のセルは $2 \times 2$ 行列の $(0, 0)$ に 2 と $c$ の 2 つの寄与を、$(1, 1)$ に 7 を順不同で `SparseBuilder` に積み、`finish_csr` で CSR 行列に確定する。
重複の方針は `DuplicatePolicy::Sum`（合算）と `DuplicatePolicy::Reject`（拒否）を並べ、値 0 の方針 `ExplicitZeroPolicy` は入力で選ぶ。
表は確定した行列の保存された成分の数 `nnz()` と、`get` で読んだ 3 つの成分を示す。
拒否された行には行列の代わりにエラーの分類 `e.kind()` と、詳細 `e.view()` から読んだ理由を示す。
既定値と各ケースのテストは、`Sum` の $a_{00}$ が手で計算した $2 + c$ に一致し、保存された成分の数が方針どおりであることを確かめる。

```rust
//| id: sparse-api-duplicate-assembly
//| ref: sparse-api-duplicate-assembly
//| title: 重複の合算・拒否と値 0 の方針で CSR 行列を確定する
//| run: reactive
//| crates: [scioxide-core, scioxide-sparse]
//| inputs:
//|   second: {"type":"range","label":"(0, 0) への 2 つ目の寄与 c [-]","description":"1 つ目の寄与 2 と同じ位置に加える。c = −2 で和が厳密に 0 になる。","min":-5,"max":5,"step":1,"value":3}
//|   preserve_zeros: {"type":"checkbox","label":"値 0 の成分を残す（ExplicitZeroPolicy::Preserve）","description":"外すと Drop になり、重複を合算したあとで値が厳密に 0 の成分を構造から除く。","value":false}
//| cases:
//|   - {"id":"cancelled-drop","label":"c = −2、Drop","description":"和 2 + (−2) = 0 の成分を除くので、保存された成分は (1, 1) の 1 個になる。","inputs":{"second":-2}}
//|   - {"id":"cancelled-preserve","label":"c = −2、Preserve","description":"和が 0 の成分を明示的に格納されたゼロ成分として残すので、保存された成分は 2 個のままである。","inputs":{"second":-2,"preserve_zeros":true}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"policies","path":"/rows/0/1","equals":2}
//|       - {"artifact":"policies","path":"/rows/0/2","approx":{"value":5,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/0/3","approx":{"value":0,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/0/4","approx":{"value":7,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/1/1","equals":null}
//|       - {"artifact":"policies","path":"/rows/1/5","equals":"InvalidInput"}
//|       - {"artifact":"policies","path":"/rows/1/6","equals":"Malformed"}
//|   - case: cancelled-drop
//|     expect:
//|       - {"artifact":"policies","path":"/rows/0/1","equals":1}
//|       - {"artifact":"policies","path":"/rows/0/2","approx":{"value":0,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/1/5","equals":"InvalidInput"}
//|   - case: cancelled-preserve
//|     expect:
//|       - {"artifact":"policies","path":"/rows/0/1","equals":2}
//|       - {"artifact":"policies","path":"/rows/0/2","approx":{"value":0,"atol":1e-15}}
//|       - {"artifact":"policies","path":"/rows/1/5","equals":"InvalidInput"}
use scioxide_core::SciOxideErrorView;
use scioxide_sparse::{DuplicatePolicy, ExplicitZeroPolicy, SparseBuilder};

let zeros = if preserve_zeros {
    ExplicitZeroPolicy::Preserve
} else {
    ExplicitZeroPolicy::Drop
};
let mut rows = Vec::new();
for (name, duplicates) in [
    ("Sum", DuplicatePolicy::Sum),
    ("Reject", DuplicatePolicy::Reject),
] {
    // (0, 0) に 2 と c の 2 つの寄与、(1, 1) に 7 を順不同で積む。
    let mut builder = SparseBuilder::new(2, 2);
    for (i, j, value) in [(0, 0, 2.0_f64), (1, 1, 7.0), (0, 0, second)] {
        builder.push(i, j, value).map_err(|e| e.to_string())?;
    }
    // 重複と値 0 の方針を引数で明示し、CSR へ直接確定する。
    match builder.finish_csr(duplicates, zeros) {
        Ok(matrix) => {
            // 保存されていない位置も、get は厳密な 0 を返す。
            let entry = |i, j| matrix.get(i, j).map_err(|e| e.to_string());
            rows.push((
                name,
                Some(matrix.nnz()),
                Some(entry(0, 0)?),
                Some(entry(0, 1)?),
                Some(entry(1, 1)?),
                None,
                None,
            ));
        }
        // 拒否は分類 e.kind() と詳細 e.view() で読み、ほかの失敗はそのまま返す。
        Err(error) => match error.view() {
            SciOxideErrorView::InvalidInput { reason, .. } => rows.push((
                name,
                None,
                None,
                None,
                None,
                Some(format!("{:?}", error.kind())),
                Some(format!("{reason:?}")),
            )),
            _ => return Err(error.to_string()),
        },
    }
}
let fixed1 = serde_json::json!({ "fractionDigits": 1 });
let columns = serde_json::json!([
    { "key": "0", "label": "重複の方針" },
    { "key": "1", "label": "保存された成分 nnz [個]", "type": "integer", "nullText": "—" },
    { "key": "2", "label": "a₀₀ [-]", "type": "number", "format": fixed1, "nullText": "—" },
    { "key": "3", "label": "a₀₁ [-]", "type": "number", "format": fixed1, "nullText": "—" },
    { "key": "4", "label": "a₁₁ [-]", "type": "number", "format": fixed1, "nullText": "—" },
    { "key": "5", "label": "エラーの分類 e.kind()", "nullText": "—" },
    { "key": "6", "label": "理由 e.view()", "nullText": "—" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "policies" })
);
```

既定値 $c = 3$ の `Sum` の行では、保存された成分は 2 個で、$a_{00} = 5$、$a_{01} = 0$、$a_{11} = 7$ になる。
合算は寄与を厳密に累積してから 1 回だけ丸めるので、寄与を積む順序によらない。
$(0, 1)$ は保存されていない格納されていないゼロ成分で、`get` は行列の範囲内のその位置に厳密な 0 を返し、範囲外の位置には `OutOfBounds` を返す。
`Reject` の行は分類が `InvalidInput`、理由が `Malformed` で、行列は作られない。
$c = -2$ にすると $(0, 0)$ の和は厳密に 0 になり、`Drop` ではその成分が構造から消えて、保存された成分は 1 個に減る。
`Preserve` では同じ 0 が明示的に格納されたゼロ成分として残り、保存された成分は 2 個のままである。
どちらでも `get(0, 0)` は 0 を返すので、違いは構造だけに表れ、分解のフィルやグラフの辺の数に影響する。

## 結果・エラー・診断の読み方

出力を書き込む演算（出力先を指定する API、`refactor`、値の更新）は、すべての検査と計算を終えてから出力や因子を書き換える。
失敗したときは、出力も、以前に成功した因子（置換と値を含む）も変わらない。
作業領域の中身は失敗で変わることがあるが、そのまま次の呼び出しに使える。
ただし、`SparseLuWorkspace` の `try_reserve` か `reprepare_natural` が失敗したときは、分解の前にそのメソッドを呼び直す。
求解・分解・グラフの作業領域では、`last_attempt()` が最後の呼び出しを記録した `AttemptRecord` を返す。
グラフの作業領域の `last_accepted()` は、最後の呼び出しが成功したときだけその結果を返す。
詳しい規則と実験は[失敗したときの出力](oxref:sparse-output-on-error)にある。

記号解析（`SparseLuSymbolic::analyze` など）、不完全分解の解析、AMG の階層の構築は、因子の要素数や作業領域のバイト数などの上限（`SparseLuLimits` など）を必須の引数に取る。
要素数の上限は因子のメモリを前もって確保する大きさにも使われる。
Schwarz 法は Plan と作業領域のバイト数の上限を `SchwarzOptions` で選ぶ。
ワンショット関数とコンストラクター、Jacobi と恒等の前処理は上限を取らない。
記号解析、因子、Plan の `workspace_requirements` は、確保の前に必要な量を返す。
上限の超過は `ResourceLimit`、形の不一致、足りない作業領域、別の解析のために事前確保した作業領域は `DimensionMismatch`、確保の失敗は `AllocationFailure` になる。
ベクトルの長さは数学的な次元にちょうど合わせる。
借用した作業領域は要件の長さ以上であればよく、余った末尾は変更されない（[上限と作業領域](oxref:sparse-limits-and-workspaces)）。

反復回数の上限は `SparseSolveOptions::with_budgets` と `GraphExecutionOptions::with_budgets` で `SolveBudgets` として与える。
出力先を指定する API とスコープ付き API はその上限に使用量を数え、コンテキストが呼び出し元の解法の `SolveContext` なら、その上限にも数える。
何を 1 回と数えるかはアルゴリズムごとに決まっていて、LU と QR の分解は列ごと、Cholesky と LDL の分解は行ごと、求解と前処理の適用は右辺ごとに 1 回である。
上限に達すると `ConvergenceFailure`（`ConvergenceReason::IterationLimit`）になり、`e.view()` の診断にそれまでの使用量が入る。
Schwarz 法は局所解法の呼び出しを部分領域ごとに 1 回の評価として数え、乗法的 Schwarz 法では残差の更新も評価に数える。
評価回数の上限に達すると `ConvergenceFailure`（`EvaluationLimit`）になる。
アルゴリズムごとの数え方の一覧は[反復回数の上限と実行コンテキスト](oxref:sparse-iteration-limits)にある。

入力の値と計算の失敗は、次の分類で返る。
NaN や無限大の入力は `NonFinite` になり、行列の値は構築のときに、右辺は呼び出しごとに検査する。
LU で非零のピボットが見つからない列、三角系と不完全分解の 0 のピボット、行列式が 0 の LDL の 2×2 ピボットは `Singular` になる。
LDL の 1×1 の 0 のピボットは分解では受け付け、その因子で解くときに `Singular` になる。
Cholesky と LDL は実数でない対角や厳密に Hermitian でない値を `InvalidInput` で拒む。
Cholesky の正でないピボット、値の桁あふれ、0 でない結果のアンダーフローは `NumericalInstability` になる。
負の重みを持つグラフのラプラシアン、始点から届く負の閉路（ワンショット関数 `shortest_paths`）、完全な割当てのない費用行列（`minimum_cost_assignment`）は `DomainError` になる。
Plan の `GraphPlan::shortest_paths` と `AssignmentPlan::solve` は負の閉路と割当ての不在をエラーにせず、`PathOutcome::NegativeCycle` と `AssignmentOutcome::Infeasible` の値で返す。
分類は `e.kind()`、詳細は `e.view()` で読み、エラーは呼び出し元を識別する情報を持たない（[エラーの分類](oxref:sparse-error-kinds)）。

`IncompleteDiagnostics`、`AmgDiagnostics`、`AssignmentResiduals` は観測した量で、精度や最適性の証明ではない。
`AssignmentPlan::verify` も、最適性条件の残差を浮動小数点数で計算し直すだけである。
これに対し、`FlowView::verify` と `MatchingView::verify` は整数の条件を厳密に確かめ、流量と切断の容量の一致、マッチングと被覆の大きさの一致によって最適性を示す。
どちらも条件を満たさない結果には `false` を返す。

## まとめ

組立てでは `finish_csr` などに重複と値 0 の方針を渡し、打ち消して 0 になった和を構造に残すかどうかを明示する。
一度だけ解くなら `solve`、`least_squares`、`SparseLu::new` などのワンショット呼び出しの形を使い、同じ構造の行列を繰り返し解くなら記号解析と作業領域を一度だけ用意して `refactor` と出力先を指定する API を繰り返す。
上限を取る解析には因子の要素数と作業領域のバイト数の上限を与え、必要な量は `workspace_requirements` で確保の前に確かめる。
失敗した演算は出力も以前の因子も変えないので、`e.kind()` と `e.view()` で原因を読み、入力や上限を直して呼び直せる。
診断の値は観測した量であり、最適性を厳密に確かめられるのは最大流とマッチングの `verify` だけである。
