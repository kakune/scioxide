物体を回して並進する写像（剛体変換）は、ロボットの関節から手先への座標の受け渡し、測定した点群の座標系の変換、分子構造の重ね合わせの結果の表現などに現れる。
剛体変換は合成の順序で結果が変わり、逆変換では回転と並進の両方を戻す必要がある。
多数の点を変換するときは、結果を書く場所の確保をいつ行うかも計算の設計の一部になる。
このページでは `RigidTransform` の数学と構成を説明し、`apply_batch_into` で多数の点を変換するための作業領域の準備を確かめる。

## 剛体変換の定義

3 次元の剛体変換は回転 $R \in \mathrm{SO}(3)$ と並進 $t \in \mathbb{R}^3$ の組による写像

$$
T(p) = R\,p + t
$$

である。
剛体変換の全体は特殊 Euclid 群 $\mathrm{SE}(3)$ をなし、2 点の距離と向き（右手系か左手系か）を保つ。
`scioxide-spatial` の `RigidTransform` は `Rotation` と同じく能動的で、固定した座標系で点を動かす。
回転の表し方と符号の規約は[回転行列と単位四元数](oxref:spatial-rotation-quaternion)で説明する。

## 合成と逆変換

$T_1 = (R_1, t_1)$、$T_2 = (R_2, t_2)$ について、$T_2$ を先に、$T_1$ を後に適用すると

$$
(T_1 \circ T_2)(p) = R_1(R_2\,p + t_2) + t_1 = R_1R_2\,p + (R_1 t_2 + t_1)
$$

で、合成は $(R_1R_2,\ R_1t_2 + t_1)$ になる。
回転の部分は回転の積で、並進の部分には後に適用する回転 $R_1$ が掛かる。
回転が可換でも（たとえば同じ軸まわりの回転どうしでも）、並進の部分は一般に $R_1t_2 + t_1 \ne R_2t_1 + t_2$ なので、剛体変換の合成は可換でない。

$q = R\,p + t$ を $p$ について解くと $p = R^\top(q - t)$ なので、逆変換は

$$
T^{-1} = (R^\top,\ -R^\top t)
$$

である。
並進は符号を反転するだけでは戻らず、逆回転を掛ける必要がある。

## 同次座標と 4×4 行列

点 $p$ に 1 を加えた同次座標 $[p;\,1]$ を使うと、剛体変換は 4×4 行列の積

$$
\begin{pmatrix} T(p) \\ 1 \end{pmatrix}
= \begin{pmatrix} R & t \\ 0 & 1 \end{pmatrix}
\begin{pmatrix} p \\ 1 \end{pmatrix}
$$

で書ける。
合成 $T_1 \circ T_2$ は行列の積 $M_1M_2$ に、逆変換は逆行列 $\begin{pmatrix} R^\top & -R^\top t \\ 0 & 1 \end{pmatrix}$ にあたる。
他のライブラリやファイル形式と変換をやり取りするときは、この同次行列を使うことが多い。

点の差 $p - p'$ のような方向ベクトルは並進の影響を受けず、$R$ だけで変わる。
同次座標では最後の成分を 0 にしたベクトル $[v;\,0]$ にあたる。
`RigidTransform` は点に `apply`、方向に `apply_direction` を使い分ける。

## RigidTransform の構成と検査

| 関数 | 内容 |
|---|---|
| `RigidTransform::new(rotation, translation)` | 並進が NaN か無限大なら `NonFinite` |
| `RigidTransform::identity()`、`rotation()`、`translation()` | 恒等写像、回転 $R$、並進 $t$ |
| `apply(p)` | 点の写像 $Rp + t$。各成分を並進まで含めた厳密な積和から 1 回だけ丸める。`p` が NaN か無限大なら `NonFinite` |
| `apply_direction(v)` | 方向ベクトルの回転 $Rv$（並進を加えない） |
| `compose(other)` | `other` を先に適用する写像 $(R_1, t_1)\circ(R_2, t_2) = (R_1R_2,\ R_1t_2 + t_1)$ |
| `inverse()` | 逆写像 $p \mapsto R^\top(p - t)$、すなわち $(R^\top, -R^\top t)$ |
| `as_matrix()` | 列ベクトル $[x, y, z, 1]$ に作用する行優先の 4×4 同次行列 |
| `RigidTransform::from_matrix(m, tolerance)` | 最後の行が $[0, 0, 0, 1]$ で、左上の 3×3 が `Rotation::from_matrix` の検査を通る行列だけを受け付ける。拡大、ずれ、鏡映を含む行列は `InvalidInput` |

`apply` は回転行列の成分を通常の浮動小数点演算で作り、$Rp + t$ の各成分 $\sum_j R_{ij}p_j + t_i$ を 4 項の厳密な積和として 1 回だけ丸める（[検査付き算術関数の誤差の保証](oxref:core-checked-arithmetic)）。
途中の積や和はあふれないので、$R_{ij}p_j$ と $t_i$ が打ち消し合って結果が小さくなる場合も、結果が表せる限り成功する。
結果の成分が表せないときだけ `NumericalInstability` を返し、メモリ領域は確保しない。
`apply_direction` は同じ計算を並進なしで行う `Rotation::apply` である。
`compose` の並進 $R_1t_2 + t_1$ と `inverse` の並進 $-R^\top t$ も `apply` と同じ積和で求め、表せなければ `NumericalInstability` を返す。
`compose` の回転の部分は `Rotation::compose` で、四元数の積を正規化し直すので、合成を繰り返しても回転は単位長さからずれない。

`from_matrix` は行列を最も近い剛体変換へ射影しない。
最後の行の各成分と $[0, 0, 0, 1]$ の差、左上の 3×3 の $MM^\top - I$ の各成分と $\det - 1$ を、`tolerance` の閾値 $\mathrm{atol} + \mathrm{rtol}\cdot 1$ と比べる。
数値の計算で作った行列を受け付けるには、丸めの大きさに合った許容誤差（たとえば `Tolerance::from_sqrt_epsilon()`）を渡す。

## 一括変換と作業領域

多数の点に回転や剛体変換を適用するときは、`Rotation::apply_batch_into` と `RigidTransform::apply_batch_into` を使う。
3 次元の `PointSet` を受け取り、結果を出力の配列に書く。
`apply_batch(&points)` は同じ変換を既定の設定で逐次に行い、作業領域と結果の `Vec<[S; 3]>` を呼び出しごとに確保して返す。
結果は `TransformWorkspace` にいったん書き、すべての点が成功してから出力へ写すので、エラーのときは出力が変わらない。
作業領域は次の順に準備する。

1. `TransformOptions::new()` は逐次実行でバイト数の上限なしの設定を返す。
   `with_execution_policy` で実行方針を、`with_max_workspace_bytes` で作業領域が持てるバイト数の上限を変える。
2. `TransformWorkspaceRequest::apply(count, options)` は点 `count` 個の変換、`euler(count, options)` は Euler 角の抽出、`rotations(count, options)` は Slerp と回転スプラインの一括評価の要求で、それぞれ一つのバッファーの大きさを決める。
3. `TransformWorkspace::workspace_requirements(request)` が `TransformWorkspaceRequirements` を返す。
   `bytes::<S>()` は必要なバイト数で、上限を超えれば `ResourceLimit`、`usize` を超えれば `SizeOverflow` になる。
4. `TransformWorkspace::new()` は確保しない空の作業領域を返す。
   `check(&requirements)` は `Capacity::Sufficient` か `Capacity::NeedsGrowth` を返し、`try_reserve(&requirements)` が足りない分を確保する。
   `TransformWorkspace::workspace(request)` は 3.
   と 4.
   をまとめて行う。

一括変換は作業領域を広げない。
点が 3 次元でない、出力の長さが点の数と違う、作業領域が足りない、のどれかなら `DimensionMismatch` を返し、保持している容量の合計が上限を超えれば `ResourceLimit` を返す。
この合計には以前の大きな事前確保で残った容量や、その呼び出しで使わないバッファーの容量も含まれる。
各点の計算は `apply` と同じで、結果が表せなければ `NumericalInstability`、取り消しや期限では `ExecutionStopped` を返す。
一度事前確保すれば、それ以下の大きさの呼び出しはメモリ領域を確保しない。
`ExecutionPolicy::Auto` では出力が 256 個以上のとき並列に実行することがあり、取り消しと期限は 256 点ごとに確かめる。

次のセルはこの手順を $n$ 点の一括変換（$z$ 軸まわりの 90° 回転と並進 $(1, 0, 0)$ m）でたどる。
点は $p_i = (i, 0, 0)$ m で、`PointSet::from_points` で配列を複製せずに借りる。
表 `steps` は段階ごとに、容量の状態、必要なバイト数、変換した点の数、最後の点の写像の $y$ 座標 [m]、エラーの分類を示す。
$n$ 点で事前確保した作業領域は、$n/2$ 点の変換にはそのまま使え、$2n$ 点の変換には足りずに `DimensionMismatch` になる。
そのとき出力の配列は変わらず、最初に入れておいた値 $-1$ のままである。
最後の行はバイト数の上限を 1024 B にした要求の要件で、$24n$ B が上限を超えると `ResourceLimit` になる。

```rust
//| id: spatial-transform-workspace
//| ref: spatial-transform-workspace
//| title: 一括変換の作業領域を要求・要件・確認・事前確保の順に準備する
//| run: reactive
//| crates: [scioxide-core, scioxide-spatial]
//| inputs:
//|   batch: {"type":"range","label":"事前確保する点の数 n","description":"1 点あたり 3 つの f64 で 24 B を使う。","min":2,"max":200,"step":2,"value":100}
//| cases:
//|   - {"id":"small-batch","label":"n = 40","description":"24n = 960 B が上限の 1024 B に収まり、最後の行も成功する。","inputs":{"batch":40}}
//| tests:
//|   - case: default
//|     expect:
//|       - {"artifact":"steps","path":"/rows/0/1","equals":"NeedsGrowth"}
//|       - {"artifact":"steps","path":"/rows/1/1","equals":"Sufficient"}
//|       - {"artifact":"steps","path":"/rows/1/2","equals":2400}
//|       - {"artifact":"steps","path":"/rows/2/4","approx":{"value":99,"atol":1e-12}}
//|       - {"artifact":"steps","path":"/rows/3/3","equals":50}
//|       - {"artifact":"steps","path":"/rows/4/5","equals":"DimensionMismatch"}
//|       - {"artifact":"steps","path":"/rows/4/4","equals":-1}
//|       - {"artifact":"steps","path":"/rows/5/5","equals":"ResourceLimit"}
//|   - case: small-batch
//|     expect:
//|       - {"artifact":"steps","path":"/rows/5/2","equals":960}
use scioxide_core::{ExecutionContext, SciOxideError, RealScalar};
use scioxide_spatial::{
    PointSet, RigidTransform, Rotation, TransformOptions, TransformWorkspace,
    TransformWorkspaceRequest,
};

let n = batch as usize;
let quarter = Rotation::from_axis_angle([0.0, 0.0, 1.0], 0.5 * <f64 as RealScalar>::PI)
    .map_err(|e| e.to_string())?;
let map = RigidTransform::new(quarter, [1.0, 0.0, 0.0]).map_err(|e| e.to_string())?;
// 点 p_i = (i, 0, 0) を m 個並べて写像を一括適用し、結果と最後の点の出力の y を返す。
// 出力は −1 で埋めておくので、失敗したときに書き換えられていないかが読める。
let run = |m: usize, workspace: &mut TransformWorkspace<f64>| -> Result<_, SciOxideError> {
    let data: Vec<[f64; 3]> = (0..m).map(|i| [i as f64, 0.0, 0.0]).collect();
    let points = PointSet::from_points(&data)?;
    let mut output = vec![[-1.0; 3]; m];
    let result = map.apply_batch_into(
        &points,
        TransformOptions::new(),
        &mut output,
        workspace,
        ExecutionContext::sequential(),
    );
    Ok((result, output[m - 1][1]))
};
let kind = |e: &SciOxideError| Some(format!("{:?}", e.kind()));

let options = TransformOptions::new();
let request = TransformWorkspaceRequest::apply(n, options);
let requirements =
    TransformWorkspace::<f64>::workspace_requirements(request).map_err(|e| e.to_string())?;
let bytes = requirements.bytes::<f64>().map_err(|e| e.to_string())?;
let mut workspace = TransformWorkspace::<f64>::new();
let mut rows: Vec<(
    &str,
    Option<String>,
    Option<usize>,
    Option<usize>,
    Option<f64>,
    Option<String>,
)> = Vec::new();
let before = workspace.check(&requirements).map_err(|e| e.to_string())?;
rows.push((
    "事前確保の前",
    Some(format!("{before:?}")),
    Some(bytes),
    None,
    None,
    None,
));
workspace
    .try_reserve(&requirements)
    .map_err(|e| e.to_string())?;
let after = workspace.check(&requirements).map_err(|e| e.to_string())?;
rows.push((
    "事前確保の後",
    Some(format!("{after:?}")),
    Some(bytes),
    None,
    None,
    None,
));
for (label, m) in [
    ("n 点の変換", n),
    ("n/2 点の変換", n / 2),
    ("2n 点の変換", 2 * n),
] {
    let (result, y) = run(m, &mut workspace).map_err(|e| e.to_string())?;
    rows.push(match result {
        Ok(()) => (label, None, None, Some(m), Some(y), None),
        Err(e) => (label, None, None, None, Some(y), kind(&e)),
    });
}
let limited = TransformWorkspaceRequest::apply(n, options.with_max_workspace_bytes(1024));
rows.push(
    match TransformWorkspace::<f64>::workspace_requirements(limited) {
        Ok(r) => {
            let b = r.bytes::<f64>().map_err(|e| e.to_string())?;
            ("上限 1024 B の要件", None, Some(b), None, None, None)
        }
        Err(e) => ("上限 1024 B の要件", None, None, None, None, kind(&e)),
    },
);
let columns = serde_json::json!([
    { "key": "0", "label": "段階" },
    { "key": "1", "label": "容量の状態", "nullText": "—" },
    { "key": "2", "label": "必要なバイト数 [B]", "type": "integer", "nullText": "—" },
    { "key": "3", "label": "変換した点の数", "type": "integer", "nullText": "—" },
    { "key": "4", "label": "最後の点の出力の y [m]", "type": "number", "nullText": "—" },
    { "key": "5", "label": "エラーの分類", "nullText": "なし" }
]);
emit_table_with_columns!(
    columns,
    rows,
    metadata = serde_json::json!({ "id": "steps" })
);
```

既定値（$n = 100$）では、要件は $24 \times 100 = 2400$ B で、事前確保の前は `NeedsGrowth`、事前確保の後は `Sufficient` になる。
$n$ 点と $n/2$ 点の変換は同じ作業領域で成功し、最後の点 $(n - 1, 0, 0)$ は $(1, n - 1, 0)$ に写って、表の $y$ は 99 と 49 である。
$2n$ 点の変換は `DimensionMismatch` で失敗し、出力の $y$ は −1 のまま変わらない。
上限 1024 B の要求は 2400 B を許さないので、要件を求める段階で `ResourceLimit` になる。
$n = 40$ では要件が 960 B で上限に収まり、最後の行も成功する。

## まとめ

剛体変換 $p \mapsto Rp + t$ の合成は $(R_1R_2,\ R_1t_2 + t_1)$、逆変換は $(R^\top, -R^\top t)$ で、`RigidTransform::compose` は引数を先に適用する。
回転が可換な場合でも並進の部分のために合成は可換でないので、関節の連鎖のような計算では適用の順序を式で確かめてから `compose` を呼ぶ。
4×4 の同次行列は `as_matrix` で得られ、`from_matrix` は許容誤差の検査を通る行列だけを受け付ける。
多数の点を繰り返し変換するときは、`TransformOptions` と `TransformWorkspaceRequest` から要件を作って作業領域を一度事前確保し、`apply_batch_into` を呼ぶ。
作業領域が足りなければ `DimensionMismatch`、バイト数の上限を超えれば `ResourceLimit` になり、どちらの場合も出力は変わらない。
